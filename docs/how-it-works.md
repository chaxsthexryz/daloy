# How Daloy works

This file explains each core module in plain language: what it does, why it is built that way, which edge cases it handles, and which tests prove it. It grows with each phase.

## Reviewing the console design

Owners and operators use a fixed 228 px Daylight Minimal sidebar on screens at least 800 px wide, with a sliding hover pill, `Cmd/Ctrl+K` Quick Jump, an always-visible AI usage meter (for owners) and Sign out. Reduced motion turns off hover pill, row, sparkline, switch and panel transitions. On a phone under 800 px, Menu opens the role's links above the bottom bar, Close and Escape return focus to Menu, and changing routes closes the menu. Approvers and requesters keep their own My requests entry. The desktop, phone and role cases in `e2e/navigation.spec.ts` and `e2e/rail.spec.ts` cover these paths.

Staff start on Automations to see which workflows need attention. Activity opens the run behind a status, and Bookings lists appointments staff can change. The sidebar groups daily work, creation and workspace settings. On a phone, the bottom navigation and Menu expose the pages available to the signed-in role. The [offline walkthrough](design/console-review.html) shows these screens with sample records. Open it in a browser and switch between Desktop and Phone. The [phase ledger](design/console-redesign-phases.md) records which actions were tested separately.

## Layout

- `packages/engine`: the rules of a workflow run (definition schema, state machine, retries, expressions). Pure TypeScript with no database or network access, so every rule can be tested in milliseconds.
- `packages/llm-ts`: a small client for language models.
- `packages/db`: Drizzle schema and SQL migrations, shared by the worker and the API.
- `apps/worker`: takes run jobs from pg-boss and executes steps.
- `apps/api`: NestJS API for the console, plus the public webhook and form routes.
- `apps/web`: the console. Vite, React and React Flow. In compose the API serves its build.
- Postgres stores application data and the job queues (pg-boss). See [decision 0001](decisions/0001-no-redis.md).

## LLM client (packages/llm-ts)

What it does: `generate({ system, messages, schema?, model, temperature, maxTokens, timeoutMs })` sends one chat request and returns the text, token usage and, when a zod schema is given, the parsed and validated data. `LLM_PROVIDER` picks the API: `ollama` (the default, Ollama's `/api/chat`) or `openai` (any OpenAI-compatible `/chat/completions`, such as the Gemini API, LM Studio, llama.cpp or vLLM). `LLM_API_KEY`, when set, goes in an `Authorization: Bearer` header.

Why this way: provider, base URL and key are read on every call, so switching between a local model, a hosted free tier and a gateway is a config change only. One OpenAI-compatible mode covers most hosted and local servers, so there is no client per vendor (decision 0015). The schema is sent as JSON schema (Ollama's `format` field, or `response_format` of type `json_schema`) and checked again with zod on the way back, because a model can still return the wrong shape.

Edge cases: an unknown `LLM_PROVIDER` fails the step at once without a request. A reply without token counts records 0 tokens. Error messages carry only the HTTP status, never the provider's error body, which can echo the key. Every failure throws `LlmError` with a `retryable` flag. Timeouts, network errors, HTTP 429 and 5xx are retryable. Other HTTP errors, non-JSON output and output that fails the schema are not retryable. For the last two, `invalidOutput` is set and `usage` holds the tokens the reply cost, so the AI step can retry once and still record the tokens.

Thinking models: Qwen 3.5 and similar models first write hidden reasoning, which counts against `maxTokens`. On a small local model a classify call spent about 300 tokens thinking, so the 256-token console test returned empty content and failed as "not valid JSON". `aiConnection()` in `packages/db/src/ai-settings.ts` therefore adds `chat_template_kwargs: { enable_thinking: false }` (the `extraBody` of the connection) when the provider is `openai` and the base URL is this machine (`localhost`, `127.x`, `[::1]` or `host.docker.internal`). Hosted APIs never get the field, because they may reject unknown fields. With thinking off, Qwen3.5-4B on llama.cpp answers the console test in about 0.5 to 1 second.

The Gemini API is different: Google's thinking docs say Gemini 3 and newer cannot turn thinking off, and that thinking tokens count toward the output limit, which can leave the answer truncated or empty. For the Gemini API's host (from the Gemini preset or from `LLM_BASE_URL`), the connection asks for `reasoning_effort: "low"`, a value every current Gemini model accepts, and sets `reasoningTokens: 2048`. `generate()` adds that to `max_tokens`, so each caller's `maxTokens` stays the budget for the answer itself. If a reply still comes back empty with `finish_reason: "length"`, the error says the model used up its token limit while thinking, instead of "not valid JSON". See decision 0018. Tests: `ai-settings.test.ts` ("turns off thinking only for a local OpenAI-compatible server", "asks Gemini for low thinking") and `llm-ts/src/index.test.ts` ("adds a connection's extra body fields", "thinking headroom", "used up its token limit").

Tests: `packages/llm-ts/src/index.test.ts` (fetch is mocked, no model needed).

## Workflow definition (packages/engine/src/definition.ts)

What it does: a zod schema that checks a workflow before it can be saved or run. A definition has one trigger (webhook, schedule, form or manual), up to 100 steps (http, email, condition, delay, ai, approval) and the edges between them.

Why this way: version 1 allows straight lines with branches only. The schema enforces that shape, so the worker never has to handle a loop or two steps running at once.

Edge cases: duplicate step ids, edges to unknown steps, cycles (including a step pointing at itself), more than one entry step, a plain step with two outgoing edges (that would be a parallel branch), and branch labels that do not fit the step. A condition step branches on `true`, `false` and the optional `invalid`; an approval step on `approved`, `rejected` and `timeout`. A missing branch means the run ends there. Two branches may join into the same later step. Step ids are limited to `a-z`, `0-9` and `_` because they appear inside expression paths.

Tests: `packages/engine/src/definition.test.ts`.

## State machine (packages/engine/src/state-machine.ts)

What it does: decides which status changes are allowed for a run and for a step attempt. Anything else throws `IllegalTransitionError`, which names the kind, the old state and the new state.

The rules live in `transitions.json`:

- A run goes `pending` to `running`. While running it can finish (`succeeded`, `failed`), be `cancelled`, or go to `waiting` when it reaches a delay or approval. A waiting run goes back to `running` when its scheduled job fires, or is cancelled.
- A step attempt goes `pending` to `running`. The table also allows `skipped`, but nothing in the code sets it: a step on a branch that is not taken has no attempt row. A running attempt ends `succeeded` or `failed`, or goes to `waiting` for a delay or approval and ends from there.
- `succeeded` and `cancelled` runs have no way out. A `failed` run can go back to `running` when an operator retries it. A step attempt in a finished state never moves again: a retry is a new attempt row, so a failed attempt never goes back to pending.

Why this way: the table is data, so the tests are generated from it. Every pair of states is tested, 85 cases in total (49 for runs, 36 for steps), and a new rule cannot be added without a matching test result. In the worker each transition will be one database transaction (phase 2).

Tests: `packages/engine/src/state-machine.test.ts`.

## Retries (packages/engine/src/retry.ts)

What it does: after a step attempt fails, `decideRetry` returns one of four answers. `retry` comes with the next attempt number and a delay. `dead_letter` means the error was retryable but the attempts ran out, so the step goes on the dead-letter list for a person to look at. `review` means the call may have gone through and is not safe to repeat (outcome `unknown`, not retryable), so the run waits for an operator (decision 0030). `fail` means the error is not retryable, such as an HTTP 400 or a bug.

A step error can carry an outcome: `not_sent`, `rejected`, `throttled` or `unknown`, and for a 429 the receiver's `Retry-After`. The delay is never shorter than `Retry-After`; one longer than an hour dead-letters instead of retrying early.

Why this way: only errors that say `retryable: true` are retried, because repeating a request that was rejected as invalid cannot succeed. The delay is exponential backoff with full jitter: a random wait between 0 and `base * 2^(attempt - 1)`, capped at 5 minutes, with a 1 second base and 3 attempts by default. The randomness spreads out retries when many runs hit the same failing service. The random function can be passed in, so tests are exact.

Tests: `packages/engine/src/retry.test.ts` (backoff, review for an unknown outcome, Retry-After never shortened, a Retry-After over an hour dead-letters).

## Idempotency

What it does: every step gets the key `runId:stepId` (`idempotencyKey` in `retry.ts`), the same on every attempt. The HTTP step sends it as an `Idempotency-Key` header. The email step builds its `Message-ID` from the key plus the attempt number, so each attempt has its own.

The PayMongo link step sends the same key to PayMongo, which keeps it 24 hours, and also stores one payment row per run and step, so a retry returns the stored link (decision 0045).

Why this way: a receiver that deduplicates by key sees a retry, a Send again or a re-run after a crash as the same request. Daloy never relies on that: most receivers ignore the header. What decides whether a call is repeated is the failure's outcome and the step's `idempotent` flag (decision 0030, see Steps below).

## Expressions (packages/engine/src/expressions.ts)

What it does: `resolveTemplate` fills `{{trigger.<path>}}`, `{{steps.<id>.output.<path>}}` and `{{secrets.<name>}}` placeholders. Secrets are only available while the worker runs a step. A template that is exactly one placeholder returns the raw value (a number stays a number); otherwise values are written into the text, with objects as JSON and missing values as empty text. `conditionBranch` runs a branch condition such as `{ left: "{{trigger.amount}}", op: "gt", right: 100 }` and returns `true`, `false` or `invalid`. `gt`, `gte`, `lt` and `lte` need a finite number on both sides (number text such as "5" counts); a missing value, "45,000" or "Infinity" gives `invalid`. `eq`, `neq`, `contains` and `exists` never give `invalid`.

Why this way: placeholders are property lookups only, so a template cannot run code. See [decision 0002](decisions/0002-expression-resolver.md).

Edge cases: paths that try to reach `constructor`, `__proto__` or `prototype`, or anything other than trigger data or a step output, throw `ExpressionError`. Inherited properties such as `toString` resolve to nothing. Unclosed braces stay as text. Resolution is a single pass, so trigger data that contains `{{secrets.x}}` is inserted as that literal text and never resolved. Templates over 10,000 characters, more than 50 placeholders, paths deeper than 32 segments and output over 100,000 characters are rejected. Numeric strings from forms compare as numbers, so `"5"` equals `5`.

Tests: `packages/engine/src/expressions.test.ts`.

## Database (packages/db)

What it does: `schema.ts` defines the ten tables from PROJECT.md with Drizzle. `pnpm --filter @daloy/db generate` turns schema changes into SQL files in `packages/db/migrations`, and `migrate()` applies them. The `run_state` and `step_state` enums are built from the engine's transition table, so the database cannot hold a state the state machine does not know.

Why this way: one schema package means the worker and the API (phase 3) can never disagree about a column. Generated SQL migrations are plain files a reviewer can read.

Edge cases: `step_runs` has a unique key on `(run_id, step_id, attempt)`, which is the idempotency key, so the same attempt can never be recorded twice. Session ids and API tokens are stored as hashes. Secrets are stored encrypted with the key outside the database.

Migration order: Drizzle applies a migration only when its journal timestamp is later than the newest one the database has recorded, so an entry older than the one before it is skipped for good on any database upgraded step by step (a fresh database applies everything in one pass and never shows it). `migrations.test.ts` fails on an out-of-order journal. `0046_repair_skipped_migrations` re-applies what earlier out-of-order entries skipped, and is a no-op on a healthy database. When a merge trips the test, raise the new entry's `when` above the previous one (decision 0101).

## Worker (apps/worker)

What it does: the worker takes `advance-run` jobs from pg-boss. One job does one piece of work for one run: run the next step attempt, or mark the run finished. Then it queues the run again. `advance.ts` holds this logic and `worker.ts` wires it to pg-boss.

Leases: before it touches a run, the worker writes its name and an expiry time (30 seconds ahead) on the run row. The UPDATE only succeeds when no other worker holds a live lease, so two workers can never advance the same run at once. A heartbeat pushes the expiry forward every 10 seconds while a step runs. The lease is cleared when the job ends.

Crash recovery: every 15 seconds a sweep looks for unfinished runs with no live lease and queues them. The queue keeps at most one waiting job per run, so a run that already has a job queued is not queued twice. If a worker dies in the middle of a step, its lease expires, the sweep queues the run, and the next worker finds the step attempt still marked running. Right before an email or an HTTP request that is not idempotent, the step claims the send (`claimSend` in `advance.ts`): it writes `dispatched_at` under its own claim, then locks the attempt row and checks the claim again, and keeps the lock until the request is on its way. HTTP asks for the claim before every request, redirects included. Email asks for it only after the sender is resolved, so the held connection never waits on another query; the worker's pool (20) is twice its run batch (10). The next worker takes the attempt over only while `dispatched_at` is empty; otherwise it marks the attempt failed with outcome `unknown` and moves the run to `needs_review`. If the old worker is still starting its send, the takeover waits for the lock first, so an operator's Stop can never come before a send that then still starts (decision 0030).

Claims: every attempt gets a random `claim_id` when a worker starts it, and the worker writes the attempt's result only while the claim is still its own. A worker that lost its lease while it was still sending (paused, cut off from the database) cannot overwrite the worker that took over or an operator's answer (decision 0030, as decision 0021 does for Sheets).

Retries: when a step throws, the engine's `decideRetry` picks one of four outcomes. A retryable error with attempts left marks the attempt failed, stores the time of the next attempt on the run (`next_attempt_at`) and queues a delayed job. A retryable error on the last attempt marks the attempt failed with `dead_letter = true` and fails the run. The dead-letter list is a query on that column. An unknown outcome that is not safe to repeat marks the attempt failed with its outcome and moves the run to `needs_review`, where nothing happens until an operator answers (see Run history below). Any other error fails the run at once. The failed attempt stores its outcome in `step_runs.outcome`.

State changes: every change to an existing row goes through `assertTransition` and then a guarded UPDATE (`WHERE state = <expected>`), so an illegal or concurrent change throws instead of overwriting. A step attempt row that is inserted already `running` or `succeeded` (the worker's first attempt, a booking reschedule, an operator's reconcile) is created in that state and does not pass through it. A failed step and its failed run are written in one transaction.

Fetching: the run queue uses Postgres NOTIFY, so a job that is sent wakes the worker at once instead of at its next 2-second poll. The worker fetches up to 10 jobs at a time and fetches again straight away while batches come back full. The runs in a batch are advanced in parallel: the queue holds one waiting job per run, so a batch never contains the same run twice, and each run is still guarded by its lease. Without this the worker managed about half a job a second, because pg-boss waits a poll interval after every fetch (decision 0014).

Shutdown: on SIGTERM the worker stops taking jobs, waits up to 30 seconds for jobs in progress, and closes the database pool.

Waiting: a step can return a wake-up time instead of finishing (delay and approval do). The worker then moves the step and the run to `waiting` in one transaction, stores the time in `next_attempt_at` and queues a job that starts at that time. Nothing sleeps in the worker. When the job runs, or the sweep finds the run after the time has passed, the step moves to `succeeded`, the run moves back to `running`, and the flow carries on. The wait is one attempt, so the step does not run again on wake-up. An approval step schedules no job, because an early answer has to be able to wake the run and the queue holds one job per run; its timeout is picked up by the sweep (see Approval step below). A job that reaches a run before its wake-up time (a duplicate from the sweep, say) does nothing and schedules nothing: a job scheduled for an approval's timeout would block the earlier wake-up that an answer needs. `worker.test.ts` has a test for that case.

Tests: `apps/worker/src/worker.test.ts` runs the real worker against Postgres. It covers a run that succeeds and passes outputs along, a condition branch, a retry that then succeeds, a step that runs out of attempts (dead letter), an error that is not retryable, a run that waits and then carries on, an approval answered by the approver and one that times out, token counts on AI attempts (failed ones too), a run left behind by a crashed worker (resumed with the same idempotency key, no duplicate row), and a run held by another worker's live lease (left alone). `fencing.test.ts` drives two workers by hand with gates and sends real POSTs to a local receiver, counting what it got: a worker paused before its send claim sends nothing after a takeover and Stop, and a worker paused while holding the claim makes the takeover wait and Stop impossible until its one send is out, a POST answered with a 307 only after Stop sends nothing to the redirect target, and as many email sends as the pool has connections all finish while each holds its lock. It also covers the dispatch mark on a POST and none on a safe step, a takeover of a dispatched POST that parks the run without sending, a stale worker answering after the takeover and after an operator's It went through (refused both times), a takeover of a safe step that re-runs it under a new claim, an unknown 503 that parks, Send again with the same key, two concurrent actions, and Retry of a dead-lettered run.

## Steps (apps/worker/src/steps)

What it does: `createExecutor` in `index.ts` runs one step attempt. It decrypts the workflow owner's secrets, resolves every template in the step config, runs the step, and then replaces each secret value in the output and in any error text with `[secret]`. Only the redacted result is written to `step_runs`. The secret crypto lives in `packages/db/src/crypto.ts`, shared with the API.

- HTTP (`http.ts`): GET, POST, PUT, PATCH or DELETE with a templated URL, headers (up to 20) and body. It follows up to 3 redirects and runs the SSRF checks again on each one. A 303, or a 301 or 302 after a POST, switches to GET without a body. A redirect to another origin drops the caller's headers, so an `Authorization` header is not sent to a third party, and a 307 or 308 to another origin fails the step instead of resending the body. A body is first read as a JSON template (`parseJsonTemplate`, decision 0025): placeholders inside quoted strings are text (a whole-string one keeps its type), a placeholder written as a bare value is one typed value (a number stays a number, text becomes one JSON string, missing becomes null), and raw line breaks inside strings are accepted. It is filled value by value and serialised once, so quotes, newlines or a crafted value in form data cannot break it or add keys. A request whose `Content-Type` says JSON must have such a body: otherwise saving is refused and a run fails without retrying. Other bodies are plain text. The whole call has a 10 second timeout and the response is cut off at 1 MB. Output is `{ status, headers, body }`, with the body parsed when the content type is JSON. Every failure carries an outcome (decision 0030). `not_sent`: the socket never opened for request bytes (DNS, refused, an SSRF refusal, a timeout before connecting, or a failed TLS handshake); it is retried, except an SSRF refusal. `rejected`: other 4xx responses, too many redirects, a refused body resend or an oversized response; never retried. `throttled`: a 429, retried no earlier than its `Retry-After`. `unknown`: a 5xx, a 408, or an error or timeout after the socket opened; retried only when the step is `idempotent` (true by default for GET, PUT and DELETE, false for POST and PATCH), else the run waits for review. Once the receiver has answered with a redirect, any later failure of a step that is not idempotent is `unknown`, so a throttled receipt lookup after a 303 never repeats the order. An error status is classified without reading its body, so a large 503 page stays `unknown`. The boundary is the socket's `connect` event (`secureConnect` for https). The request's `finish` event is not used: it only means Node handed the bytes on.
- Email (`packages/db/src/mail.ts`): plain text over SMTP (nodemailer), sent as the workflow owner. `sendAs()` asks `resolveSender()` who that is: the owner's own Gmail account (over SMTP with an app password, or through the Gmail API with a Google sign-in, see Gmail with Connect with Google below), or the installation's server (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`) when they connected none. When `SHARED_MAIL` is `approved`, the default for any server other than Mailpit or localhost, the installation's server only sends for workspace owners the operator approved. Before sending, `sendAs()` counts the recipients against the owner's daily limit with one guarded upsert, so the limit holds across processes. Unapproved or over the limit: a non-retryable error that points to Connect Gmail, and nothing is sent (decision 0024). See Business profile and Gmail sender below. The `to` template is resolved first, then split on commas, and each address is checked. At most 10 recipients. The `Message-ID` comes from the step key and the attempt number. nodemailer writes the message only after the server answers DATA with 354, and its errors do not say how far the session got, so `sendEmail` wraps the message stream and marks its first read (decision 0030). A connection that fails before that mark is `not_sent` and retried. A failure after it without a server reply (a drop, a timeout waiting for the final answer) is `unknown`, and the run waits for review. A 4xx reply is retried and a 5xx is final. An approval email with an unknown outcome is retried instead, since each attempt sends its own working link. The step output records the sending address.
- Condition: evaluates the step's condition and returns the `true`, `false` or `invalid` branch. When the branch is `invalid` and the step has no `invalid` edge, the worker fails the step without retrying and the run error names the values, for example `"gate" needs a number on both sides of gte, but got "45,000" and 30000` (decision 0027).
- Delay: returns a wake-up time 1 second to 30 days ahead (see Waiting above).
- AI task (`ai.ts`): see AI step below.
- Approval: see Approval step below.
- Create payment link (`paymongo.ts`, `packages/db/src/paymongo.ts`): `amount` is text in pesos, parsed by string into integer centavos (1.00 to 9,999,999.99, no floats). It makes a PayMongo Checkout Session (GCash, Maya, card, QR Ph) and returns `{ paymentId, url, reference, amount, amountPesos, status }` for a later step to send (`amount` in centavos, `amountPesos` as text such as `150.50`). One link per run and step: a stored `payments` row is reused. A timeout after the request left goes to needs_review. It counts as `http` usage. Mocked runs call nothing. A live key is refused while the server's `PAYMONGO_LIVE` is not `on`, checked right before PayMongo is called. Decisions 0045 and 0056.

Secrets (decision 0025): only HTTP steps receive them; every other step resolves `{{secrets...}}` to nothing, and saving such a step is refused. In an HTTP step that uses a secret, the host may come only from literal text or secrets: the worker resolves the URL once with trigger and step data blanked and once in full, and refuses the request if the origins differ. The stored input is a preview resolved with every secret as the literal `[secret]`, never the request that went out, so no encoding of a secret reaches history through it.

Secrets page (N26, `apps/web/src/Secrets.tsx`, route `#/secrets`, under Advanced next to API tokens and linked from the webhook trigger's "Signing secret name" field): owners save, replace and delete named secrets through `GET`, `PUT /secrets/:name` and `DELETE /secrets/:name`. The page validates the name (`a-z`, `0-9`, `_`, starting with a letter, up to 100) the same way the API does, uses a password field for the value, and clears it after every save, even a failed one. A value is never kept in state past the request or shown, and the list holds only names and creation dates. Replace fills the name and focuses the value; saving under the same name replaces the secret, so the date shown is when it was first created. Delete asks first. Only owners get the route (the API enforces the same rule). Tests: `apps/web/src/lib/secrets.test.ts` (names, Tagalog copy) and `e2e/secrets.spec.ts` (a saved value never appears in the page or the list response, replace, cancelled and confirmed delete).

Edge cases: a secret that appears in a response body, a response header or an error message is redacted in every form it takes: as is, JSON-escaped, URL-encoded and form-encoded. Redaction is text replacement, so a very short secret (such as `1`) also hides unrelated text that matches it.

Tests: `steps/index.test.ts` (secrets reach the request but not the stored output or errors, trigger data cannot pull in a secret, templates, condition, delay, mocked ai and approval, the approval email and its stored hash, a mocked unknown outcome on the first attempt only), `steps/http.test.ts` (each outcome against local servers: 5xx and 408 on GET, POST and a flagged POST, 4xx, 429 with Retry-After in seconds and as a date, a reset after the body, a timeout after connecting, a 303 to a receipt that answers 429, 503 or 404 (one order, review), a large 503, the send claim asked for once and refused before any request, a plain connection closed on accept, an https connection closed before the handshake, refused, DNS, SSRF), `packages/db/src/mail.test.ts` (recipient cap and validation, message id, SMTP error mapping, sending as the owner), `packages/db/src/mail-uncertain.test.ts` (a scripted SMTP server that fails before DATA, on DATA, right after 354, after the message, by timeout, and with 4xx and 5xx answers) and `steps/senders.test.ts` (two owners, approval mail, disconnecting one owner).

## Plans and usage (packages/db/src/usage.ts, apps/worker/src/steps/index.ts, apps/worker/src/worker.ts, apps/api/src/usage.ts, apps/api/src/workflows.ts, apps/web/src/AppSettings.tsx)

What it does: a workspace's plan (`users.plan`: `pilot`, `business` or `business_plus`, or null) sets how many live automations it may have, how many AI actions, email recipients and web requests it may use, and how often a schedule may fire. The operator sets the plan with SQL (decision 0038, docs/operations.md). The numbers are in `PLANS` in `usage.ts`.

What is counted: an AI step, one "Build with AI" request, or one "Explain in simpler words" press is one AI action. An email step counts its recipients, an Outlook step too, and an approval step counts one email for its link. An HTTP step counts one request. A test run with mocked steps counts nothing, and a test run with live calls counts like a real run. Sheets and Slack steps, form submissions and webhooks are not counted. AI actions are counted per monthly cycle that starts on the plan start date (`users.plan_started_on`). Emails and web requests are counted per day. Both use Manila time. The counts live in `usage_counts`, one row per workspace, kind and period. A workspace with no plan is counted with no limit. A new sign-up starts on the `preview` plan (from `PLANS.preview`: one live automation, a schedule at most hourly, 20 AI actions, 20 email recipients, 50 web requests and 20 files a day or cycle) unless the installation sets `SIGNUP_PLAN=none`. The operator approves an account by setting a real plan, and `preview` never gets the shared AI key (decision 0057, M6). Tests: `apps/api/src/usage.test.ts` ("a fresh public sign-up (M6)") and `packages/db/src/ai-settings.test.ts` (preview gets no shared key).

Where the check sits: in the worker, `runStep` calls `claimUsage()` right before the outside call, with the step's key. One transaction records the key in `usage_claims` (a retried attempt finds it and counts nothing) and adds to the counter with an upsert that only succeeds while the total stays within the limit. Over the limit it throws a `QuotaError`: the step fails with a plain message, nothing is sent and the run keeps its data. The API does the same for `POST /ai/draft` and answers 429. Publishing checks the plan with the owner's row locked: a schedule faster than the plan allows is refused with 400, and a new live automation over the limit with 403. The worker also skips a schedule fire when the workflow already ran within the plan's interval.

What the owner sees: Settings has a Plan and usage section from `GET /usage` with each count, its limit and the date it comes back. Notices start at 80% of a limit. A run stopped by a limit shows as failed with the message from the step, such as "This office reached today's limit of 100 email recipients", and Retry works once the count has reset or the plan changed. The workspace's own AI key does not skip the AI count.

Not counted: the "Send a test email to me" button and the AI settings test.

## AI model settings (packages/db/src/ai-settings.ts, apps/api/src/settings.ts, apps/web/src/Settings.tsx)

What it does: each user picks the model their AI steps run with on the console's AI model page: a local model, the Gemini API, OpenAI or OpenRouter, plus a model name and, for the hosted ones, an API key. `aiConnection()` turns that choice into the provider, URL, key and model that `generate()` uses. The worker calls it for the workflow owner on every AI step, so a change applies to the next step without a restart. The page shows the choice in use at the top and a "key saved" tag on each provider that has one. "Save and test" saves and then makes one real call with a sample inquiry through the Inquiry triage classify prompt, reporting the label, the time and the tokens, or a plain reason for the failure. "Save without testing" skips that call.

Keys per provider: each hosted provider keeps its own encrypted key in `ai_keys` (one row per user and provider, migration `0005_ai_keys_per_provider`, which moved keys saved before it). Switching from Gemini to the local model and back needs no new key. Saving a provider with a new key replaces only that provider's key.

Model names: a hosted provider serves a fixed list of ids, and the page reads that list (`POST /settings/ai/models`, which reads `GET /models` on the provider's own fixed URL) instead of offering only the built-in suggestions. DeepSeek, for example, serves `deepseek-flash` and `deepseek-v4-pro`, while its dashboard labels the first one "DeepSeek-V4.1-Flash", and a dashboard label pasted into the field was saved and then failed every call with HTTP 400 (decision 0047). Saving a hosted choice checks the typed name against that list and refuses one the provider does not serve, naming the ids it does. The test answer does the same when the provider answers 400 or 404. The list is kept for five minutes under a hash of the key and never stores the key itself, and a provider that cannot be reached within three seconds lets the save through, so an outage does not block the page. A local model keeps a free text name.

Local models: for the local choice the page lists the models the server in `.env` actually has, from `GET /settings/ai/local-models` (`listModels()` in llm-ts: Ollama's `/api/tags` or `/models` on an OpenAI-compatible server such as llama.cpp). Only the operator's `LLM_BASE_URL` is ever called. If the server does not answer, the page says so, offers "Check again" and still accepts a typed model name. The local default model is `LLM_MODEL`. `docker compose --profile local-ai up` runs Ollama in its own container with llama3.2 pulled; `LLM_BASE_URL=http://ollama:11434` then makes it the local model (docs/deployment.md, section 9). Without the profile nothing changes.

Why this way: switching models used to mean editing `.env` and restarting the worker. Hosted providers have fixed URLs in code and the local choice uses the operator's `LLM_BASE_URL`, so a user can never make the server call an address of their choosing (decision 0016).

Edge cases: no saved choice means the env vars decide, as before, and so does the "Local model" choice. Neither sends `LLM_API_KEY` unless `SHARED_LLM_KEY=open` and the workspace has a plan, so an account on a public installation cannot spend the operator's key (decisions 0035 and 0038); a hosted provider then needs the account's own key. A hosted choice without a key, new or saved, is refused. The provider is part of each key's associated data, so a key saved for one provider never decrypts as another's. Keys are encrypted like secrets and the API never returns them, only `hasKey` and the list of providers with a key (`keys`). The test is limited to 10 a minute per IP because it costs tokens. Failure messages come from the HTTP status only, never the provider's response body.


The Test button (`POST /settings/ai/test`) makes one real model call, so it claims one AI action first, like Build with AI and Ask. At the monthly limit it answers 429 and calls no provider (security review M7, decision 0055).

Tests: `packages/db/src/ai-settings.test.ts` (env fallback, encrypted key, each provider's key kept across switches, a key moved to another provider does not decrypt, key required, a preset's connection before saving), `apps/api/src/settings.test.ts` (session needed, key never returned, validation, a display name refused with the ids the provider serves, an unreachable provider still saves, the model list route, a refused test call naming the ids, local default from `LLM_MODEL`, local model list and a server that is down, live test against a fake Ollama, unreachable model), `packages/llm-ts/src/index.test.ts` ("listModels"), `apps/worker/src/steps/index.test.ts` (an AI step uses its owner's model), `e2e/settings.spec.ts` (save Gemini with a key, key shown as saved but never displayed, switch to local and back with the key kept).

## Building automations by describing them (packages/engine/src/ai-chat.ts, ai-draft.ts, apps/api/src/ai-chat.ts, ai-draft.ts, apps/web/src/BuildWithAi.tsx, apps/web/src/lib/ai-chat.ts, ai-build.ts, apps/web/src/AiDraft.tsx)

What it does: the Build with AI tab (`#/ai`, owners only, also under "Describe it to the AI" on New automation and as the AI link of the phone bottom bar) is a conversation (`packages/engine/src/ai-chat.ts`, decision 0048). The person says what should happen; the model either asks one question, with two to four short choices offered as buttons that can also be answered in the person's own words, or replies with the whole draft. An empty page is one box with four starter chips (Freelancer, Small shop, Salon, Virtual assistant) that fill the box and send nothing. Enter sends, Shift+Enter is a new line. Once a message is sent the conversation grows above the box, with a thinking indicator (three dots, off under reduced motion) while a message is in flight. The draft appears as plain sentences ("When someone fills the form, Daloy will: 1. Email ...") with the checker's warnings under "Check before turning on" and the apps it needs (Connect in Apps when one is missing). The draft always shows as a summary card, the last bubble, with Turn it on, Change something and Save as draft. Nothing is created until the owner presses Turn it on (`saveDraft` with `publish: true`, then the page opens the automation) or Save as draft; a draft with warnings, or one whose publish is refused because an app is not connected, stays on the card (decision 0049). A later message carries the current draft, so "Change something" is just another sentence in the same conversation. "Build it now" skips any further questions. "Start over" clears the conversation. In the editor, "Ask the AI" is a short chat that rewrites the current draft the same way. Build with AI sends `POST /ai/chat` with the conversation, the current draft when there is one and the connected app kinds; the editor's "Ask the AI" still sends `POST /ai/draft`. Both use the model picked on the AI model page. Each message is one AI action, and a draft can take one more call to fix a lint warning or a malformed reply.

What the model receives: the conversation as typed, the current draft when one exists, and the names of the connected app kinds (google_sheets, slack, outlook, teams), which are checked against a fixed list so no typed text reaches the prompt through that field. People are labels: the owner is `owner@people.invalid`, and the page swaps the real address in after the draft returns (`withPeople`) and back out before the next message (`withLabels`); anyone else the owner names is written as a placeholder address the owner edits. Form submissions, run data, booking details, secrets, the business profile and team addresses are never read in. What the owner types is sent as written, so the page says so under the box.

No model, or a failed call: the page says "The AI is not set up, or it did not answer", shows the server's reason, links to the AI model page and offers the closest ready-made automation from what was typed (`closestTemplate`: a mention of approval gives Purchase request, "website" or "inquiry" gives Reply to a website inquiry, anything else Track an office request). Operators do not see the tab, because `POST /ai/draft` is owner-only. Before N6 the tab spends only the workspace's own model, never the operator's key unless `SHARED_LLM_KEY=open` (decision 0035).

Why this way: the model writes the whole definition as JSON in one reply, and `parseChatReply()` or `parseDraftReply()` checks it with the same `definitionSchema` as a hand-built workflow, so a draft can never hold a step type, edge or branch the engine would refuse. The chat reply is one of two shapes, `{"kind":"question"}` or `{"kind":"draft"}`, so the page never has to guess which it got. The prompt lists each step type's JSON schema (from `stepJsonSchemas()`), the branch labels, the expression syntax and the Inquiry triage template as an example; it stays under about 3,000 tokens so a local model's default context fits it. No JSON schema is sent to the provider: the definition union is too complex for some providers' schema support, so the reply text is parsed instead (decision 0017).

Edge cases: a reply with text or a code fence around the JSON still parses. A question is returned as it is, because a repair round would make the person wait twice for it. After six questions the route adds one line telling the model to draft, so a conversation cannot ask forever. A conversation is at most 20 messages and 2,000 characters each, and the oldest are dropped. A draft that is invalid or has lint warnings gets one more try with its problems listed; if that also fails, the API answers 422 with the reasons and nothing is saved. A model that cannot be reached, or rejects the key, gives the same plain reasons as the AI model test. The description and the current draft go in the user message, never the system prompt. Drafts are never saved or published by the AI: the user reviews, test runs and publishes them, and live HTTP calls still pass the SSRF guard. A taken slug gets `-2`, `-3` and so on. Small local models often write invalid drafts; Gemini or a larger model does much better.

Tests: `packages/engine/src/ai-chat.test.ts` (the two reply shapes, six-question cap, apps and draft passed apart from the words, prompt size, fenced replies, readable errors), `apps/api/src/ai-chat.test.ts` (session needed, a question with its choices, a draft with warnings, the current draft and apps, the stop-asking line, one repair, 422 after two failures, message limits), `packages/engine/src/ai-draft.test.ts` (prompt content and size, fenced replies, readable errors, graph errors), `apps/api/src/ai-draft.test.ts` (session needed, draft from a request, one repair with the errors, 422 after two failures, change request carries the current draft, input limits), `apps/api/src/ai-draft.test.ts` also holds the privacy tests (a workspace with a team member, a business profile, a secret and a submitted form: the recorded model request holds only the placeholder labels), `apps/web/src/lib/ai-build.test.ts` (questions by connected app and team, the request text, the address round trip, a plain sentence per step type, the template choice), `e2e/build-with-ai.spec.ts` (a question with chips, a typed answer, the plain review and warnings, nothing saved until Save as draft, the request body without the owner's address, the no-model template suggestion), `e2e/ai-draft.spec.ts` (the editor's "Ask the AI" chat and lint list; `e2e/llm-fake.ts` stands in for the model).

Prompt size and the stress test: a hosted model gets the full prompt, with every trigger and step and the rules for picking them. A local model (Ollama, or any server on this machine, from `isLocalModel`) gets a shorter one that fits Ollama's default 4,096-token context and leaves out SMS, Messenger, Shopify, payments, Discord, Docs, Airtable, Notion and Trello (decision 0106). The size tests in `packages/engine/src/ai-draft.test.ts` and `ai-chat.test.ts` hold the short prompt to that budget. `extractJson` also accepts a reply that closes its object once too often. `pnpm --filter @daloy/api ai:stress` plays 61 seller requests through `chatTurn`, the code behind `POST /ai/chat`, against the model in `.env` and prints a pass rate, question rate, waits and tokens. Results and fixes are in `docs/ai-stress-2026-11-23.md`. Tests: `packages/engine/src/ai-draft.test.ts` ("full prompt for hosted models", "extractJson") and `packages/db/src/local-model.test.ts`.

### Draft lint (packages/engine/src/lint.ts)

What it does: `lintDefinition()` reads a valid definition and returns warnings for things a business would not want: an approval with no `rejected` or `timeout` edge, a classify label that lands on a branch with no edge, a field or condition named like a test switch (`dry_run`, `test_mode`), a number comparison with no `invalid` edge on a value that may be missing, and a step that only an impossible `invalid` edge leads to.

Why this way: the schema only checks structure, so the QA-01 draft with a `dry_run` branch was legal. Warnings are advice and never block saving (decision 0033). The API lints each valid draft; with warnings it asks the model once more and returns the better of the two attempts together with what is left in `warnings`. The editor lints the open draft and lists the results under "Check before publishing". Messages hold only step ids, field names and labels, so they can go back to the model without free text.

Edge cases: a threshold counts as a number when the engine would read it as one (`"1e3"` is 1,000, `"abc"` is not). The label walk reads the label on either side of the comparison, and stops without a warning when the other side comes from the run. The test-switch warning names Mock mode and says a Live run can still send. A number field that is required on a form or a webhook with fields counts as certain, because every entry point checks it. The label walk uses `conditionBranch()`, so it follows the same comparison the worker makes. A second reply that is broken or unreachable falls back to the first valid draft instead of a 422. A field truly named `test` gets a false warning.

Tests: `packages/engine/src/lint.test.ts` (each rule, one passing and one failing case, shipped templates and guided setups lint clean), `apps/api/src/ai-draft.test.ts` (clean draft makes one call, warnings are sent back once, remaining warnings returned, broken repair keeps the first draft), `apps/api/src/scenarios.test.ts` (the QA-01 dry-run shape, and every fixture), `e2e/ai-draft.spec.ts` (the editor lists the approval warnings).

## AI step (packages/engine/src/ai.ts, apps/worker/src/steps/ai.ts)

What it does: runs one task on text. `classify` picks one of the configured labels, `extract` pulls named fields out of the text, `summarize` writes a short summary and `draft` writes a reply. Later steps read the result, for example `{{steps.classify.output.label}}` in a condition. The model is `LLM_MODEL` (default `llama3.2`) at `LLM_BASE_URL`, through `packages/llm-ts`.

Why this way: the text usually comes from a form or webhook, so it is untrusted. Only the `input` field is a template. It resolves to the text, which goes in the user message between `<data>` and `</data>`. The instructions and the label and field descriptions go in the system prompt, so the schema rejects `{{` in them and they are never resolved. Each task has a fixed output schema (`aiOutputSchema`): classify can only return one of its labels, extract returns every field as text or null. The reply is checked against it, so a later step never sees a shape it did not expect. See [decision 0010](decisions/0010-ai-step.md).

Edge cases: a closing `</data` tag inside the text is escaped, so the text cannot end its own block. Text over 20,000 characters is cut. A reply that is not JSON or fails the schema is retried once, then the step fails. Timeouts and server errors follow the normal retry policy. Input and output token counts are stored on `step_runs` for every attempt, including failed ones. In a mocked test run the model is not called and the step returns a fixed reply that matches the schema (a classify step returns the label whose name sorts first in Postgres jsonb order, so the shortest name). In a "real AI only" test run the model is called as in a live run. A tester can choose a classify step's label in either; the chosen label wins and the model is not asked.

Tests: `packages/engine/src/ai.test.ts` (config rules, output schemas, prompt placement and the escaped closing tag, mock replies match the schema) and `apps/worker/src/steps/ai.test.ts` (a fake Ollama server: the data is only in the user message, the schema is sent as `format`, tokens are returned, a bad reply is retried once, a 503 stays retryable).

How it reads files (decision 0052, `apps/worker/src/steps/ai-files.ts`, `pdf-text-worker.mjs`): the config's `files` lists the names of the form's file fields the model may read, 1 to 5. The definition check rejects a name that is not a file field, and the worker keeps only names that are file fields of the form. With no `files`, no file bytes reach the model. Images are sent to the provider (Gemini JPEG, PNG, WebP and HEIC; OpenAI and OpenRouter JPEG, PNG and WebP; DeepSeek none; the local model none unless `LLM_VISION=on`). PDFs are read as text with PDF.js in a worker thread (10 second timeout, 256 MB heap, first 10 pages, 20,000 characters), and the text goes inside the `<data>` block.

File edge cases: a file the model cannot take, a scanned PDF, a file past the 7 day retention, or more than 10 MB of images in one step fails the step with a plain message and no AI action counted. A hosted model that answers 400, 404, 413, 415 or 422 to an image fails without a retry and without the provider's body. The quota is one action for the step plus one per file, claimed once under the step key after all checks. An empty optional file field runs on text alone. Test runs never carry files, and a mocked run does not call the model.

File tests: `apps/worker/src/steps/ai-files.test.ts` (images, PDF text, limits, refusals, quota), `apps/worker/src/steps/ai.test.ts` (an unlisted file is never sent), `packages/llm-ts/src/index.test.ts` (image payloads per provider and the refused statuses), `packages/engine/src/ai.test.ts` and `definition.test.ts` (the `files` config and the file-field check), `packages/db/src/ai-settings.test.ts` (which types each provider reads, `LLM_VISION`), `e2e/receipt-expense.spec.ts` (the receipt template and the editor checkbox).

## Approval step (packages/db/src/approvals.ts, apps/api/src/approvals.ts)

What it does: emails a person a link, waits, and continues on the `approved`, `rejected` or `timeout` branch. The config has `to`, `subject`, `message` (all templates) and `timeoutSeconds` (one minute to 30 days).

How it works: the worker creates a 32-byte random token and stores only its SHA-256 in `approvals` with the expiry. The email holds the link `PUBLIC_URL/approvals/<token>`. The token is not part of the stored step input, so it never shows in run history. The step and the run go to `waiting`. Opening the link (GET) shows the message and two buttons and changes nothing. Pressing one (POST) records the decision with one guarded UPDATE that only matches a link that is unused and not expired, sets the run's wake-up time to now and queues it. When the step wakes, the worker calls `claimTimeout` in the same transaction that finishes the step: if nobody answered, it marks the link used with the decision `timeout`. Either way the step takes the branch that is stored. See [decision 0009](decisions/0009-approval-links.md).

Edge cases: a second click, an expired link and an unknown token all get the same 404 page. If the click and the timeout happen at the same moment, the row lock lets only one of them win. One approval step of one run is one decision, however many links it sent: a retry after a failed send (a new attempt) or a re-run after a crash sends another link, earlier links keep working, the first answer through any of them decides for all, and they all stop working together. Every link keeps the first link's deadline. If an earlier link was already answered, the retry takes that decision and sends nothing. An answer that arrives before the run is parked wakes the run at once, and a wake-up before the deadline with no answer puts the run back to sleep instead of taking the timeout branch. All of this runs under the run's row lock (decision 0009). The public routes allow 30 page views and 10 decisions a minute per IP, and answer with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. In a mocked or "real AI only" test run no email is sent, no approval link is stored, and the step takes the decision the tester chose (`approved`, `rejected` or `timeout`), `approved` by default, at once.

Named approvals: with `approver` set instead of `to`, only that workspace member can answer, signed in, and the email goes to their sign-in address. The guarded UPDATE also requires the signed-in user to be the approver and, at that moment, a member of the run's workspace with the owner or approver role, and it stores who decided. A signed-out visitor sees only a sign-in link and anyone else sees "assigned to someone else", with no request details. See the office teams section below and [decision 0022](decisions/0022-workspace-members-named-approvals.md).


Counting: the step resolves the final recipient list (the named approver, or the `to` list of up to 10 addresses), checks it like the email step and claims one email unit per address before it creates the link, so an approval to several people costs what an email to them costs (security review M8).

Tests: `packages/db/src/approvals.test.ts` (stored hash, single use, expiry, replacing a link, the click and timeout race), `apps/api/src/approvals.test.ts` (escaped page, GET changes nothing, POST once then 404, same page for unknown and expired links, bad decisions rejected, rate limit), `apps/worker/src/worker.test.ts` (approve and timeout branches) and `e2e/approval.spec.ts` (a live run waits, the email arrives at a test SMTP server, the link approves once, the run finishes on the approved branch).

## SSRF protection (apps/worker/src/steps/ssrf.ts)

What it does: stops an HTTP step from reaching the server's own network. Only `http:` and `https:` on ports 80 and 443 are allowed. A `node:net` `BlockList` holds the private, loopback, link-local (including the 169.254.169.254 metadata address), shared, reserved and multicast ranges for IPv4 and IPv6. IPv4-mapped IPv6 addresses such as `::ffff:127.0.0.1` are checked against the IPv4 ranges.

Why this way: the hostname is checked inside the `lookup` function passed to `http.request`. The socket connects to the exact address that lookup returned, so a DNS server cannot answer once with a public address for the check and then with a private one for the connection. See [decision 0006](decisions/0006-ssrf.md).

Edge cases: Node does not call `lookup` for IP literals, so `checkUrl` checks those first. `new URL()` has already normalised spellings such as `http://2130706433` and `http://0x7f.1` to `127.0.0.1`. A hostname is refused if any of its addresses is blocked. Requests use `agent: false`, so a pooled connection never skips the check. When `HTTP_ALLOWED_HOSTS` is set (the public demo), `checkUrl` also refuses any host not on that list; an entry is an exact host or `*.domain` for its subdomains, and `*.example.com` does not match `example.com` itself. Redirects go through `checkUrl` again, so they cannot leave the list either.

Tests: `steps/ssrf.test.ts` (every range, IPv6 and mapped addresses, scheme and port rules, odd IP spellings, lookup with mixed answers, the allowlist with exact, wildcard and look-alike hosts) and `steps/http.test.ts` (redirect to a private address, redirect to a host off the allowlist, DNS rebinding with a resolver that changes its answer, the redirect limit, the 1 MB limit, the timeout, header stripping across origins).

## API (apps/api)

What it does: the console API covers sign up, login, workflows and their versions, secrets, API tokens and run history. `app.ts` builds the Nest app and `main.ts` starts it. Each file in `src` holds one area: `auth.ts`, `workflows.ts`, `secrets.ts`, `tokens.ts`, `runs.ts`, and `public.ts` for the unauthenticated trigger routes.

Validation: every body, path parameter and query value goes through `ZodPipe` with a zod schema before a handler sees it. Workflow definitions are checked with the engine's `definitionSchema`, so the API and the worker apply the same rules.

Sessions: logging in creates 32 random bytes, sent as an httpOnly, SameSite=Lax cookie, marked Secure when `SECURE_COOKIES=true` or `NODE_ENV=production`. Only the SHA-256 of the cookie is stored, so a database leak does not hand out live sessions. Passwords are hashed with argon2id. A login with an unknown email still runs a hash check, so response time does not reveal which emails exist.

Changes from another origin: a signed-in POST, PUT, PATCH or DELETE is refused with 403 when the browser's `Origin` header is neither the `PUBLIC_URL` origin nor the host the request was sent to (`SessionGuard`, decision 0078). SameSite=Lax alone does not stop a sibling origin of the same site. A request with no `Origin` passes, so tokens, scripts and tests are unchanged.

Ownership: every console query filters on the signed-in user, and another user's workflow returns 404, the same as one that does not exist.

Versions: saving a definition adds the next immutable version. Publishing also makes it live (the newest published version is the live one) and syncs the workflow's single trigger row and pg-boss schedule.

Secrets: values are encrypted with AES-256-GCM using `SECRETS_KEY`, with a fresh IV per write. The owner id and secret name are bound in as associated data, so a ciphertext copied to another row will not decrypt. The API never returns a value, only names.

API tokens: shown once at creation, stored as SHA-256, and revocable. MCP clients send them as bearer tokens (see MCP below). The console page `#/tokens` creates, lists and revokes them.

Rate limits: every route allows 120 requests per minute per IP, login, form submissions and approval decisions 10, approval pages 30, webhooks 60, sign-up 10 per hour (`REGISTER_LIMIT_PER_HOUR`), and invite accepts 10 per minute (`INVITE_ACCEPT_LIMIT_PER_MINUTE`). Request bodies are capped at 256 kb for JSON and 64 kb for forms. The IP is `req.ip`. Behind a proxy that is the proxy's address, so every client would share one bucket; `TRUST_PROXY` tells Express how many proxies sit in front, and it then takes the client address from that many entries from the right of `X-Forwarded-For`. A hop count, never "trust all", because the left entries are whatever the client sent. `deployEnv()` in `http.ts` refuses a `TRUST_PROXY` or `SECURE_COOKIES` value it cannot read, so a typo stops the boot instead of turning a protection off.

Tests: `api.test.ts` drives the real app with supertest against Postgres. `deploy.test.ts` covers one proxy hop (a bucket per client, a spoofed left entry ignored), no proxy (`X-Forwarded-For` ignored), the sign-up limit, the Secure cookie and `deployEnv`. `secrets.test.ts` covers encryption and signature checks. `e2e.test.ts` runs the API and the worker together, from a webhook call to a finished run.

Limits: rate limit counters live in process memory, so each API instance counts on its own.

## Triggers

- Field checks: a form trigger's fields, and a webhook trigger's optional `fields`, are checked by `parsePayload` (packages/engine/src/definition.ts) wherever a payload comes in: the hosted form, a webhook call, a builder test run, the console Run button and MCP. A number field can set `min`, `max` and `integer`; number text must be plain decimal, so "45,000", "0x10" and "Infinity" are refused. Empty text and null count as not given. A refusal is a 400 with one message per field, such as `amount: must be at least 0.01` or `order_id: is required`. For webhooks, test runs and console runs, declared fields are stored parsed and other keys pass through unchanged; the hosted form keeps only its fields. Saving refuses `min` above `max` and number limits on a non-number field (decision 0027). `datetime` and `resource` fields are described under "Zoned times, reminders and resources".
- PayMongo payment: `POST /hooks/paymongo/:path`, one random path per connection. The `Paymongo-Signature` header (`t`, `te`, `li`; HMAC-SHA256 of `t.rawBody`) is checked in constant time for the connection's mode, and `t` must be within 72 hours (5 minutes ahead). Only an exact amount and currency match marks a payment paid (otherwise needs_review). Each published workflow with the trigger "When a PayMongo payment is confirmed" gets one run per payment and status (`paid` or `refunded`), keyed `paymongo:<paymentId>:<status>`. The run is a test run (emails, HTTP calls and sheet rows mocked) when the payment is a sandbox payment or was made by a builder test run, and a payment only changes on an event of its own mode. An event id this workspace has seen answers 200 `duplicate`. A paid or refund event with no matching payment yet is kept: a later paid event applies a kept refund, so a refund that arrives first still ends refunded, and storing a checkout session applies a kept paid event. Payload: `status`, `reference`, `amount` (centavos), `amountPesos` (text), `currency`, `livemode`, `paymentId`, `sourceRunId`, `providerPaymentId`. Decision 0056. Not handled: failed payments, expiry, partial refunds. See [decision 0045](decisions/0045-paymongo-payments.md) and [live-paymongo-check.md](live-paymongo-check.md).
- Shopify order: `POST /hooks/shopify/:path`, one random path per connection, registered in the store as an `orders/create` subscription when Shopify is connected. The `X-Shopify-Hmac-Sha256` header is checked against the app's client secret, and each published workflow with the trigger "When a new Shopify order comes in" gets one run per order, keyed `shopify:<shop>:order:<order id>`. See "Shopify products and order trigger (I2, decision 0105)" below.
- Manual: `POST /workflows/:id/runs` from the console runs the live version with a JSON payload, whatever its trigger type.
- Webhook: `POST /hooks/:path`, where the path is 32 random bytes made at the first publish and kept across later publishes. If the trigger names a secret (`hmacSecret`), the request must carry `X-Daloy-Timestamp` and `X-Daloy-Signature` (see Webhook signatures below), compared in constant time. A named secret that no longer exists rejects every call, and so does a blank or missing name: any `hmacSecret` key that is present means the call must be signed, so an old definition with a blank name fails closed with 401. The definition schema now requires a name made of `a-z`, `0-9` and `_`, and publishing checks that the workspace has that secret (decision 0057, M1; tests in `packages/engine/src/definition.test.ts` and `apps/api/src/public-intake.test.ts`). The signature is checked before the fields. A webhook can set `eventKey`, a template such as `{{trigger.event_id}}`; without one, a timestamped signed call is keyed by its signature (an exact replay), and otherwise the caller's `Idempotency-Key` header is the key. The header is not signed, so a signed sender that retries with a new timestamp needs `eventKey` to avoid a second run. The invoice starter is signed with the workspace secret `invoice_webhook_secret`, requires the timestamp and keys on the invoice number (decision 0056). Only roles that can manage automations see the webhook URL, and the editor's New URL button (`POST /workflows/:id/webhook-url`) replaces it, after which the old one answers 404. A second call with the same key gets `{ runId: <first run>, duplicate: true }` and starts nothing. A key that comes out empty, or longer than 200 characters, is a 400 (decision 0029).
- Form: public forms, webhooks and the PayMongo listener find the trigger and its latest published version in one SQL statement, so a submission that overlaps a republish runs the version it was read with, and its fields, signing secret and payment events come from that version (decision 0057, H3; tests in `apps/api/src/public-intake.test.ts` and, for PayMongo, "starts the version its listener was read with..." in `apps/api/src/paymongo.test.ts`). `GET /forms/:triggerId` renders an HTML form from the field list in the definition, with labels escaped. `POST` validates the fields and starts a run. Number inputs carry the field's `min`, `max` and `step` so the browser warns early; the server checks the same limits. A hidden honeypot field (`_website`, a name no form field can have) catches bots: if it is filled, the API answers as if it worked and starts nothing. A form of an office request automation also records a request (see "Track an office request").
- Schedule: publishing registers a pg-boss cron schedule keyed by workflow id. pg-boss sends a job to `schedule-trigger` at each tick, and the worker starts a run of the live version. Publishing a version with another trigger type removes the schedule.

### Incoming website email

The owner chooses the email trigger in the editor and connects the folder receiving website notifications. The API checks workspace ownership and stores the encrypted password separately from the definition. A successful check on a draft verifies access. After publication, **Listening for new mail** means the worker has recorded the folder's current position. A draft-period message stays in the inbox. Editing a continuously published email workflow keeps its position. Switching away and back starts from new mail.

The worker opens the folder read-only. It reads a window of up to 20 message numbers at a time, checks sizes before downloading, skips messages above 256 KiB, and stores up to 20,000 characters of decoded body text. Steps can read `from`, `replyTo`, `to`, `subject`, `text`, `messageId` and `receivedAt` under `trigger`. The received time comes from the mailbox. The From and Reply-To headers are supplied by the sender.

Each poll holds a temporary claim. A replaced credential, disconnected mailbox or newer claim prevents an old response from recording a run. The worker saves the run, event key and checkpoint together. If it stops after saving but before enqueueing, the regular sweep finds the pending run. It retries temporary connection failures. If the mailbox renumbers its messages, the owner must confirm a fresh baseline before intake resumes.


Fair turns (security review M13): a worker polls one mailbox at a time. It takes live mailboxes (a published email trigger) before drafts, then the workspace whose mailboxes were checked longest ago, and never two mailboxes of one workspace at once across workers. A temporary failure doubles the wait before the next check, up to one hour; a successful read, a saved connection or the owner's Check now resets it. So slow or failing draft mailboxes of one office cannot hold back another office's incoming mail.

`apps/api/src/email-source.test.ts` covers ownership, connection checks and publication. `packages/db/src/email-sources.test.ts` checks credential storage. The worker's `email-in.test.ts` and `imap.test.ts` exercise redelivery, competing polls, network boundaries, MIME decoding and interrupted reads. `e2e/email-in.spec.ts` connects a local mailbox from the editor and follows a new inquiry through run history.

## Zoned times, reminders and resources (packages/engine/src/zoned.ts, apps/api/src/resources.ts)

What it does: a `datetime` field reads a time in the field's IANA timezone and checks it on the server: it must be a real date and time, exist in that zone, be in the future, and start on the field's slot grid (`slotMinutes`, counted from local midnight). It is stored as local time with the offset, such as `2027-01-20T14:00:00+08:00`. A delay can wait `until` such a time, moved by `offsetSeconds` (-3600 for an hour before). A `resource` field takes the id of one of the workspace's active resources (Resources page, `GET/POST/PATCH /resources`) and stores `{ id, name }`.

Why this way: `Intl.DateTimeFormat` already carries the timezone database in Node and in browsers, so a short conversion function replaces a date library (decision 0031). To turn a wall time into an instant, it tries the zone's offset a day before and a day after, and keeps each candidate at which the zone really shows that wall time. That gives none in a spring-forward gap and two in a fall-back overlap. Input with an offset (webhooks, MCP) is converted to the field's zone first, so the slot grid is always the business's own clock. The resource name is copied in when the run starts, so renaming a therapist never rewrites history.

Edge cases: a gap time is refused naming the zone; a time that happens twice is refused unless it carries its offset; 32:00, 30 February, past times, off-grid times and seconds are refused; `.000Z` from `toISOString()` is fine. Lord Howe's 30-minute change is handled like any other. A delay whose time has passed takes its `late` edge, or ends the run with "Skipped: the wake-up time had passed" in run history, so a reminder is never sent after the appointment it was for. A mocked test run waits one second but shows the real wake-up time. A resource of another workspace, an archived one, or a name instead of an id is refused at the hosted form, webhooks, test runs, the Run button and MCP. A replayed webhook event (same `Idempotency-Key` or `eventKey`) gets its first run back even if its resource was archived or its time has passed since; only new events are checked. The hosted form sets the browser's `step` only when the slot divides the day, because browsers count steps from 1970 and other grids would block real slots. The Resources page ignores a list answer older than the latest one.

Tests: `packages/engine/src/zoned.test.ts` (New York, London, Manila, Kathmandu, Lord Howe and UTC, gaps, overlaps, offsets, slots, future), `payload.test.ts` and `definition.test.ts` (field options, delay `until`, `late` edges), `apps/worker/src/steps/index.test.ts` (waiting, late, bad `until`, mocked wake-up time), `apps/api/src/resources.test.ts` (roles, workspace isolation, every entry point, rename keeps history, replays after archiving and after the time passed, form steps), `mcp.test.ts`, the QA-02 harness cases and `e2e/booking-form.spec.ts` (also a held first list answer, and 00:07 on a seven-minute grid in Chromium).

## Bookings (packages/db/src/bookings.ts, apps/worker/src/steps/index.ts, apps/api/src/bookings.ts, apps/web/src/Bookings.tsx)

What it does: a `booking` step books a workspace resource for a time from a datetime field (create), moves it (reschedule) or cancels it, and takes the branch `done`, `taken` or `not_found`. Owners and operators see live bookings on the Bookings page and in `GET /bookings`, and cancel or reschedule them there or through the MCP tools `list_bookings`, `cancel_booking` and `reschedule_booking`. A staff reschedule starts one new run that carries on after the booking step with the new time, and the runs for the old time stop at their next step.

No-show (N27): on the Bookings page, Mark no-show shows on an active booking whose start has passed (`POST /bookings/:id/no-show` with the version; the API refuses a future or cancelled booking with 409). One transaction sets the status `no_show` (migration 0033 widens the status check), bumps the version, logs the change and starts one run of the workspace's no-show follow-up, found as the first workspace workflow whose published version begins with a condition on `{{trigger.status}}` equal to `no_show` (the template or an edit of it; none gives a 409 and changes nothing). The run's payload is `status: no_show`, `customer_email`, `customer_name`, `service` and `reference`, read from the payload of the run that made the booking (`customer_email` or `email`, `customer_name` or `name`; no email gives a 409). The run is not linked to the booking, so it is not stopped as superseded. A repeat with the same version is a duplicate with the same run, and the run key holds the version, so two markings never start two follow-ups. Undo no-show (`POST /bookings/:id/undo-no-show`) cancels the follow-up while it is still pending or waiting on its delay and sets the booking active again; once the follow-up has run past that (an email sent, or failed) it is a 409 and the booking stays a no-show. The Google Calendar event is left as it is.

Why this way: Postgres decides every conflict. An exclusion constraint refuses overlapping active bookings for one workspace, test scope and resource, so two requests for the same slot can never both succeed, whichever path they take (decision 0032). Each booking has a version. A run remembers the version it belongs to and checks it before every attempt, and again under a lock right before an email or an unsafe HTTP call, so a reminder for a moved or cancelled booking is not sent. Every change is logged per version in the database, which is how a repeated staff or MCP request finds its first answer instead of moving the booking twice.

Edge cases: back-to-back slots fit (ranges are `[start, end)`); a cancelled booking frees its slot. A step retried or taken over after it booked returns the stored result, and attempts of one step that overlap take turns on an advisory lock, so a takeover that starts while the first worker is still committing waits and then returns that worker's result. Ten concurrent bookings for one slot give one `done` and nine `taken`. A repeated reschedule with the same version and time (also written with another offset) answers `duplicate: true` with the same run and the booking as that change left it, even after later changes or once its time has passed, because the change log is read before the time is checked; a different change from the same version, or a stale version, is a 409; a taken time is a 409 that changes nothing. The booking step checks its start with the datetime field's zone, slot and future rules again when it runs. A staff or MCP time written without an offset is read in the booking's own timezone, which the Bookings page shows, so editing the workflow's field zone later does not shift it. A staff reschedule copies the trigger payload of the run that created the booking, so a booking moved by a desk workflow still sends the new confirmation and reminder to the guest. A reschedule is refused when the published version no longer has the booking step, or when a later step reads a step that ran before the booking. Builder test runs only make `TEST-` bookings, which never collide with live ones and never show to staff or MCP. A booking whose run failed afterwards stays active and shows "needs attention". A superseded waiting reminder shows "superseded" until it wakes and stops. Sheets, Slack, Outlook and Teams deliveries are sent by the delivery worker apart from the run, so the worker checks the booking itself: right before the provider call it reads the run's current booking link and the booking `FOR SHARE`, and keeps that lock until the provider answers. A change that committed first means nothing is sent and the Requests list shows "The booking was rescheduled or cancelled, so this was not sent."; a change that arrives during the call waits for it. Retry and Post again refuse such a delivery with the same reason. A run whose own booking step moved its link keeps delivering, and a run with no booking is not affected. Known race: idempotent HTTP calls have no send lock, so a change in the moment between the check and such a send does not stop it.

Tests: `packages/db/src/bookings.test.ts` (constraint, stored results, concurrent creates, staff duplicates and races), `packages/db/src/deliveries.test.ts` "booking changes stop queued deliveries" (change before the claim, Retry and Post again, a change during the send, unaffected runs) and `apps/api/src/connections.test.ts` (the 409 reason), `packages/engine/src/definition.test.ts` (save rules) and `test-run.test.ts` (choices), `apps/worker/src/steps/index.test.ts` (field rules at booking time, test scope), `apps/worker/src/worker.test.ts` (stop at the next step, after a wait, before a retry, inside the send claim), `apps/api/src/bookings.test.ts` (no-show mark, repeat, undo, refusals; roles, isolation, cancel, reschedule, concurrency, MCP, a takeover during a booking attempt, a staff reschedule after a desk workflow, replays after later changes and after the time), the QA-02 harness cases and `e2e/bookings.spec.ts`.

## Builder (apps/web)

What it does: the console where a user signs in, creates a workflow (blank or from a starter template), builds it, test-runs it with sample data, publishes it and runs it.

How the editor works: the workflow definition is the editor's only state. Every edit (add a step, delete a step, change a field) is a pure function in `src/lib/graph.ts` that turns one draft into the next. React Flow only draws the result: `toFlow()` turns the draft into nodes and edges, and `layout()` places each step one row below its deepest parent, with each row centred. Nodes cannot be dragged and edges cannot be drawn by hand, so the picture always matches the definition. The API validates the definition on save, so the editor shows the same error messages as any other client.

- Adding a step after a step that already leads somewhere inserts the new step in between. After a condition, it fills the first free branch (`true`, then `false`), or the branch the user picks.
- Deleting a step with one parent and one child connects the two, keeping the parent's branch label.
- A new step gets an id such as `http_1`, the lowest free number for its type.

Step forms: the engine exports `stepJsonSchemas()`, which turns each step's zod config schema into JSON Schema with `z.toJSONSchema()`. `GET /step-schemas` serves them with the branch labels. `src/SchemaForm.tsx` renders a form from that schema: enums become selects, integers become number inputs, long text fields become text areas, and string maps (HTTP headers, AI labels and fields) become lists of name and value rows. Adding a field to a step's zod schema adds it to the form with no UI change. See [decision 0007](decisions/0007-builder-ui.md).

Event keys (packages/db/src/runs.ts `createKeyedRun`, decision 0029): a run with a key inserts the run and a `run_keys` row (primary key workflow, test flag, key) in one transaction. A concurrent call with the same key waits on that primary key until the first commits, then rolls back its own run and returns the first one; if the first rolled back instead, the second goes ahead. Webhooks, the console Run button, test runs and MCP tools all use it. Test runs have their own scope, so a test never swallows a real event, and the same event id in another workflow is another event. A repeated test event answers with the earlier run's own version and mode (`{ id, versionId, mode, duplicate: true }`), not the new draft's, and the builder says that nothing ran and which earlier test it is showing. MCP tools take an optional `idempotencyKey` argument (not stored in the payload); for office and purchase request tools it becomes the request's submission key, so a retried call returns the same reference. Keys are kept as long as their run.

Test runs: `POST /workflows/:id/test-runs { definition, payload, mode, choices }` saves the draft as an unpublished version (or reuses the newest version if the draft is identical, compared with sorted keys because Postgres jsonb reorders them) and starts a run with `runs.test = true`. `mode` is `mock` (the default), `ai` or `live`; the older `live: true` still means `live`. In `mock` and `ai` runs the worker fakes the steps that reach outside: the HTTP step returns `{ mocked: true, status: 200, body: null, request }` without a request, the email step returns the resolved recipient and subject without sending, approvals store no link and send nothing, Sheets, Slack, Outlook and Teams queue no delivery, and a delay or a retry waits at most one second. `ai` runs call the model; `mock` runs do not. `choices` fixes outcomes per step id: `{label}` for a classify step, `{decision: approved|rejected|timeout}` for an approval, `{fail: retryable|permanent}` for a step that reaches outside, so the failure and retry path can be seen. `choiceProblems` refuses a choice that does not fit its step, and any choice on a live run, with a 400 naming it. The run stores `ai_live` and `test_choices` (migration 0014, decision 0028); the run page labels it "test run, real AI, other calls mocked". The builder has a "Test calls" picker and a "Test outcomes" list. Templates and secret redaction still run, so the output shows what a real run would send. The console polls `GET /runs/:id` once a second and shows each step's state, branch and output.

Accessibility: every action has a button, and the side panel lists the trigger and every step as buttons, so the whole editor works from the keyboard. Canvas nodes are also focusable (Enter selects, Delete removes) and have names that say where each branch leads. Colours, type and spacing are CSS variables (the tokens in `DESIGN.md`, in `apps/web/src/styles.css`) for light and dark mode, with Geist and IBM Plex Mono served from `apps/web/public/fonts/`. The only motion is the running step's pulse and the dot moving along an edge; `prefers-reduced-motion: reduce` turns both off. A menu on the left of every page (a bar with a Menu button under 800 px) holds the links, the account and Sign out. The main text pairs (body, muted, links, buttons, node text, the success badge) were measured in the browser at 5:1 contrast or better in both modes. The side panel has a fixed width, so the canvas does not move when the panel content changes.

Tests: `src/lib/graph.test.ts` covers adding, inserting, branching, deleting and the layout. `packages/engine/src/step-schemas.test.ts` checks the JSON Schema shapes the form relies on, and `templates.test.ts` checks that the three starter templates are valid. `api.test.ts` ("builder") covers the schema and template routes, test runs, version reuse and ownership. `apps/worker/src/steps/index.test.ts` ("mock mode") proves mocked steps make no request. `e2e/main-flow.spec.ts` (Playwright) signs up, builds a condition and an HTTP step, test-runs, publishes and runs a live version, and checks the step outline from the keyboard.

Limits: the contact and client-request starters and the guided website inquiry, office request, and purchase request templates send a fixed acknowledgement (plus the opaque `{{trigger.reference}}` where tracked) to the address on the form, with none of the visitor-supplied text in either English or Tagalog (the submitted text stays in the sheet, staff notification, or approval record), and Lead to booking asks staff to approve before it books, so a public request holds no slot until a person approves it (decision 0057, M10, M17, and M2; tests in `packages/engine/src/templates.test.ts`). Starter templates are offered when creating a workflow: Inquiry triage, Invoice follow-up, Booking no-show follow-up, then ten ready-made business starters from simple to complex (Appointment reminder, Client request to Sheets, Lead to booking, Order to Sheets with payment link, Order paid, Invoice with payment link and reminders, Quote approval with deposit, Renewal reminders, Shopify or WooCommerce orders, Receipt to expense row). Receipt to expense row (`receipt-expense`) is a form with a receipt photo: Drive saves it, the AI reads shop, amount and date, the owner approves, and an approval adds a sheet row and emails the sender. It needs a shared drive folder, Sheets and a model that reads images. Renewal reminders is a form, not a schedule: no step reads a sheet, so each item is added with its expiry date, logged to the Sheet, and waits until 30 days before it. Shopify or WooCommerce orders is a webhook recipe that expects the four fields order_id, customer_name, customer_email and total; a store's raw payload has other names, so it needs a small relay or the owner maps the fields. The seed script publishes only the first three for the demo user, because the others need Sheets, Calendar or PayMongo connected before they can be turned on. Each new template has Tagalog names, labels and email texts. The invoice and quote templates use the `payment_status` step, which reads the current status of the payment a `paymongo_link` step made earlier in the same run (pending, paid, needs_review or refunded) from the stored row the PayMongo webhook updates, never calling PayMongo, so a reminder is skipped once the invoice is paid.

## Run history and versions

What it does: `#/w/<id>/runs` (called Activity in the console) lists a workflow's latest 50 runs with their plain result, kind (real run or preview) and duration, filtered to everything, real runs, previews or runs that need you. `#/runs/<id>` shows one run in plain words, and under "Details for a technician" its raw state, version, trigger data, and for every step attempt its state, branch, attempt number, duration, input and output (see Console navigation below). `#/w/<id>/versions` lists the versions, shows what each one changed against the version before it, and rolls back.

Step input: the worker resolves a step's templates once, runs the step with the result, and stores that result as `step_runs.input` after replacing secret values with `[secret]`. The page shows the address an email went to, not `{{trigger.email}}`. A failed attempt keeps its input too. See [decision 0008](decisions/0008-step-input.md).

Masking: secrets are hidden twice. The worker stores a preview built with `[secret]` in place of every secret and replaces every form of every secret value in output and error text. On the way out, `GET /runs` and `GET /runs/:id` replace every form of the workspace's current and retired secret values (`retired_secrets` keeps values that were replaced or deleted, encrypted, for this only) in trigger data, input, output and errors, so rows written before a fix or before a rotation stay hidden. The API then runs `maskSecrets()` (`apps/api/src/mask.ts`) over trigger data, input and output in `GET /runs` and `GET /runs/:id`: the value under any key that looks like a secret (`password`, `token`, `authorization`, `api_key`, `cookie` and similar) becomes `[secret]`. The second pass covers trigger data, which comes from outside and is never redacted by value.


The same read-time hider (`historyHider()` in `apps/api/src/mask.ts`) also covers the office request list, delivery activity (`GET /deliveries`) and the MCP run status, so a secret in an error written before a redaction fix, or before a rotation, shows on none of them (security review M9). Calendar errors store only Daloy's own message and the status code, never the text Google sends back.

Versions: every save or test run adds an immutable version, and publishing marks it published. The newest published version is the live one. The versions page hides draft-only versions until "Show drafts" is ticked. The diff (`jsonDiff()` in `apps/web/src/lib/diff.ts`) lists changed paths such as `steps[send].config.to`. It matches steps by id, so adding a step in the middle shows one added step and not a change to every step after it. Other arrays, such as edges, are compared by position. `GET /workflows/:id/versions/:version` returns one version's definition.

Rollback: "Roll back to v1" posts v1's definition to `POST /workflows/:id/versions` with `publish: true`. The result is a new published version, such as v3, so history is never rewritten and the run history still points at the versions that actually ran.

Review (decision 0030): a run in `needs_review` shows a panel with the step's error (status code included), the redacted request that may have gone through, and three buttons. It went through makes the step succeed with `{reconciled: "delivered"}` and the run carries on from the next step, so an approval before it is not asked again. Send again runs one more attempt with the same key, and the panel warns that a receiver without deduplication may get it twice. Stop cancels the run. A failed run shows Retry, one more attempt of its failed step. `POST /runs/:id/resolve` and `POST /runs/:id/retry` (owner and operator, 30 a minute) call `resolveRun`, one guarded UPDATE on the run, so of two people acting at once one acts and the other gets a 409 that names the state. The answered attempt shows who acted and when. The runs list has a "Needs review" filter (`review=true`) and a badge for runs whose Sheets or Slack delivery waits for review.

Edge cases: `test` accepts only `true` or `false`. A version number that is not a positive integer gets 400, and another user's workflow gets 404. A null value under a secret key stays null, so an empty field still reads as empty.

Tests: `apps/api/src/mask.test.ts` and `apps/web/src/lib/diff.test.ts` (unit). `apps/worker/src/steps/index.test.ts` checks that the stored input is resolved and redacted, on success and on failure, and `worker.test.ts` checks that the worker saves it. `api.test.ts` covers the `test` filter, masked fields, the version route with its 400 and 404 cases, and a rollback that creates a published v3. `e2e/history.spec.ts` (Playwright) runs a workflow, opens the run with a masked trigger field and its step input, changes the flow, reads the diff and rolls back. `e2e/review.spec.ts` answers a mocked run in review with It went through. The resolve and retry routes are covered by the QA-08 cases of the scenario harness.

## MCP (apps/api/src/mcp.ts)

What it does: `/mcp` is a Streamable HTTP MCP endpoint. An MCP client (Claude Desktop, an agent, a script) connects with `Authorization: Bearer <token>`, using a token from the console's API tokens page. A token has scopes and an optional expiry, see Accounts and API tokens. Each of the token owner's published workflows with a form trigger is a tool named after the workflow slug. Its input schema is the form's fields. Calling it starts a run and returns `{ runId, status: "pending" }` right away. `get_run_status { runId }` returns `{ runId, status, error, finishedAt }`, where status is the run state, or `waiting_approval` while the run waits on an approval step. `resolve_run { runId, action }` answers a run in `needs_review` with `delivered`, `again` or `stop`, or gives a failed run one more attempt with `retry`, through the same guarded `resolveRun` as the console; the answered attempt records the token owner's email with "(MCP)".

Why it's built this way: it uses the official MCP SDK v2 (`@modelcontextprotocol/server`), which is the stable line and supports both the 2026-07-28 protocol and older clients. The endpoint is stateless: every request builds a fresh MCP server with that user's tools, so nothing is stored between requests, a newly published workflow appears on the next request, and a revoked token stops working at once, and a token's scopes decide which tools that request gets. See [decision 0011](decisions/0011-mcp-sdk-v2.md).

Auth: `McpTokenGuard` hashes the bearer token with SHA-256 and runs one UPDATE that matches the hash, skips revoked and expired tokens and sets `last_used_at`. No match gives 401 with `WWW-Authenticate: Bearer`. The owner's id is passed to the tool handlers, and every query filters on it, so a token only sees its owner's workflows and runs.

Tools: `toolsFromRows()` turns each workflow row into a tool. The input schema is `fieldsSchema()`, the zod schema the hosted form uses, so a tool call and a form submission accept the same input: required fields, email format, length limits and number coercion. Only the latest published version runs, as with the form. `runStatus()` reports `waiting_approval` when the run is waiting and its last step run is a waiting step whose definition type is `approval`. A waiting delay step reports plain `waiting`.

## Google Sheets and Slack (packages/db/src/providers.ts, connections.ts, deliveries.ts, apps/api/src/connections.ts, apps/web/src/Connections.tsx)

What it does: Apps has a card for Google Sheets and one for Slack (a Connections section of Business and email before N4e). Google Sheets takes a service account key file, a sheet link and a tab name; the page shows which email to share the sheet with. Daloy reads the sheet to check access and the tab before saving, and Add a test row writes one visible row. Slack has Connect Slack when the installation has a Slack app (`SLACK_CLIENT_ID` and `SLACK_CLIENT_SECRET`): Slack's consent page, then the workspace's name on the card. The bot token from the owner's own Slack app stays available under "Advanced: use your own Slack app token", and is the only option when the installation has no Slack app. Then Pick a channel lists the public channels and warns when the app is not in the chosen one. Send a test message posts once. Each connection has Disconnect. In the office request setup, "Where requests and alerts go" offers "A row in your Google Sheet" and "A short note in your Slack channel". The row is the reference, the time, the name, email, subject and any extra fields. The note is the reference and subject only, since everyone in the channel can read it. The editor also offers both as steps ("Add to Google Sheets", "Post to Slack") for any workflow.

The steps do not call the providers. Each one stores a delivery (one per run and step) and succeeds, and the worker delivers it within a couple of seconds. The Requests list shows each delivery on its own: "Sheet row: added ('Requests'!A7:F7)", "Slack note: posted", or the reason it failed, with Retry. A Slack note that may already be in the channel shows Mark as posted and Post again.

Why this way: runs are sequential, so as ordinary steps a sheet failure would stop the Slack note and there would be no way to retry one of them. A delivery row has its own attempts, backoff and state, so Sheets and Slack fail, wait and retry independently, and retrying one never re-runs the workflow or sends a second receipt. A service account and a bot token work on any self-hosted installation without registering OAuth clients. Slack's install flow is an addition on the shared OAuth core, not a replacement ([decision 0061](decisions/0061-slack-oauth.md)): it asks for the bot scopes `chat:write` and `channels:read` only (no `chat:write.public`, no user scopes), without PKCE (Slack's support is unverified), with token rotation off, so the bot token never expires and has no refresh token. The Slack workspace's team id is the stable account: a reconnect to the same workspace keeps the chosen channel and another workspace clears it. A queued note whose workspace changed is held for review through the destination rule (R7). Disconnect deletes the row and then calls Slack's `auth.revoke`, best effort. The send code takes the bot token from either credential shape (`slackToken`). See [decision 0021](decisions/0021-sheets-slack-deliveries.md).

Edge cases:

- Expired access: a Google 401 drops the cached token and gets one new one before failing. A Google key that was deleted or disabled, or a revoked or expired Slack token, marks the connection "Needs reconnecting"; later deliveries fail at once without calling the provider, and Retry works after reconnecting.
- Permission denied: an unshared or missing sheet fails the delivery with "Share the sheet with <service account> as an Editor". A Slack app outside the channel fails with "Type /invite ...". The connection stays active, and nothing retries until someone fixes it and selects Retry.
- Quotas and outages: 429, 5xx on reads, and unreachable hosts are retried with backoff, up to 5 attempts, waiting at least as long as Slack's `Retry-After`.
- A write that timed out or broke off may have reached the provider. For Sheets a retry cannot add a second row while the delivery's marker exists: the row is written with one atomic `spreadsheets.batchUpdate` that also creates a project-private developer metadata marker whose id Daloy chose when it queued the delivery. Google refuses a second marker with the same id and applies a batch entirely or not at all, so a retry, a parallel attempt or a late copy of the first request adds nothing; a refused batch whose marker is ours counts as delivered ("already in the sheet, not written twice"), and a marker id held by anything else goes to review. A delivery with an uncertain attempt (a timeout, a 5xx on the write, or a claim taken back from a worker that died mid-call) is flagged in the same UPDATE that records it, and its marker is never deleted, so a request Google applies late is still refused. Markers of deliveries whose every attempt got a definite answer are deleted 24 hours after delivery. This makes a delivery land at most once while its marker exists. It is not unconditional exactly-once delivery (decision 0021 lists the limits). Every delivery is also pinned to the connection's account and destination when it is queued; if the owner reconnects elsewhere first, or the delivery was queued before pinning existed, it waits for review, and Post again sends it to the current connection (decision 0021). Slack cannot be checked without reading the channel, so the delivery waits for the operator; Post again asks for confirmation first.
- Every claim gets a new random `claim_id` in the same UPDATE that claims it, and a worker records its outcome (and pins the destination) only while the row is still `sending` under that same id. Attempt numbers were the guard before, but Retry and Post again start them from zero, so a worker whose claim had expired could answer for a later attempt: its late success marked a Post again to another sheet delivered while that sheet had refused the row (Astra, c05fa81). Now a late answer from a taken-over, retried or re-posted claim changes nothing. A worker that loses its claim while pinning a first destination stops before sending, so it cannot write to a sheet another worker has since replaced (Astra, 8e2c5d8).
- A connection's status follows the credential that was used: each save gives the credential a new revision (its IV), and an authentication refusal or a passing test only updates the connection while it still holds that revision. A refusal for a key the owner has since replaced leaves the new connection working. Outlook rotates its refresh token on use: the new token is saved only over the revision it was rotated from, and the send or test then carries the new revision, so its own result still lands, while a late rotation for a mailbox the owner has since reconnected changes nothing (Astra, 283fa1a).
- A worker that dies mid-call leaves the delivery "sending". Two minutes later another worker takes it and treats it as uncertain, as above.
- Double-clicking Retry queues once; another owner's delivery answers 404.
- Form text is written with `valueInputOption=RAW`, so `=IMPORTXML(...)` in a request stays text and never runs as a formula. Secrets in templates are sent as `[secret]`.
- Turning on an automation that uses Sheets or Slack is refused until the connection works and has a sheet or channel. Test runs and the preview show the row and note without queueing anything.
- Disconnect deletes the credential. Queued deliveries then fail with "not connected" and keep their content for Retry.

## Accounts and API tokens (apps/api/src/auth.ts, tokens.ts, mcp.ts, apps/web/src/Account.tsx, Tokens.tsx)

What it does: the Account page changes the password. `POST /auth/password` needs the current password and a new one of 12 to 200 characters, hashed with argon2id. It keeps the session that made the request, deletes the account's other sessions and marks every open reset link used. A wrong current password is a 400, so the console does not mistake it for a signed-out session. The route allows 10 requests a minute per user.

A signed-out user can ask for a reset link from the sign-in page. `POST /auth/password-reset` always answers 202 `{ ok: true }`, whatever the email. The account lookup and the mail run after the response, so the timing does not show whether an account exists. The link is `/#/reset-password/<token>`: 32 random bytes, only the SHA-256 stored in `password_resets`, valid for 30 minutes. `POST /auth/password-reset/:token` claims it with one guarded UPDATE, so it works once, then sets the new password, deletes every session of the account and marks the account's other open links used. Unknown, used and expired links all get the same 400. A new password that is too short is refused before the claim commits, so the link stays usable. The mail goes through the installation's SMTP server (Mailpit locally, the SMTP sink in e2e), in the workspace language from `resetSubject` and `resetBody` in `packages/engine/src/email-copy.ts`. It skips the shared-mail approval, because it is a system message to the account's own address.

API tokens now have scopes and an expiry. `read` registers `get_run_status` and `list_bookings`. `run` registers one tool per published form workflow. `manage` registers `resolve_run`, `cancel_booking` and `reschedule_booking`. No MCP tool edits workflows, so `manage` means changing runs and bookings. Tools outside a token's scopes are not registered for that request, so they are missing from `tools/list` and a call to one is an unknown tool. The expiry is optional, 1 to 365 days. The Tokens page defaults to read and run on, manage off and 90 days.

Why it's built this way: the link sits in the URL fragment, so it is not sent to the server in request lines or in a Referer header. Only a hash is stored, so a database read does not give working links. The per-IP limit (5 per 15 minutes, the existing in-memory `RateLimit`) cannot stop many addresses mailing one person, so the hourly cap of 3 links per account is counted in Postgres under a row lock on the user and holds across API processes. Scopes are enforced where tools are registered, so a handler cannot forget a check. A password change does not revoke API tokens, because tokens belong to the workspace and not to a person. The owner revokes them on the Tokens page. See [decision 0053](decisions/0053-accounts-and-token-scopes.md).

Edge cases: a request over the per-account cap gets the same 202 and no mail. If the SMTP server fails, the failure is logged and the requester sees the same answer. Sign-up emails are not verified, so a reset goes to whatever address registered. Tokens made before this phase keep full access and never expire: migration 0031 adds `scopes` with the default `{read,run,manage}` and a null `expires_at`, and the token hash is unchanged. An expired token gets 401 like a revoked one, and its `last_used_at` is not updated. This is migration 0031 and decision 0053.

## Shared OAuth core (packages/db/src/oauth/, apps/api/src/oauth.ts, apps/web/src/ConnectPanel.tsx)

What it does: an app with an OAuth client on this installation gets a Connect button named for the app (Connect Outlook) on its Apps card. It opens the provider's consent page and comes back to Apps with the app connected or a plain reason (declined, an administrator must approve, a permission was not allowed, too slow or started by someone else, failed). The card shows the account, its status and last error, Reconnect and Disconnect, and today's paste form under "Advanced: use a key or token instead". An app without a client shows only today's form. Outlook and Slack are on it so far; Google, Airtable, Notion and Trello follow in later phases of the managed OAuth plan. Slack's definition (`oauth/slack.ts`) uses the optional fields `tokenTypes` (Slack's token type is `bot`), `scopeSeparator` (a comma) and `revokeAccepted` (`auth.revoke` answers 200 with `ok: false` when it did not revoke), and has no refresh tokens, so the keepalive sweep skips it.

How it works: a provider is data (`OAuthProvider` in `oauth/core.ts`): URLs, scopes, PKCE, refresh behaviour, an identity call and a consent error mapper, listed in `OAUTH_PROVIDERS`. Start (`POST /settings/connections/<slug>/oauth/start`, owner only) stores a flow row with the SHA-256 of a random state and a random PKCE verifier, encrypted, for ten minutes. The callback (`GET /settings/connections/oauth/callback`) consumes that row with one guarded UPDATE that only the same member in the same workspace can win, exchanges the code with the verifier, refuses a grant narrower than the required scopes, reads the provider account id, and saves the connection in one transaction. The credential is a versioned JSON blob (access token, its expiry, refresh token, the previous refresh token, scopes), encrypted as before. `withFreshToken` uses the stored access token while it has two minutes left; otherwise it locks the connection row (`SELECT ... FOR UPDATE`, `lock_timeout` 15 s), reads it again, and refreshes only if no other worker already did, writing the new pair in the same transaction. Deliveries refresh before their booking-lock transaction opens. The worker refreshes idle grants (keepalive) at start and daily and deletes flow rows a day past expiry. Disconnect deletes the row, then revokes at the provider. A provider whose grant is kept elsewhere (Gmail, on `mail_senders`) gives the core a `GrantStore` that does the same on its own row. The history hider also hides the tokens of the workspace's OAuth connections. See [decision 0058](decisions/0058-oauth-core.md), which also has the steps to add a provider.

Why this way: a one-time flow row cannot be replayed and has room for a random verifier; the row lock is what keeps two workers, or a worker and a reconnect, from both spending a refresh token that the provider allows only once.

Edge cases: a replayed, expired, unknown, another member's or another workspace's state lands on `#/apps/oauth-expired` and stores nothing; a member who is no longer an owner is refused at the callback. No parameter chooses where the browser goes. A refused grant marks the connection failed for the credential it read, never for one saved after it; 429, 5xx and timeouts leave the row unchanged. A crash after the provider answered loses the new pair; a strictly rotating provider then refuses the old one and the owner reconnects. A revoke that fails still disconnects, and the page says to remove Daloy at the provider. Outlook rows from before keep working: their bare refresh token becomes a blob on its first refresh. `OAUTH_ENV` must match `PUBLIC_URL` (development only on a local address) once a managed client is set, or the API and worker refuse to start.

## Google Calendar (packages/db/src/calendar.ts, providers.ts, deliveries.ts, bookings.ts, apps/api/src/connections.ts)

What it does: Apps has a Google Calendar card. The main action is Connect with Google (decision 0064): Daloy creates its own "Daloy bookings" calendar and uses only that, so nothing is picked or typed. A service account key and a calendar id, with the calendar shared with that account, stay under Advanced and are the whole card when the installation has no Google client. The `calendar` step, placed after a booking step, puts the booking on the calendar. After that the event follows the booking: staff or a step move it and the event moves, a cancel deletes it.

How it works (decision 0044): the step records the event's title in `calendar_events` and queues a delivery. The event id is derived from the booking id, and Google refuses a second insert of the same id, so a retry cannot make a second event. Every delivery makes the calendar match the booking as it is when it is sent: insert, or patch after a 409, or delete if cancelled (404 and 410 count as done). `bookFromStep` and `staffChange` queue one such delivery per new booking version, in the same transaction, so a cancel (which has no run) still removes the event. The booking-moved stop of decision 0032 is skipped for these deliveries. Times go out in UTC with the booking's own zone. Reminders already stop for a changed booking, so a cancelled booking sends none.


The event stays where it was written (security review M11): `calendar_events` records the account and calendar of the last successful write, and every later sync of that booking is pinned there, not to the connection as it is now. If the owner has since switched Apps to another calendar, the sync stops in review and says the event is still in the old calendar; Post again is the explicit choice to write the change to the new one, which then becomes the event's calendar. Writes for one booking happen in order (M12): a sync reads the booking under a share lock held until Google answers, so a cancel or reschedule waits for an older write to finish, and the sync it queues then makes the event match the booking. A write whose answer was lost is sent again and reads the booking again.

Connect with Google (decision 0064): the grant asks for `openid email` and `calendar.app.created` only, so Daloy reaches calendars it created and nothing else of the owner's. After a successful consent the shared callback runs `ensureCalendar`, which creates the calendar with `calendars.insert` and saves its id as the destination. A reconnect with the same Google account keeps the destination, so the calendar is made once; another Google account clears it and gets a new one, and the old calendar keeps its events. If Google refuses the creation the connection stays and the card shows Create the Daloy bookings calendar (`POST /settings/connections/google-calendar/create`; `{ "again": true }` replaces a calendar deleted by hand). `calendarInfo`, `calendarWriteTest` and `syncCalendarEvent` take a service account or an access token, `withGoogle` chooses by the connection's `auth_method`, and the worker refreshes the token before the booking-lock transaction opens. With a Google sign-in, a delivery compares only the calendar id: the same calendar after re-authorization sends without review, a different calendar goes to review as before (M11). A service account still compares the account. Using an existing calendar of the owner's through a Google sign-in is not built (its scope class is unverified); use the service account form for that.

Edge cases: an unknown outcome is sent again, never held for review, because every call is repeatable. A calendar not shared with the service account fails with the address to share it with. No attendees: a service account cannot invite people.

Tests: `packages/db/src/calendar-oauth.test.ts` (consent, the calendar made once, create, move and cancel through the token, M11, pinning across re-authorization, no token in rows), `apps/api/src/google-calendar-oauth.test.ts` (callback, create route, roles, logs, disconnect), `apps/web/src/lib/google-calendar.test.ts`, `e2e/google-calendar.spec.ts`, and for the service account `packages/db/src/calendar.test.ts` (id, create once, lost answer, reschedule, cancel, unshared), `apps/worker/src/steps/deliveries.test.ts` (the step through the worker, staff cancel), `apps/api/src/connections.test.ts`, `e2e/calendar.spec.ts`. ## Run animation (apps/web/src/lib/run-flow.ts, FlowCanvas.tsx, Editor.tsx, Runs.tsx)

What it does: the diagram shows how far a run has got (N4c). After "Test run draft" in the editor, and on a run page under "Path it took", each node says Done, Working, Waiting, Needs you, Problem or Not reached, and each edge shows whether the run went that way. Done is green, Problem is red, Waiting and Needs you are amber. While work moves into a step, a small dot travels along the edge into it and the step pulses. The run page draws the version the run used, read only, and hides the diagram under 600 px (the steps are still listed under "Details for a technician").

How it works: `runFlow(draft, run)` is a pure function from a definition and a run's step rows to a state for every node and edge, so the editor and the run page draw the same picture. Each step takes its newest attempt, so a retry that succeeded shows Done. `succeeded` is Done, `failed` is Problem, `waiting` is Waiting, `running` and `pending` are Working, and a step with no row (or a skipped one) is Not reached. A run in review marks its last unfinished step Needs you. An edge is taken when its source is Done and the source's branch matches the edge's label (a condition's `true` or `false`); the other branch is drawn dashed. A taken edge flows while the run is pending, queued or running and its target is Working or has no row yet; an edge into a failed or waiting step is solid green, not moving. Nothing flows once a run is finished or waiting. The data comes from the polling that `useRun` already does (`pollDelay`), the definition from `GET /workflows/:id/versions/:version`, so there is no new endpoint. `toFlow()` takes the optional state, adds it to the node data, gives edges the `run` type and adds the state to each node's accessible name.

Edge cases: colour is never the only signal. Every node prints the state in words with a symbol, edges differ by line style (solid, dashed, dotted), and screen readers hear the state in the node name. Under `prefers-reduced-motion: reduce` the dot is not drawn (SVG `animateMotion` ignores CSS media queries, so the edge reads the preference itself through `matchMedia`) and the pulse is not applied (it sits inside `prefers-reduced-motion: no-preference`). Motion is linear and ease-in-out, with no bounce. A draft edited after a run is still coloured by step id; ids the draft no longer has are ignored, so the picture can be stale until the next run. The state colours reuse the existing tokens, and a test checks them against WCAG AA in both colour schemes.

Tests: `apps/web/src/lib/run-flow.test.ts` (every node and edge rule, retries, branches, review, finished runs, unknown ids, the words for each state, and the contrast of text at 4.5:1 and lines at 3:1 in light and dark mode read from `styles.css`), and `e2e/run-animation.spec.ts` (the editor and the run page show the trigger and first edge Done while the last step still waits, a failed step shows Problem, and a faked in-flight poll shows the moving dot and pulse, and neither under reduced motion).

## Schedule watchdog (apps/worker/src/watchdog.ts, packages/engine/src/email-copy.ts, apps/web/src/lib/automations.ts)

What it does: tells the owner when a scheduled automation did not run when it was due, so a stopped worker or a lost job does not go unnoticed. See [decision 0050](decisions/0050-schedule-watchdog.md).

How: every minute the worker looks at each live automation whose trigger is a schedule. It works out the latest cron time that is at least 15 minutes old and checks that a real run started by a schedule fire (trigger payload has `firedAt`) was created since. If not, it sets `workflows.schedule_missed_at`, which the Automations page shows as "Missed its schedule" and counts under Problem, and it emails the owner once.

Why it is built that way: it reads the database, not pg-boss, so a lost schedule row is caught too. Manual runs do not count as the fire, so they cannot hide a broken schedule. It only reports and never replays, because a replay could send the same email twice.

Edge cases: a version published after the due time is not blamed for it. Turning the automation off clears the flag. The flag clears once a fire is covered, and the owner gets at most one email per automation per 24 hours even if the flag clears and returns, because `schedule_alert_at` stays. Two workers checking at once send one email (a conditional UPDATE claims it), and a failed send gives the claim back so the next check retries. The email is in the workspace language.

Tests: `apps/worker/src/watchdog.test.ts` (grace, manual runs, one email, a day later, clearing, Tagalog, retry, two workers), `apps/worker/src/worker.test.ts` (a running worker flags a stopped schedule once and clears it after a fired run), `apps/web/src/lib/automations.test.ts` (ordering and the Problem filter).

## Form files and Google Drive (packages/engine/src/file-type.ts, packages/db/src/uploads.ts, providers.ts, deliveries.ts, apps/api/src/public.ts, runs.ts)

What it does: a form can have file fields. A visitor attaches photos or PDFs, and a `drive` step saves them into one Google Drive folder chosen in Apps. The owner and operators can also download each file from the run's details for 7 days.

How it works (decision 0051):

- Limits: 5 MB per file, 3 files per field, 5 files per submission. The type comes from the file's first bytes (JPEG, PNG, WebP, HEIC or HEIF, PDF). The browser's type and the file name's extension are ignored, so SVG, HTML and anything else are refused even when renamed `.jpg`.
- The per-IP limit of 10 posts a minute is a guard, and Nest runs guards before the upload parser, so a blocked address never gets its body read. Next to it, `UploadBudget` checks the form and the declared `Content-Length` before the parser reads anything, and reserves those bytes from a shared 128 MB budget until the response closes (decision 0078). Full budget: 503 with `Retry-After: 5`. No length: 411. More than one submission can hold: 413. A form with no file field: 415.
- The files are stored in Postgres (`uploads`) in the same transaction as the run. An invalid post stores nothing, and a replayed submission key stores no second copy. The worker's sweep deletes files 7 days after upload.
- The run's trigger data holds only references (`id`, `name`, `type`, `size`) under each file field. File contents never enter trigger data, step input or output, so templates, failure explanations and Ask cannot read them. The AI step reads a file only when the owner lists its field in the step's `files` (decision 0052, see the AI step). Only the form handler sets a file field: a value sent through a webhook, MCP, a test run or the Run button is dropped.
- Each workspace may store a number of files per Manila day: Pilot 100, Business 500, Business Plus 2000, and 20 without a plan. Over the limit, a submission with files gets a plain refusal. One without files goes through. On a tracked form the allowance is claimed in the transaction that creates the request, its run and its files. A repeat with the same submission key returns the first reference before any claim, and a duplicate that loses the unique index rolls its claim back (decision 0057, M15; test in `apps/api/src/public-intake.test.ts`). Preview workspaces get 20.
- The Drive step queues one delivery like Sheets: the folder is pinned when it is queued, and each saved file is recorded under the worker's claim, so a retry skips files already saved. Drive cannot be asked whether an upload landed, so an unknown outcome waits in `needs_review` for Mark as posted or Post again. Post again also skips files already recorded.
- Downloads are always attachments, with the stored type, `nosniff`, a sandbox CSP and no caching.

Edge cases: a service account has no Drive storage of its own, so Connect refuses a folder outside a shared drive and says how to fix it. A file removed after 7 days fails its delivery with that reason. A run with no files completes the step and queues nothing. Files above 5 MB would need Google's two-step upload, which is not built.

Tests: `packages/engine/src/file-type.test.ts`, `packages/engine/src/payload.test.ts` (file fields), `packages/db/src/uploads.test.ts`, `packages/db/src/usage.test.ts` (upload quota), `packages/db/src/drive.test.ts` (connect check, saves, progress, needs_review, Post again, shared drive refusal, purged file), `apps/worker/src/steps/index.test.ts` (drive step), `apps/worker/src/steps/ai.test.ts` (a file the step does not list never reaches the model), `apps/api/src/form-files.test.ts` (limits, types, replay, quota, download headers and roles, Drive connect), `e2e/form-files.spec.ts`. ## Reliability tests (apps/worker/reliability)

What it does: two scripts start an embedded Postgres, a test receiver and real worker processes. The load test (`pnpm reliability:load`) also starts the API and has k6 send 1,000 webhook calls. The chaos test (`pnpm reliability:chaos`) creates 200 runs and kills the worker with SIGKILL ten times while it works, starting a new one after each kill. Both use a five-step workflow: HTTP call, condition, HTTP call, one-second delay, HTTP call. The HTTP steps are POSTs marked `idempotent: true`, because the receiver deduplicates by key; without the flag a kill mid-POST would park the run for review (decision 0030). Results are in [reliability.md](reliability.md).

Why this way: the checks look at the database and the receiver, not at log output. Every run must succeed. Every run and step pair must have exactly one succeeded attempt. The set of idempotency keys the receiver executed must equal the set of `runId:stepId` keys of succeeded HTTP steps (one key per step since decision 0030, so a redelivery repeats a key instead of adding one), so a lost step, a doubled step or a side effect from an attempt the engine does not count all fail the test. The receiver honours Idempotency-Key like a real payment API: a repeated key gets the stored reply, and the report counts those redeliveries separately (decision 0012).

Edge cases: the worker scripts use a copy of the production worker whose SSRF guard allows the receiver's loopback port; nothing else differs. k6 sends from 40 loopback addresses so the real webhook rate limit (60 a minute per IP) stays on. The scripts only kill processes they started, by PID.

### Webhook signatures

The caller sends two headers. `X-Daloy-Timestamp` is the time in unix seconds. `X-Daloy-Signature` is `sha256=` and the hex HMAC-SHA256, with the signing secret as the key, of the timestamp, a dot and the exact request body:

```js
const t = Math.floor(Date.now() / 1000);
const body = JSON.stringify({ order: 42 });
const signature = "sha256=" + createHmac("sha256", secret).update(`${t}.${body}`).digest("hex");
await fetch(url, { method: "POST", headers: { "Content-Type": "application/json", "X-Daloy-Timestamp": String(t), "X-Daloy-Signature": signature }, body });
```

```bash
t=$(date +%s); body='{"order":42}'
sig=$(printf '%s.%s' "$t" "$body" | openssl dgst -sha256 -hmac "$SECRET" -hex | sed 's/^.* //')
curl -X POST "$URL" -H "Content-Type: application/json" -H "X-Daloy-Timestamp: $t" -H "X-Daloy-Signature: sha256=$sig" -d "$body"
```

Calls more than 300 seconds from the server clock, either way, get 401 with a message that names the window. A captured call cannot be replayed later. Inside the window an identical call (same timestamp and body) returns the first run with `duplicate: true` and starts nothing, unless the caller sends an `Idempotency-Key` or the trigger has an `eventKey`, which then decide. Two different events sent in the same second with identical bodies would be seen as one, so put an id in the body.

For callers written before this: a call with no `X-Daloy-Timestamp` and the old signature (HMAC of the body alone) is still accepted until the owner ticks "Require the timestamp" on the webhook trigger. Each such call answers with `Daloy-Signature-Warning: timestamp-missing` and the editor shows the date of the last one. A call that has the timestamp header is never read as the old format. The box is ticked by default when a signing secret is first added.

Tests: `apps/api/src/public.test.ts` (the check: window to the second, timestamp not covered, old format), `apps/api/src/api.test.ts` (through the route: replay, Idempotency-Key, the warning header and the recorded date, required).

### Pause

What the owner sees: a Pause button on an automation's card. A paused automation shows "Paused" and starts no new run from a webhook, a form, an email, a schedule, a PayMongo event, MCP, the Run button or a staff reschedule. Runs already started finish. Resume starts everything again.

How: `workflows.paused_at`. `assertNotPaused` runs in the transaction that inserts a run and reads the workflow row under a share lock, so a pause waits for runs being created and none starts after it commits. A webhook, the Run button and MCP get 409 with a plain message. A public form shows "This form is paused". A PayMongo event gets a 2xx and no run, so PayMongo does not disable the webhook. A schedule fire is skipped and logged. Email-in skips the message but moves its checkpoint, so a resume does not replay a burst. Builder test runs are not blocked.

The schedule watchdog leaves paused automations out and clears an old flag. After a resume it only expects fires after `resumed_at`, so the fires the pause skipped are not reported as missed.

### Cancel a pending run

What the owner sees: "Cancel run" on a run that is pending or waiting on a delay or an approval, with a confirmation. It stops before its next step. Anything already sent stays sent. A run that is running right now cannot be cancelled (it stops at its next wait), and a run in review has Stop.

## Managed OAuth across all apps (integration of plan phases P1 to P7)

What it does: nine apps share the OAuth core above. `OAUTH_PROVIDERS` in `packages/db/src/oauth/index.ts` lists Outlook, Google Sheets, Google Drive, Gmail, Google Calendar, Slack, Airtable, Notion and Trello. ## Retired secret purge and read-side redaction (decision 0067)

What it does: every API and MCP read surface that returns stored history, request text, approval messages, or provider and mailbox errors applies `historyHider` (`apps/api/src/mask.ts`), covering `GET /runs`, `GET /runs/:id`, `GET /runs/export.csv`, `GET /workflows/:id/requests` (including `subject` and delivery `reference`), `GET /my/requests` (`subject`), `GET /deliveries` (`reference`, `lastError`, `result`), `GET /approvals/:token` (`input.message`), `GET /settings/connections` (`lastError`), `POST /settings/connections/:provider/test` (live error), `/workflows/:id/email-source` (`lastError`), `GET /settings/email` and `POST /settings/email/test` (`lastError` and live error), OAuth picker/calendar `ProviderError` responses, and MCP `get_run_status`. Each endpoint loads `historyHider` before querying history rows so a concurrent purge cannot commit between reading stored rows and reading `retired_secrets`.

Purge policy: `purgeRetiredSecrets` (`packages/db/src/retired-secrets.ts`) runs on the worker's daily maintenance sweep at startup and every 24 hours (`apps/worker/src/worker.ts`). Retention defaults to 90 days (`DEFAULT_RETIRED_SECRET_MAX_AGE_DAYS = 90`) and can be set to another positive integer with `RETIRED_SECRETS_MAX_AGE_DAYS`. For each workspace with rows at or past the cutoff, one transaction guarded by `pg_advisory_xact_lock` checks for any in-flight `runs` (`state = 'running'`) or `deliveries` (`state = 'sending'`) and skips the workspace until the next sweep if any are active, decrypts each expired row safely (skipping undecryptable rows without deleting them), scans `runs`, `step_runs`, `deliveries`, `requests`, `email_sources`, `calendar_events`, and `payments` in bounded keyset batches (`DEFAULT_RETIRED_SECRET_BATCH_SIZE = 200`, configurable via `batchSize`, alongside `connections` and `mail_senders`), locks each matching row with `FOR UPDATE`, re-computes scrubbing of all four encoded forms (`secretForms`) on the locked row, updates only the specific columns that changed, re-checks for in-flight work, and deletes only the exact captured expired ids. Newer retired copies for the same secret name and other workspaces stay untouched, and any mid-transaction failure rolls back so no retired secret is deleted before its history is scrubbed.

Tests: `packages/db/src/retired-secrets.test.ts` (env parsing, 90-day boundary, all four encodings across all scrubbed tables, workspace isolation, newer retired copy preserved, undecryptable row skipped safely, atomic rollback via a real Postgres trigger, keyset pagination across bounded batches, `FOR UPDATE` locking and column-only updates, and skipping workspaces with active runs or deliveries until they finish), `apps/api/src/secrets-history.test.ts` (all read surfaces before and after rotation, deletion, and purge), and `apps/worker/src/worker.test.ts` (daily sweep runs on startup even when deliveries are omitted).

### Steps editor (A7, `#/w/<id>`, `Editor.tsx`, `FlowCanvas.tsx`, `lib/editor.ts`, `editor.css`)

What it does: the editor opens the newest saved version of an automation (published or draft) and lets the owner change the trigger and the steps, then Test run, Save or Publish from the header. The header shows the name, a Draft or Live chip and a status line ("Unsaved changes", "Version 3 (live)", "Version 4, draft"). Below it, a banner counts the apps the steps still need ("0 of 1 apps connected") with a link to Apps. The canvas shows the steps as numbered cards joined by square edges, with the branch name (approved, rejected, true, false and so on) as a coloured pill on each edge, and a zoom bar. A Diagram and List switch chooses the view. The panel beside it holds the trigger or step form, the data references the step can use (each copies to the clipboard), "What happens next" for the selected step, the "Check before publishing" advice, Add step, an Ask AI box that proposes a changed draft (applying it also refreshes the sample payload), and the test run controls.

Why it is built that way: the diagram is for seeing the shape, the list is for doing the work. React Flow nodes are not draggable or connectable, because the graph is always the one `lib/graph.ts` derives from the saved steps, so a drag could never change anything. Every edit goes through `addStep` and `removeStep` in `lib/graph.ts`, which keep the edges consistent, and the editor only holds the resulting draft in state until Save posts it as a new version. The list view is the keyboard and screen reader route to every step, and it is the first view on a phone, since a whole diagram fitted to 360px is too small to read. `lib/editor.ts` holds the three rules that are not drawing: `nextPaths` (what follows a step, branch by branch), `insertables` (which `{{trigger.x}}` and `{{steps.id.output}}` references a step may use) and `setupLeft` (which apps the draft needs and whether each is connected). They are unit tested apart from the page.

Edge cases:
- `nextPaths` stops at a step it has already listed, so a loop or a join cannot repeat forever, and returns no path at the end of a flow. The trigger's path starts at the entry step.
- `insertables` offers only steps that run before the selected one, found by walking the edges backwards. A step on another branch is not offered, because it may never have run. An email trigger offers from, subject and text, a form or webhook trigger offers its declared fields, a manual trigger offers none. An AI step offers one reference per key of its output.
- `setupLeft` lists each app once, in step order, even when several steps use it (PayMongo serves both payment steps). Only connections with status active count as connected. When the connection list cannot be read, the banner is hidden and no card is marked, because a guess would be wrong more often than silence. A step whose app is missing shows "Not connected" on its card.
- Changing the trigger type refreshes the sample payload, so a test run of a new form trigger does not fail on fields the old sample lacked. File fields are left out of the sample, because a test run takes no files.
- Save, Test run and Publish are off while the draft has no steps or a request is running. Publish asks for confirmation, since it replaces the live version at once, and the server still checks connections, approvers and signing secrets when it publishes.
- The advice checks (`lintDefinition`) run only when the draft already parses. A draft that does not parse yet is a work in progress and gets no warnings (decision 0033). They never block saving.
- Delete on a selected card removes the step through `removeStep`. The trigger card cannot be deleted.
- Reduced motion: scrolling to the run result and the edge animation use no motion when the visitor asked for less.
- A failed save, test run or publish shows "Save failed: <reason>" in the status line and leaves the draft as it was.

Tests: `apps/web/src/lib/editor.test.ts` (branch paths, loops, references by trigger type and branch, apps needed and connected), `e2e/editor.spec.ts` (create, change the trigger, add approval steps on two branches, the missing Sheets banner, copy a reference, four diagram nodes, zoom, mocked test run, save, publish after dropping the sheet). `Editor.tsx` itself has no component test, so the form fields are covered by the e2e flow only.

#### Test one step (T1, decision 0110)

## Facebook Messenger and Instagram DM intake and replies (N16, decision 0075)

What it does: owners connect a Facebook Page and optional Instagram Business Account in Apps (`PUT /settings/connections/meta-messenger`, `POST /settings/connections/meta-messenger/test`, `DELETE /settings/connections/meta-messenger`). Daloy generates one random 32-byte `webhookPath` per workspace and keeps it across credential updates. Incoming DMs arrive at `POST /hooks/meta/:path` (verified by `GET /hooks/meta/:path` for Meta's `hub.challenge`), start matching published `meta_dm` workflows, and can reply within Meta's 24-hour messaging window using the `meta_reply` step.

How it works:

- Webhook verification and parsing (`apps/api/src/public.ts`, `packages/db/src/meta.ts`): `GET /hooks/meta/:path` checks `hub.mode === "subscribe"` and constant-time compares `hub.verify_token`, returning `hub.challenge` as `text/plain` (403 otherwise). `POST /hooks/meta/:path` checks `X-Hub-Signature-256` against `req.rawBody` using HMAC-SHA256 with the workspace's decrypted `appSecret` and `timingSafeEqual`. It parses `object === "page"` (Messenger) and `object === "instagram"` (Instagram) events matching the connected `pageId` or `instagramAccountId`, hands echoes (`is_echo === true`) to the conversation (see Conversation state below), ignores delivery or read receipts, and deduplicates per `(workflowId, false, "meta:" + mid)` in `run_keys`.
- Receipt image downloads and duplicate reference flagging: up to 3 image attachments per message are downloaded over HTTPS port 443 only from allowlisted Meta CDN hosts (`*.fbcdn.net`, `lookaside.fbsbx.com`, `*.cdninstagram.com`, overridable only via `ProviderUrls.metaCdn` in tests) with IP-pinned DNS SSRF checks, no redirects, a 5 MB streaming cap, a 10-second timeout, and magic-byte verification for JPEG, PNG, and WebP. Verified images count against the workspace's daily `upload` quota and are stored in `uploads` in the run's transaction while `triggerPayload.image` stores only `{ id, name, type, size }` references. When an AI extract step reads attached files and returns a `reference` on a live run, `checkReceiptReference` records the normalized reference in `receipt_references` per workspace and flags repeats across distinct runs without flagging retries of the same run or test runs.
- Replies and 24-hour window (`packages/db/src/deliveries.ts`, `apps/worker/src/steps/index.ts`): `meta_reply` steps mock cleanly in test runs and queue `meta_messenger` deliveries in live runs. The worker posts to Meta Graph API `/v21.0/me/messages` with `messaging_type: "RESPONSE"` and `redirect: "error"`. Error code 10 with subcode 2018278 (outside the 24-hour window) fails cleanly as non-retryable without failing the connection; 401, 403, or code 190 marks the connection failed fenced by credential IV; 429 backs off honouring `Retry-After`; timeouts and 5xx answers park in `needs_review`.
- Starter template (`meta-receipt-intake`): extracts receipt fields with vision, saves the photo to Google Drive, checks `is_receipt === "yes"`, logs a Google Sheets row marked "Pending verification" (never "Paid"), and sends an owner approval before any `meta_reply` runs.

Tests: `packages/engine/src/definition.test.ts`, `packages/engine/src/templates.test.ts`, `packages/db/src/meta.test.ts`, `apps/api/src/meta.test.ts`, and `apps/api/src/members.test.ts`. Live checks against Meta remain with the owner in [docs/live-meta-check.md](live-meta-check.md).

The receipt shows the reference in a card with a "Received" label, and a repeated send of a tracked form (same submission key) shows the first reference. A paused form says so and stores nothing. ### Booking form (E9, `slots.ts`, decision 0080)

Proven by `slots.test.ts` (grid, overlap, past slots, zones), `public-form-pages.test.ts` (endpoint scope, notice) and `e2e/booking-public.spec.ts` (two visitors, one real booking made by the worker).

GET shows the request and records nothing; the decision is a POST, as before. The decision, sign-in, not-yours and answer-recorded pages carry the brand of the approval's own workspace. Proven by `approvals-brand.test.ts`, `approvals.test.ts`, `approvals-named.test.ts`, `e2e/approval.spec.ts` and `e2e/team.spec.ts`.

The demo has its own scoped stylesheet and the console's real flow diagram and checker. A step that waits for the visitor shows "Needs you". ## First-time onboarding (R1, decisions 0082 to 0084)

What it does: a new owner answers three questions on three screens (the name customers see with an optional website and logo, the kind of business with up to three related ones, then the first workflow and how customers pay) and ends with one editable draft and a sample order. Nothing is connected, published, sent or invited by this flow. Each of those is its own action later.

Why it is built this way: the name, website and logo are the workspace's existing business profile and brand kit, so Business settings and onboarding never disagree and existing owners' settings are untouched. ## Disable a step (U3, decision 0097)

What it does. A step's right-click menu (or Shift+F10 on the focused node) has Disable, and Enable once it is off. A turned-off step stays in the flow with `disabled: true`, drawn grey and dashed with "Turned off" in words. A run, test or live, does not call it: the worker writes a `skipped` step row with the reason "This step is turned off in the editor." and goes on along the step's one edge. The run result and run history list the step as skipped, and the diagram shows it as Skipped with the line after it still taken.

Why it is built this way. The flag lives in the step definition, so it is saved and versioned like any other edit and a published version keeps it. Skipping happens in `advance.ts` before the attempt is created, so nothing is sent, no claim or lease is taken for it and no retry applies. `disabled` accepts only `true`, so an enabled step carries no key and older drafts are unchanged. The worker and the engine ship together: an older worker would ignore the flag and run the step.

Edge cases. A branching step (condition, approval, booking, payment expiry) cannot be turned off: the definition check refuses it and the menu leaves Disable out, because a skipped step has no branch to follow. A delay with a "late" edge follows its usual edge when skipped. A turned-off first or last step is skipped like any other; a flow of only turned-off steps succeeds with nothing sent. A later step that reads `{{steps.<id>.output}}` of a turned-off step gets nothing, as it would for a step on a branch not taken. Duplicate copies the flag; Copy and paste carry only the type and config, so a pasted step is on.

Tests. `packages/engine/src/definition.test.ts` (the flag is kept, refused on a branching step, only `true` accepted), `apps/worker/src/worker.test.ts` (a turned-off middle step is skipped and the next runs; a test run skips a turned-off first and last step), `apps/web/src/lib/graph.test.ts` (`setDisabled` on and off, a branching step stays on), `apps/web/src/lib/run-flow.test.ts` (a skipped row draws as Skipped and the flow carries through), `e2e/disable-step.spec.ts` (no Disable on a condition, the greyed node, kept after Save and reload, Skipped in the mocked test, Enable).

## Both payment paths (R3, decisions 0088 to 0091)

What it does: a workflow asks a customer for a deposit, a full payment or a balance with the `payment_due` step. The customer pays the seller's QR Ph code or GCash number and sends the transfer reference on a private pay page, or pays a PayMongo checkout. Staff see one Receipts to review list. Unpaid orders get a reminder and, after a deadline, are cancelled with the booking slot released.

How it works:

- Dues (`packages/db/src/payment-review.ts`, migration 0043): a due is what is owed on one order or booking, in integer centavos. It moves pending to confirmed to refunded, or pending to cancelled, never back. Every change locks the due row first and writes a line to `payment_history` in the same transaction, which is the history the booking card shows.
- Manual path (`apps/api/src/payments.ts`): `/pay/<token>` shows the amount, the order, the seller's number, name and QR image and the form. A submission becomes a claim with flags (reference used before, amount differs, upload not readable, already confirmed, paid after the deadline). It never confirms. The reviewer confirms, rejects with a reason or asks the customer a question, and the customer gets the reason by SMS or Messenger. Each decision sends the claim version it showed, so a second reviewer gets a 409.
- Pay page limits (review of 22 November, decision 0102): the post shares the forms' multipart byte budget and refuses an unknown link before reading the body. One order can have at most 5 references waiting for the seller. The upload allowance is spent inside the claim transaction after the repeat check, so a repeated reference or a file that is not an image costs nothing.
- Who sets the price: a `payment_due` amount or total can read `{{trigger.*}}` only from a manual, schedule, payment or signed webhook trigger. On a public form, an unsigned webhook, inbound email or a direct message it must be a fixed amount, or the visitor would choose what counts as paid. Take prices from the owner's own data; a price read by an AI step from a customer's message is not checked.
- Automatic path (`settleCheckout`, called from the PayMongo webhook in `apps/api/src/public.ts`): after the signature and mode checks of decision 0045, the due is confirmed only when the payment is paid and its amount, currency and order reference equal the due's. Anything else (a wrong amount, a payment after the deadline, a second payment) becomes a checkout claim in the same list. A failed attempt changes nothing, since the checkout stays payable.
- One confirmation: the reply is a delivery keyed `<due step>#confirmed` per run, queued by the pending to confirmed update alone. Whichever path confirms first sends it. A transfer receipt still open when the checkout confirms is flagged "Already confirmed" and cannot confirm again.
- Payment and reply apart: the list shows "Payment confirmed, Reply failed" when the reply delivery failed. Retry reply re-queues that delivery only.
- Nudges and deadline (`apps/worker/src/steps/index.ts`): ordinary steps the seller edits. `payment_status` reads the due, a condition checks `pending`, an SMS reminds. `payment_expire` expires the PayMongo checkout through its Expire API, cancels the due and releases the booking with the booking step code. If PayMongo says a payment is in progress, it keeps the order (`kept` branch).
- Deposits and pay later: a deposit with a total shows the rest as the balance outstanding on the booking. A pay-later booking asks for a balance and has no deadline, so it stays active.
- Templates: `booking-deposit-review` and `order-gcash-checkout` in `packages/engine/src/templates.ts`.

Edge cases: two reviewers at once, duplicate receipts, duplicate and out-of-order webhooks, wrong amounts, a payment after the deadline, a checkout paid after a manual confirmation, a refund after confirmation, a checkout mid-payment at the deadline, a failed reply.

Tests: `packages/db/src/payment-review.test.ts` (every transition and exception), `apps/worker/src/steps/payments.test.ts` (the steps against a fake PayMongo), `apps/api/src/payments.test.ts` (pay page, rate limit, who may review, decisions, webhook), `packages/engine/src/templates.test.ts`, and `e2e/payments.spec.ts` (the D-1042 pilot: a receipt in review, a verified checkout confirming it, one SMS, the booking history, a pay-later booking). The limits above: `apps/api/src/payments.test.ts` (one upload for a repeat, the cap of 5), `apps/api/src/upload-budget.test.ts` (the pay page and the shared budget), `packages/engine/src/definition.test.ts` (payment_due amount).


## Daily tools: morning digest, payments CSV, Taglish and photo compression (R5, decision 0093)

What it does: the owner can get one email each morning listing receipts to review, unpaid orders and failed customer replies. Staff download a CSV of confirmed payments for a date range. A seller can start a template with Taglish wording. A photo chosen on the pay page or a public form is shrunk on the phone before it uploads.

How it works:

- Digest (`apps/worker/src/digest.ts`, `packages/db/src/digest.ts`, `packages/engine/src/digest.ts`, migration 0044): the worker's minute tick looks for owners with `digest_enabled` whose `digest_sent_on` is before today in Manila. Between 8 am and noon Manila it claims the day with a conditional UPDATE, counts the workspace's real receipts, pending dues and failed SMS or Messenger replies, and emails the owner's login address through the installation's server. With nothing to do it sends nothing and still uses up the day. A failed send gives the day back. The owner switches it on under Receipts to review (`GET` and `PUT /settings/digest`). It is off until then.
- Payments CSV (`GET /payments/export.csv`, `apps/api/src/payments.ts`): owners and operators, a Manila day range of at most a year, one row per confirmed or refunded due of real runs, through the N19 `toCsv` so formula cells are quoted. Amounts come from integer centavos.
- Taglish (`packages/engine/src/taglish.ts`, `templatesForLanguage(language, "taglish")`): replaces the customer messages of six templates and nothing else, so the workflow runs the same. The New automation page has a Wording choice.
- Photo compression (`apps/api/src/compress.ts`, served at `/public/compress.js`): on choosing a JPEG, PNG or WebP it scales to at most 2000 px on the longest side, encodes JPEG at quality 0.8, and keeps the original when it cannot decode, when the result is not smaller, or when the file is 300 KB or less and already fits. The server still checks the type from the bytes and the 5 MB limit.

Edge cases: a worker down at 8 (sends until noon, not later), two workers (one email), a failed send (retried next minute), test runs and other workspaces (never counted), a formula in a reference (quoted), a range over a year or backwards (400), a browser that cannot decode a photo (original uploaded), a visitor with no script (original uploaded, same server checks).

Tests: `apps/worker/src/digest.test.ts` (timing, once a day, empty mornings, opt-in, counts, failure, Tagalog, no customer detail), `packages/engine/src/digest.test.ts`, `packages/engine/src/taglish.test.ts`, `apps/api/src/csv-export.test.ts` (columns, range, escaping, roles), `apps/api/src/compress.test.ts` (the limits, with a faked browser), `apps/api/src/payments.test.ts` and `form-files.test.ts` (the script is loaded and the server still refuses bad bytes and big files), `apps/api/src/members.test.ts` (roles), and `e2e/photo-compression.spec.ts` (a real browser resizes a 3000 x 2000 photo to 2000 x 1333).


## Customer privacy: notice, receipt retention, export and delete (R6, decision 0094)

What it does: every public form and the pay page show a short line under the send button saying who gets the answers, what they are used for, and that the customer can ask the business to show or delete them. The owner can export everything the workspace holds about one customer, or erase it, from the Customer data section on the Receipts page. Receipt images are removed a set number of days after an order closes.

How it works:

- Finding a customer (`packages/db/src/privacy.ts`, `matcher`): the owner enters an email or a phone number. A run matches when any string inside its trigger payload holds the whole email (case-insensitive, not as part of a longer address) or a run of digits that reads as the same Philippine mobile number (`0917...`, `+63 917...`, `63917...`). A payment due matches the same way on its `reply_to`, and its run joins the set. Kept PayMongo events match on their payload. Matching is a scan of the workspace's runs, so it fits small-business volumes.
- Export (`GET /privacy/customer`): one JSON file with the matched runs and everything hanging off them (step inputs and outputs, uploads and receipt images as base64, deliveries, requests, bookings and their results and changes, calendar text, dues, claims, payment history, matched PayMongo events). Nothing from other customers or other workspaces. It is sent as an attachment with `Cache-Control: no-store`.
- The export hides the workspace's current and retired secret values and secret-looking keys, like the run page, because the file goes to the customer (review of 22 November). Test: `apps/api/src/privacy.test.ts`, "hides the workspace's secret values that a step saw".
- Delete (`POST /privacy/customer/delete`, body needs `confirm: "DELETE"`): one transaction. Payloads become `{"erased": true}`, step inputs and outputs become null, uploads, deliveries and calendar events are deleted, request subjects and booking results are blanked, dues lose `reply_to` and `reply_text`, receipt images are deleted, unfinished runs are cancelled. Amounts, statuses, references, the transfer reference of a confirmed payment, payment history and receipt reference numbers stay for bookkeeping. The response lists counts and what was kept and why.
- Audit (`privacy_requests`, migration 0045): one row per export or delete with the counts and the kept reasons. It never holds an email, a phone number or any deleted value.
- Retention (`payment_settings.receipt_retention_days`, 1 to 3650, default 90, a missing settings row counts as 90): the worker's upload sweep also clears the image on claims whose due is confirmed, cancelled or refunded and was last changed longer ago than that. Claims on open dues keep their image.
- Both endpoints are for the owner only and always filter on the session's workspace.

Edge cases: the same email in two workspaces (each owner sees only their own), a customer who used another email or number (not found, run the request again with each), "annamaria@x.com" when deleting "maria@x.com" (not matched), a phone inside a sentence or a list (found), a longer digit run that contains the digits (not matched), a run still waiting (cancelled so nothing more is sent), a due with no settings row (90 days).

What Daloy cannot reach: data already sent to Google Sheets, Slack, Telegram, Airtable, Notion, Trello, Drive, Google Calendar or email. The export lists the deliveries so the owner knows where to look.

Daloy does not make a business compliant with the Data Privacy Act. It gives the owner the tools to answer a customer's request. The rest is the owner's own work.

Owner's own tasks:

- Register with the National Privacy Commission if the business is required to.
- Name a Data Protection Officer.
- Write the business's own privacy policy.
- Answer customer requests within the time the law sets.
- Delete copies already sent to Sheets, Slack, Telegram, Airtable, Notion, Trello, Drive, Google Calendar or email.
- Handle backups, which keep old data until they roll over.

Tests: `packages/db/src/privacy.test.ts` (phone and email matching, retention at 89, 91 and open dues, per-workspace days, batch limit, the 1 to 3650 check), `apps/api/src/privacy.test.ts` (export holds one customer's data only, delete erases it everywhere and keeps bookkeeping, workspace isolation, roles 401 and 403, bad input 400, audit row without customer values, the notice in English and Tagalog with the business name escaped), `apps/api/src/members.test.ts` (route matrix).

## Shopify products and order trigger (I2, decision 0105)

What it does: a new order in the owner's Shopify store starts a run, with the order's number, customer, total and items as trigger fields. Two steps, Create product and Update product, write products to the store. A product can be found for update by its Shopify id or its exact SKU. Stock and inventory are not handled, which keeps the app's scopes to `read_orders` and `write_products`.

How it works:

- Connecting (`packages/db/src/shopify.ts`, `PUT /settings/connections/shopify` in `apps/api/src/connections.ts`): the owner enters the shop domain (only `*.myshopify.com`, checked by `normalizeShopDomain`, so a token can only be sent to Shopify), the app's client secret, and either the client ID of an app made in the Shopify Dev Dashboard or the Admin API access token of an older app made in the store admin (Shopify closed that path for new apps). With a client ID, Daloy gets a 24-hour token by the client credentials grant (`POST https://<shop>/admin/oauth/access_token`), keeps it in process memory and asks for a new one once after a 401. That grant only works when the app and the store are in the same Shopify organization (otherwise `shop_not_permitted`, shown as a plain message). The credential is stored encrypted and never returned. One read call proves the shop and lists missing scopes. Calls use the GraphQL Admin API pinned at 2026-10, because Shopify answers an unsupported version with the oldest supported one without an error.
- Order webhook: connecting also registers an `ORDERS_CREATE` subscription at `<PUBLIC_URL>/hooks/shopify/<32 random bytes as the path>`. Shopify only delivers to a public https address. If Shopify refuses it, the connection is still saved with `webhook: failed` and the reason. Disconnecting removes Daloy's subscription, best effort, and leaves the owner's own subscriptions alone.
- Receiving (`ShopifyHooksController` in `apps/api/src/public.ts`, 60 calls a minute): an unknown path is 403, a bad or missing `X-Shopify-Hmac-Sha256` (base64 HMAC-SHA256 of the raw body, keyed with the client secret, compared in constant time) is 401, a missing webhook id is 400, an `X-Shopify-Shop-Domain` that is not the connected shop is 403, and any topic other than `orders/create` is 200 with no run. Each published, unpaused workflow with the trigger `shopify_order` gets one run keyed `shopify:<shop>:order:<order id>`, so a retry, a replay or a concurrent duplicate starts one run. Shopify signs no timestamp, so the key does the replay protection.
- Trigger fields: `order_id`, `order_number`, `customer_name`, `customer_email`, `customer_phone`, `total` (text, as Shopify sent it), `currency`, `financial_status`, `created_at`, `shop`, `item_count`, `items` (one line per item) and `line_items`.
- Product steps (`shopify_create_product`, `shopify_update_product`, `apps/worker/src/steps/shopify.ts`, `packages/db/src/deliveries.ts`): queued as deliveries like Google Sheets and Airtable, one per run and step. A delivery is pinned to the shop connected when it was queued. A reconnect to another store holds it for review (`destination_changed`), and Post again sends it to the new store. Quota and unavailable answers are retried with backoff, and Retry, Post again and Mark as posted work.
- Price and SKU live on the variant, so they go through `productVariantsBulkUpdate` after `productCreate`. Descriptions are HTML-escaped, since trigger data is untrusted. An image must be an `https` link.
- Retries: an update sets absolute values, so an unknown outcome is retried automatically. A create with a SKU is retried too: on the retry, one product with that SKU is taken as the one the first attempt made. A create without a SKU goes to `needs_review` after an unknown outcome, because Shopify has no idempotency key for product mutations. If `productCreate` worked but the price call failed, the delivery goes to review and names the product id.
- Rule in `definitionSchema`: a product step cannot read `{{trigger.*}}` from a public form, an unsigned webhook, inbound email or a DM, since anyone can fill those in. A manual run, a schedule, a payment, a signed webhook and a Shopify order are allowed.
- Templates (`packages/engine/src/templates.ts`): `shopify-orders` uses the native trigger. `store-orders` stays a generic webhook, named "WooCommerce or other store orders".

Edge cases: a second product with an existing SKU on first create (refused, use Update), a SKU that matches no product or more than one (refused, nothing guessed), a price or SKU change by id on a product with several variants (refused, find it by SKU), a paused workflow (200, no run, so Shopify does not drop the webhook), an order for another connected workspace (each connection has its own path), a client secret from another app (401), a store outside the app's organization (plain message at connect).

Not supported: creating and then updating the same product in one run, because the deliveries of one run go out in no set order. Stock and inventory levels.

Tests: `packages/db/src/shopify.test.ts` (shop domain checks, HMAC accept and reject, order mapping, HTML escaping, the Admin API against the fake: errors, create, update, SKU reconcile, client credentials and renewal after a 401, webhook registration), `apps/api/src/shopify.test.ts` (connect, test, disconnect, webhook statuses, one run per order including concurrent duplicates, paused workflow, workspace isolation, product deliveries pinned to the store, retries and review, no token or secret in history, the 60 a minute limit), `e2e/shopify.spec.ts` (a signed order starts a run that creates and updates a product, and a replay does not repeat it), with the fake server in `test/fake-shopify.ts`. The check against a real store is in [live-shopify-check.md](live-shopify-check.md) (not run yet).

## Telegram message trigger (T9, decision 0117)

What it does: a photo, PDF or message sent to the owner's own Telegram bot starts a workflow. The trigger takes messages from the chat chosen in Apps only (the default) or from anyone. A photo or PDF becomes the upload field `file`, so an AI step can read it, and a `telegram` step with chat id `{{trigger.chatId}}` replies to the sender. The template "Log GCash receipts from Telegram" reads a receipt, adds a Google Sheets row that starts with "To check" and replies with what it read.

How it works:

- Connecting (`PUT /settings/connections/telegram` with `receive: true`, from the Receive messages box in the Telegram wizard): Daloy calls `setWebhook` with `<PUBLIC_URL>/hooks/telegram/<32 random bytes>`, `allowed_updates: ["message"]` and a secret token. The secret is an HMAC of the path keyed with the bot token (`telegramWebhookSecret` in `packages/db/src/telegram.ts`), so nothing new is stored and a new token gets a new secret. Telegram only sends to a public https address; if it refuses, the connection is saved with `webhook: failed` and the card says why. Turning receiving off or disconnecting calls `deleteWebhook`. Publishing a workflow with this trigger needs receiving on.
- Receiving (`TelegramHooksController` in `apps/api/src/public.ts`, 120 calls a minute): an unknown path is 403 and a missing or wrong `X-Telegram-Bot-Api-Secret-Token` is 401, compared in constant time before the body is read. `parseTelegramUpdate` keeps only new messages: chat id, sender name, text or caption, date, and at most one file. Each unpaused listener whose `from` setting allows the chat gets one run keyed `telegram:<bot id>:<update_id>`, so Telegram's retries and concurrent duplicates start one run.
- Files (`downloadTelegramFile`): a photo (the largest size under 5 MB) or a document with a JPEG, PNG, WebP or PDF mime type. `getFile` gives the path, which must look like `photos/file_1.jpg`. The declared size, the getFile size, `Content-Length` and the bytes read are each capped at 5 MB, and the bytes must sniff as one of the four types. The download happens once, only when a listener will run and the workspace has upload space. A file server that is down answers 503 so Telegram sends the update again.
- Trigger fields: `text`, `chatId`, `chatType`, `fromId`, `fromName`, `username`, `messageId`, `updateId`, `date`, `fileRefused` and `file` (the upload).
- Reply: the `telegram` step's optional `chatId` is allowed only with this trigger (`definitionSchema`), and the worker refuses a rendered chat that is not the run's `trigger.chatId`. The delivery carries that chat to `telegramSend`; without it the chat chosen in Apps is used.

Edge cases: an edited message or a button press (200, no run), a text message when a file is required (no run), a Word file or HTML named `.jpg` (refused, `fileRefused: true`), a file larger than the cap even when Telegram did not say its size (refused while reading), a paused workflow (no run), no upload space left (a listener that needs the file does not start, the others start without it).

Not supported: albums (each photo is its own update and its own run), voice, video and stickers, and edited messages.

Tests: `packages/db/src/telegram.test.ts` (secret, update parsing, photo size choice, type and size refusals), `apps/api/src/telegram.test.ts` (setWebhook with the secret, path kept, deleteWebhook on off and disconnect, refused address, publish needs receiving on, 403 and 401 before the body, one run for a repeated update including concurrent ones, my chat only against anyone, JPEG and PDF stored as uploads, fakes and oversize files refused, 503 when the file server is down, reply only to the sender's chat), `packages/engine/src/templates.test.ts`. The fake Bot API is in `test/fake-providers.ts`. Not run against the live Bot API yet.

## Read a public page (phase B1, decision 0107)

What it does: the `read_page` step fetches one public web page and returns its `title`, its main `text`, and `value`, the text of the first element that matches an optional CSS selector (the whole text when there is no selector). It also returns `previous`, the same step's `value` from this workflow's last successful live run, and `changed`, which is true when the two differ. The usual use is a schedule trigger, then `read_page` with a selector for the price, then a condition on `changed`, then an SMS.

How it runs (`apps/worker/src/steps/read-page.ts`): the address is checked by `checkUrl`, then `/robots.txt` of that host is read through the same guarded request as the http step and `robots-parser` is asked about `DaloyBot`. If the page is disallowed the step stops with "the site asks bots not to read this page". Otherwise one web request is claimed against the daily cap and the page is fetched (2 MB cap, HTML or text only, user agent `DaloyBot/1 (+<PUBLIC_URL>/bot)`). `cheerio` reads the selector first, then drops script, style, nav and footer and builds the text, with a line break after each block element. `previousValue` reads the earlier value from `step_runs`, so no new table is needed.

Why this way: the guarded request already holds the SSRF checks, redirect limit, timeout and size cap, so a second fetch would be a second place to get them wrong. A selector that matches nothing fails the step, because an empty value would look like a price change on the next run. A test run (mocked) returns a fixed sample page with no request.

Edge cases: a missing robots.txt (4xx) means no rules, while a server error on robots.txt stops the step and is retried. A page that is not HTML or text, a page over 2 MB, a private address, a redirect to a private address, an invalid selector and a selector with no match each give their own message. The first run has `previous: null` and `changed: false`. Test runs and failed runs never count as the previous value. Known limits: pages that need JavaScript or a login return little, the console has no `/bot` page yet, and `changed` is an exact text comparison.

Page text and AI: text from a page is written by strangers. A later AI step receives it only through its input template, and `buildPrompt` puts that input between `<data>` tags, tells the model it is not instructions and rewrites any closing `</data` tag inside it, so it cannot end its own block.

Tests: `apps/worker/src/steps/read-page.test.ts` (text extraction, selector, robots rules, user agent, content type, size cap, claim, SSRF refusals including redirects, all against a local fixture page with localhost allowed in that test only), `apps/worker/src/steps/read-page-run.test.ts` (`previous` and `changed` from `step_runs`, one claim per step, the mocked sample page), `packages/engine/src/read-page.test.ts` (config limits, a price watch definition, hosted-only prompt), `packages/engine/src/ai.test.ts` (hostile page text stays in one data block), `apps/web/src/ReadPage.test.tsx`, and `e2e/read-page.spec.ts` (add the step in the editor and run a test).

## Discord and Google Docs steps (phase I1, decision 0104)

What it does: Apps has a Discord card and the editor has two more steps. "Post to Discord" sends a message to one channel through a webhook link the owner pastes (three guided steps: make the webhook in the channel's Integrations settings, copy the link, paste it and a channel name to show in Daloy). Saving sends one test message at once. "Make a document" copies a Google Docs template into the Drive folder picked in Apps and fills its `{{placeholders}}`. The template is chosen with the Google Picker in the step panel (Pick a template), and the placeholder list below it maps each `{{name}}` in the document to a value, which can use `{{trigger.*}}` and earlier step outputs. Later steps can read `steps.<id>.output.url`, `documentId` and `name`. Both steps and the Apps card have Taglish text (`locale-integrations.ts`) and a logo (`public/logos/discord.svg`, `google-docs.svg`).

How it works, Discord (`packages/db/src/discord.ts`, `deliveries.ts`, `apps/api/src/connections.ts`, `PUT /settings/connections/discord` and `POST .../discord/test`): a delivery like Slack and Teams. The webhook URL is stored encrypted as the connection's credential and is write-only. The step queues a delivery with the connection pinned at queue time; the delivery worker posts `{ content, allowed_mentions: { parse: [] } }` to `<url>?wait=true`. Only https on `discord.com` or `discordapp.com` (and their subdomains) with the exact `/api/webhooks/<id>/<token>` path is accepted, with no user info, query or redirects, so a pasted URL cannot reach an internal host. A 429 waits for `Retry-After` or the body's `retry_after`. A deleted or changed webhook (401, 403, 404) marks the connection as needing a new link. A 5xx or a connection lost after the request left is an unknown outcome: the delivery goes to `needs_review` with Retry and Post again, like the other deliveries. Text over 2000 characters or empty after values are filled in fails without a request. Test runs queue nothing.

How it works, Google Docs (`packages/db/src/google-docs.ts`, `apps/worker/src/steps/google-docs.ts`, `POST /settings/connections/google-drive/template`): it runs inside the step and uses the Google Drive connection's `drive.file` grant, so no scope was added (Google lists `drive.file` for both `files.copy` and `documents.batchUpdate`, checked 22 November 2026). The Picker view shows Google Docs only; the server reads the picked file with the grant, accepts only a Google Docs document, and returns its name. The step stores the id and the name. The copy is made with `files.copy` into the Drive folder and named from the step. Placeholders are replaced with `documents.batchUpdate` `replaceAllText`: every `{{name}}` first becomes a random token and then each token becomes its value, so a value that contains `{{other}}` is inserted as typed. The step needs Drive connected with a Google sign-in (a service account has no storage) and a folder. Placeholders that matched nothing are listed in the step output as `unmatched`.

Why this way: the Teams pattern gives Discord encryption, pinning and the review state for free, and a webhook is one link per channel. The Docs step cannot be a delivery because later steps need the link. It does not need a review state either: each copy carries a hash of the run and step in `appProperties`, so a retry finds its own copy and only finishes filling it.

Edge cases: Google answers 404 for a template this Google account never picked, so the step says to pick it again. A full Drive, an API that is off in the Google project, a rate limit with a wait, and a revoked grant each give their own message. A failed fill after a successful copy is retried and finishes the same copy. Known limit: Drive's file list can lag a few seconds, so a retry inside that window can leave a second copy.

Tests: `packages/engine/src/discord-docs.test.ts` (content and placeholder rules, replace requests, definitions), `packages/db/src/discord.test.ts` and `google-docs.test.ts` (host and path allowlist, 429 waits, error mapping, no URL or token in any error, one copy per retry), `apps/worker/src/steps/discord-docs.test.ts` (both steps from a run, secrets out of deliveries and results, test runs), `apps/api/src/discord-docs.test.ts` (encrypted write-only connection, test message, template check, publish checks), `apps/web/src/DiscordDocs.test.tsx`. They use fake Discord, Drive and Docs servers in `test/fake-providers.ts`. The live check is a manual list in [live Discord and Google Docs check](live-discord-docs-check.md), not run yet.

## Browser step and browser service (phase B2, decision 0108)

What it does: the "Use a web page" step opens a public page in Daloy's own Chromium, runs up to 20 actions on it and keeps what they read. The actions are open an address, click (a CSS selector or visible text), type into a field, wait for an element, read a value into a name, and take a screenshot. Later steps read each name as `{{steps.<id>.output.<name>}}` and the last address as `output.url`; the screenshots are files of the run, like a form's uploads. A test run opens nothing: the output lists what the step would do, line by line, and never shows typed text. The step panel edits the action list with `BrowserActions.tsx`, with Taglish text in `locale-browser.ts`.

How it works: the worker (`apps/worker/src/steps/browser.ts`) fills the templates (the first address, `goto` addresses and typed values; selectors and names stay as typed) and posts the list to the browser service at `BROWSER_URL` with `BROWSER_TOKEN`. The service (`apps/browser/src/service.ts`) opens a fresh browser context for the job, with its own forward proxy (`proxy.ts`), runs the actions and closes both. The proxy is where the network guard lives. Every connection Chromium makes, including redirects, iframes, scripts, WebSockets and service workers, goes through it. It resolves the host once, refuses private, loopback and metadata addresses (`BLOCKED_RANGES`, the same list the HTTP step uses, now in `packages/engine/src/browser.ts`) and ports other than 80 and 443, and connects to the address it checked. Before typing, the service reads the field's `type`, `autocomplete`, name and id, refuses password, one-time code and card fields, and refuses a value that is a card number. The worker checks the answer, stores each screenshot as an upload after checking it is a PNG under 5 MB, and returns the output. The service also has a session API (open a page, get an accessibility snapshot with element refs, click or type by ref) for B3's AI agent; decision 0108 describes it.

Why this way: a browser runs a stranger's scripts, so it is its own service on its own Docker network, with nothing on that network but the worker. A proxy sees every connection, which `page.route` alone does not (service workers, DNS rebinding). One proxy per job keeps refusals with the job that caused them and gives B3 a place for a per-step domain allowlist. The design follows n8n's nod (Apache-2.0); `apps/browser/NOTICE` credits the adapted proxy code.

Edge cases: a page that redirects to 127.0.0.1 fails with "Daloy refused to open 127.0.0.1:<port>". An iframe or script aimed at a private address is refused while the page itself still loads, and the refused addresses are in the answer. A selector that never appears fails with the action's number and the selector. The service answers 503 when `BROWSER_CONCURRENCY` jobs are running, and the worker retries. A job past 60 seconds is closed and fails. A lost answer is retried only when the list has no click and no fill; otherwise it is an unknown outcome for a person. Without `BROWSER_URL` the step fails with "not set up on this server". Downloads, file pickers and passkeys never work.

Tests: `packages/engine/src/browser.test.ts` (action schema, limits, reserved names, the password and card field rules, the card number check, would-do lines, the lint warning), `apps/browser/src/proxy.test.ts` (refusals by literal, DNS, mixed answers, IPv4-mapped IPv6 and port; one lookup per request; deny-all), `apps/browser/src/service.test.ts` (real Chromium against a local fixture site: the action list, field refusals, a redirect, an iframe, a `fetch` and a WebSocket aimed at 127.0.0.1 that never reach the internal server, downloads, passkeys, busy, the time limit, sessions and refs), `apps/worker/src/steps/browser.test.ts` (templates, token, uploads, retries and unknown outcomes against a fake service) and `e2e/browser-step.spec.ts` (add the step in the editor, edit its actions, mocked test run).

## Conversation state (C1, decision 0115)

What it does: every guest who writes on Messenger, Instagram or to a connected mailbox has one conversation per workspace. Each message is stored with the conversation, and the run that answers it sees the conversation's id, status, saved details and last 10 messages as `{{trigger.conversation.*}}`. A newer message stops older runs of the same guest at their next step, so a burst of messages gets one answer and a waiting follow-up is dropped. A staff reply from the Page inbox makes the bot quiet for 12 hours (a workspace setting). The first reply carries a short privacy notice. Message text is deleted 90 days after the conversation's last message (a workspace setting).

How it works (`packages/db/src/conversations.ts`, `apps/api/src/public.ts`, `apps/worker/src/email-in.ts`, `apps/worker/src/advance.ts`, `apps/worker/src/steps/index.ts`):

- Recording: `recordInbound` upserts the conversation, locks it, and inserts the message with its `mid` (Meta) or Message-ID (email; the mailbox position when there is none). A new `mid` raises `version` and moves `last_inbound_at` (never past the current time). A replayed `mid` changes nothing. The Meta webhook and email-in call it in the same transaction that creates the runs, and each run gets `conversation_id` and `conversation_version`. A message no workflow listens to is not stored.
- Supersede: `runSuperseded` checks the run's booking version and then its conversation version. The worker checks it before every step, under a share lock right before an unsafe send, and after a failed attempt; the delivery worker checks it before sending. A stopped run is `cancelled` with "The customer sent a newer message".
- Replies: `meta_reply` first reads the run's conversation. While staff have it (`status = staff` until `staff_until`) the step takes branch `paused`; more than 24 hours after `last_inbound_at` it takes `outside_window`. Each can have its own edge to a fallback, such as SMS or email. Without a `paused` edge the run ends; without an `outside_window` edge the step fails with the window message. Otherwise it records an `out` message and queues the delivery in one transaction. The first reply of a conversation gets the notice in front (workspace language, retention days from the workspace), claimed through `notice_sent_at`.
- Echoes: `parseMetaEchoes` reads `is_echo` events. Every reply Daloy sends carries `metadata: "daloy"`, which Messenger returns on the echo. An echo with that mark, or with the same text as an `out` message from the last ten minutes, is Daloy's own and changes nothing. Any other echo is stored as a `staff` message and sets `status = staff` with `staff_until` at now plus the quiet period. The next guest message after that time sets the status back to `bot`.
- Saved details: step `conversation_update` merges `check_in`, `check_out`, `guests`, `name`, `phone` and `email` into `conversations.fields` (200 characters each; an empty value keeps the saved one). Only `meta_dm` and `email` workflows may use it.
- Retention: `purgeConversations` runs on the worker sweep. It deletes conversations older than the workspace's `conversation_retention_days`, with their messages, and erases the runs linked to them like an R6 delete.
- R6: export and delete find a guest's conversations by saved fields, the email address, any message text, or a matched run, and include every run of those conversations. Delete removes the conversations and messages outright.

Why this way: it follows the booking version pattern (decision 0032), so stopping an older run needs no new worker logic. Recording and run creation in one transaction means a replay or a crash never leaves a message without its run or the other way round.

Edge cases: two webhooks for one guest at the same moment wait on the conversation lock and get versions one after the other. A sender timestamp in the future is clamped to now, so it cannot hold the window open. A reply that already went out before the newer message stays sent. A notice and reply longer than 2,000 characters together: the reply goes alone and the next one carries the notice. Known limits: no link to a privacy page yet, no notice on email replies yet, and Take over and Hand back buttons come with the Conversations page (C7).

Tests: `apps/api/src/conversations.test.ts` (two messages in one second give one reply; a newer message ends the older run's follow-up; window at 23:59 and 24:01 with the `outside_window` edge and without one; Page inbox echo pauses and own echo does not; replayed `mid` adds nothing; notice once; saved details reach the next run; R6 export and delete include messages; the sweep deletes after the retention days), `apps/worker/src/email-in.test.ts` (an email starts a conversation once), `packages/engine/src/definition.test.ts` (the two edges and the trigger rule for `conversation_update`).

## Knowledge sheet (phase C3, decision 0116)

What it does: the Knowledge page (menu entry "Knowledge", `#/knowledge`, owner and operator) is where the resort writes what the concierge may say. An entry has a kind (room, rate, fee, FAQ, policy, location, activity, arrival or review link), a title, some text, and for rooms, rates and fees a price block. Nothing a guest sees changes when an entry is saved. Publish saves a numbered copy of every entry, and the page shows the live version, when it was published and whether the drafts differ from it.

How it works: drafts live in `knowledge_entries`; Publish (`POST /knowledge/publish`, `publishKnowledge` in `packages/db/src/knowledge.ts`) copies them into a new `knowledge_versions` row for the workspace, with the next version number, under an advisory lock. A database trigger refuses any later UPDATE of that table. `readKnowledge` returns the highest version, which is the only thing C4's answers will read. The price block is a base price in whole pesos with a unit (per night, per person, per person per night, per stay, per day), a capacity, a deposit (fixed pesos or a percent) and up to 12 named rules (a season as `MM-DD` to `MM-DD`, weekdays, or an extra-guest fee, each with its own price). The shape and its limits are `knowledgeEntryInput` in `packages/engine/src/knowledge.ts`, shared by the form, the API and the stored copy. Links must be https.

Why this way: the resort has not said whether rates vary by season, weekday or head count, so the form stores a base price plus rules instead of fixed columns. Draft and published copies are separate so an edit made while a guest is chatting cannot change the answer in flight, and each copy keeps the draft ids so C4 can say which entries an answer used. The tables hold business text, not guest data, so `privacy.ts` does not list them.

Edge cases: Publish is refused with nothing to publish or no change since the live version; two publishes at once get one version number each or a 409. Deleting a draft leaves published copies alone. A price, deposit or rule on an FAQ, policy, location, activity, arrival or link entry is refused. An entry needs text, a price or a link. Prices with centavos are not accepted. Which rule wins when two match is not decided here; `stay_quote` in C4 does that.
