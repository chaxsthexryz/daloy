# Threat model

Kept current with each phase. A mitigation marked "planned" does not exist in code yet.

## Assets

- Stored secrets (API keys and SMTP credentials that workflows use)
- Each owner's Gmail app password or Google sign-in (`gmail.send` token blob, decision 0063), and the right to send as their address
- IMAP credentials, incoming message text and the saved position of each monitored folder
- Each owner's Google service account key and Slack bot token (pasted, or from Connect Slack), which can write to their shared sheets and post to their channels, and their Telegram bot token, which can message every chat the bot is in. The Google Calendar connection uses the same kind of service account key, which can change every event on the calendars shared with it
- Each owner's Microsoft access and refresh tokens, which can send email as their mailbox, and their Teams workflow link, which lets anyone holding it post to one channel
- OAuth consent flows in progress (the hash of a random state and an encrypted PKCE verifier, ten minutes) and every OAuth connection's token blob (decision 0058)
- The installation's Microsoft Entra client secret (`MICROSOFT_CLIENT_SECRET`)
- Console sessions and API tokens
- Workspace membership and roles, which decide who can change automations and who can authorize a purchase
- Run data: trigger payloads and step outputs, which can hold customer personal data
- Files visitors attach to forms (photos, IDs, receipts), kept 7 days in the database
- The ability to send email and make HTTP requests from the server

## Entry points

- Console API (session cookie)
- Webhook URLs and hosted forms, including anonymous embedded forms (public), and file uploads on those forms
- File downloads from run details (`GET /runs/:runId/files/:fileId`, owner and operator session)
- Owner mailbox setup and the worker's outbound IMAP connection
- Approval links (public, random single-use token; a named approval also needs the approver's session)
- Invite links (public, random single-use token)
- Gmail confirmation links (need the owner's session and a random single-use token)
- MCP endpoint (bearer token)
- Password reset links (public, random single-use token)
- Outbound: HTTP request step, email step (the installation's SMTP server, the owner's Gmail over SMTP, or the Gmail API), the API's test email, LLM calls, Google Sheets, Google Drive, Slack, Outlook and Teams deliveries and connection tests
- Inbound from OAuth providers: the shared consent callback, `GET /settings/connections/oauth/callback`, and Outlook's older address for it, `GET /settings/connections/outlook/callback` (no session needed to reach either; only Microsoft's administrator consent answer is handled without one)

## Threats and mitigations

| Threat | Mitigation | Status |
| --- | --- | --- |
| A site frames a signed-in console or attributes an inquiry to a visiting employee | Cross-origin framing is enabled only for the public form embed. Its submissions ignore cookies for requester attribution. The standalone form records a signed-in member as the requester only when `Origin` equals the `PUBLIC_URL` origin, so a sibling origin cannot post a tracked request as a member (M14). Standalone and embedded forms share field validation, the honeypot and the ten-post per-IP limit. | Implemented, N9 |
| Someone reads a mailbox password or directs the worker to an internal service | Only the workspace owner can manage a mailbox. Credentials are encrypted for the workspace and workflow, omitted from status responses, and cleared on disconnect. The worker checks all resolved addresses and connects to a checked public IP with TLS certificate verification against the entered host on port 993. Provider error text and authentication data stay out of logs. | Implemented, N9 |
| Replayed messages, a large attachment or a forged sender starts unintended work | The worker bounds each read and stores a run and mailbox checkpoint together. Obsolete polls lose their claim. It skips oversized mail, exposes plain text and leaves attachments in the mailbox. Sender and Reply-To headers are untrusted. A workflow that needs authorization must use a separate approval. One workspace's slow or failing mailboxes cannot delay another office's mail: live mailboxes go before drafts, workspaces take turns, one workspace holds at most one poller, and a failing mailbox backs off to one check an hour (security review M13, decision 0055). | Implemented, N9; fair turns N11c-3 |
| SSRF through the HTTP step | Allow only http and https on ports 80 and 443. Block private, loopback, link-local and metadata ranges for IPv4 and IPv6, including IPv4-mapped addresses. Check inside the socket's DNS lookup, so the connection goes to the checked address. Re-check after each redirect (max 3) and drop the caller's headers on a cross-origin redirect. A 307 or 308 to another origin fails instead of resending the body. 1 MB and 10 second limits. On a public demo `HTTP_ALLOWED_HOSTS` limits HTTP steps, and their redirects, to listed hosts. See [decision 0006](decisions/0006-ssrf.md). | Done, phase 4; allowlist N3 |
| Webhook spoofing | Random 32-byte URL path, optional HMAC-SHA256 signature checked in constant time, 256 kb body limit, 60 requests a minute per IP. A blank or missing signing secret name fails closed with 401, the definition schema requires a valid name, and publish checks the secret exists (M1) | Done, phase 3 |
| Replay of a captured signed webhook call | The signature covers a timestamp and the body, and calls more than 5 minutes from the server clock are refused. An identical replay inside the window returns the first run and starts nothing. A caller still on the old format (no timestamp) stays replayable until its owner ticks "Require the timestamp"; the last such call is recorded and shown in the editor, and the response carries a warning header. | Done, N11b (decision 0054). Remaining: old callers until their owner switches |
| A busy automation getting the owner's Gmail or Outlook suspended, or mailing far more people than intended | A per-workspace daily cap on recipients through Gmail and Outlook (`MAILBOX_DAILY_CAP`, default 400, Manila day), counted before sending with the step key. Over the cap the run waits in review with a plain reason; nothing is sent or dropped. Remaining: the watchdog's alert and the test email are not counted. | Done, N11b (decision 0054) |
| A paused automation still starting runs through a forgotten route | One check, in the transaction that inserts a run, under a share lock on the workflow row. Every insert of a live run calls it (`createRun`, the tracked request insert, a booking reschedule). Webhook, form, MCP, Run button, schedule, email-in and PayMongo are tested; builder test runs are exempt on purpose. A new route that inserts runs must call `assertNotPaused`. | Done, N11b (decision 0054) |
| Cancelling a run racing the worker, or an approval link confirming a cancelled run | Cancel is one guarded UPDATE from pending or waiting, so the worker's wake-up and the cancel have one winner. The waiting attempt closes as not sent and the run's open approval links expire. Cancel is for owners and operators of the workspace; another workspace gets 404. | Done, N11b (decision 0054) |
| Secrets leaking into logs | Secrets are inserted by reference (`{{secrets.name}}`) only while a step runs. The stored step input is a preview resolved with `[secret]` in place of each secret, so no encoding of a secret is stored through it; output and error text have every form of every value (raw, JSON-escaped, URL- and form-encoded) replaced before anything is stored. The run history API replaces every form of current and retired secret values again on the way out, so older rows and rotated values stay hidden, then masks by key name (`password`, `token`, `authorization`, `api_key`, `cookie` and similar) in trigger data, step input and step output. See [decision 0008](decisions/0008-step-input.md). The office request list, delivery activity and MCP run status use the same read-time hider (security review M9). | Done, phases 4 and 6; all readers N11c-3 |
| Expression injection | Expressions are path lookups only (no eval or Function), with limits on template size, path depth and output size. Resolution is a single pass, so trigger data containing `{{secrets.x}}` stays literal text. See [decision 0002](decisions/0002-expression-resolver.md). | Done, phase 4 |
| Approval link theft and replay | 32 random bytes per link, only the SHA-256 stored, so a database leak gives no working links. The link expires with the step's timeout and works once (guarded UPDATE on `used_at`). GET only shows the request, so link scanners cannot decide; POST records it. Unknown, used and expired links get the same response. `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. 30 views and 10 decisions a minute per IP. Remaining risk: for an approval with `to` (link-holder), whoever holds an unused link can decide, because the email is the only authentication. Named approvals close this (next row). See [decision 0009](decisions/0009-approval-links.md). | Done, phase 7 |
| A forwarded approval link, a repeated answer or someone from another workspace authorizing a purchase | A named approval is decided by one UPDATE that requires an unused, unexpired link, the signed-in user to be the named approver, and that user to be, at that moment, a member of the run's workspace with the owner or approver role. The page shows no request details until the approver is signed in, and the confirmation page shows only the decision. Who decided and when are stored. Tests cover forwarded links, other workspaces, removed and demoted members, expired links, repeated and concurrent answers. See [decision 0022](decisions/0022-workspace-members-named-approvals.md). | Done, roadmap phase 4 |
| A form, webhook or MCP caller naming another workspace's resource, an archived one, or a time the business does not offer | `parsePayload` accepts a resource id only from the active resources of the workflow's own workspace, loaded at every entry point (hosted form, webhooks, test runs, the Run button, MCP); a name or a foreign id is a 400 that reveals nothing about other workspaces. The name stored with the id is read from the database, never from the caller. Times are checked on the server whatever the browser sends: real date and time, in the field's IANA zone, not in a DST gap, not ambiguous without an offset, in the future and on the slot grid. Only owners add, rename or archive resources; resource names are shown on the public form by design. See [decision 0031](decisions/0031-zoned-times-and-resources.md). | Done, P6a |
| Double booking a resource, or a retried request moving a booking twice | A Postgres exclusion constraint refuses overlapping active bookings per workspace, test scope and resource, whatever the path. A booking step stores its result with its change, so a retry returns it. Staff and MCP changes carry the version they saw; each version changes once (primary key on the change log), and a repeat of the same change gets the first answer. See [decision 0032](decisions/0032-booking-lifecycle.md). | Done, P6b |
| A public form or an unsigned call cancelling or moving someone's booking | Saving refuses reschedule and cancel steps unless the trigger is manual (the owner's Run button) or a webhook with a signing secret, whose calls are checked in constant time. Staff changes need the owner or operator role and are scoped to the workspace; MCP needs the owner's token. Bookings of other workspaces answer 404. | Done, P6b |
| A reminder or follow-up sent for a booking that was moved or cancelled | Runs are linked to a booking version and stop before any attempt of an older version, including retries, resumed waits and operator recovery. Emails and unsafe HTTP calls check again under a lock held until the send starts. Sheets, Slack, Outlook and Teams deliveries check the run's booking under a lock held until the provider answers, and Retry and Post again refuse them once the booking moved on. Remaining risk: idempotent HTTP calls can still go out if the change lands between the check and that send; a change during an open send waits for it. | Done, P6b and N2b |
| Test bookings blocking or leaking into live ones | `test` is part of the constraint and of every lookup; test references start with `TEST-`; staff lists and MCP show live bookings only. | Done, P6b |
| A logo upload carrying script, or a page or email loading something from another site | The logo is accepted only as PNG, JPEG or WebP by its first bytes, at most 100 KB, from a signed-in owner. SVG and every other type are refused. It is served from the API with a fixed image type, `nosniff` and no cookies needed. Pages and emails reference it on their own origin or as an inline attachment, and the accent colour is checked as `#rrggbb` before it reaches CSS. See [decision 0050](decisions/0050-brand-kit.md). | Done, N18 |
| A member doing more than their role allows | Every console route names its roles with `Allow(...)` after the session guard, and a test calls every route as every role. Queries are scoped to the session's workspace. The owner row can't be changed, given or taken (check constraint and guarded UPDATEs). | Done, roadmap phase 4 |
| A removed member keeps access | Removing a member deletes their sessions, and an account with no membership counts as signed out and can't sign in. Named approvals waiting for them can't be answered. | Done, roadmap phase 4 |
| Invite link theft | 32 random bytes, only the SHA-256 stored, seven days, one use (guarded UPDATE in the same transaction that adds the member), 10 accepts a minute per IP. An email that already has an account must enter its password. Remaining risk: whoever holds an unused invite for a new email can join with that role, so the owner should send it over a channel they trust. | Done, roadmap phase 4 |
| An AI-built workflow does something the owner did not want | The AI only returns a draft, checked against the same definition schema as a hand-built workflow. A draft the checker finds nothing to fix is then created and turned on in one step (decision 0048), because the owner asked for a chat that deploys what it builds; the owner lands in the editor with it on and can turn it off there. A draft with lint warnings, or one whose publish is refused (an app it needs is not connected), is not saved until the owner presses Turn it on or Save as draft. Remaining risk: a clean-looking draft that does something the owner did not intend starts running as soon as it exists. Test runs mock HTTP and email by default, and live HTTP steps still pass the SSRF guard. `POST /ai/draft` needs a session and is limited to 10 calls a minute per IP. A draft is also linted for silent approvals, unrouted classify labels, test switches and unguarded number gates, and the editor lists the warnings (advice only, not a security boundary; the messages hold only step ids, field names and labels, so the repair round adds no free text to the prompt). See [decision 0017](decisions/0017-ai-workflow-drafts.md) and [decision 0033](decisions/0033-draft-lint.md). | Done |
| Private data reaches the model through Build with AI (N4f) | The tab sends the conversation as typed, the current draft when there is one and the connected app kinds (a fixed list, never typed text), nothing else: no form submissions, run data, booking details, secrets, business profile or team addresses. People are labels (`owner@people.invalid`, `member1@people.invalid`); the page puts the real address into the draft after it returns and takes it out again before the next message. `apps/api/src/ai-draft.test.ts` records the request the fake model receives in a workspace holding a member, a profile, a secret and a submission and asserts none appears, and `e2e/build-with-ai.spec.ts` asserts the same on the browser's request body. Nothing is saved until Save as draft, so a draft the owner dislikes leaves no record. Remaining risk: what the owner types is sent as written (the page says so), a model may ignore the labels and invent an address (the review lists every address and the owner reads it before saving), and the editor's "Ask the AI" still sends the open draft with its real addresses, as before; moving it to labels is a follow-up. | Done, N4f |
| Provider API keys saved in the console | Encrypted with AES-256-GCM like secrets, with the user and provider as associated data; write-only (the API returns only `hasKey`); error messages never include the provider's response body. See [decision 0016](decisions/0016-ai-settings-page.md). | Done |
| Private data reaches the model through failure explanations (N10a) | The model gets only `{ facts, fixed }`: closed-set fields built by `failureFacts` (run state, preview flag, step type, outcome, attempts, dead-letter flag, an HTTP status code, a reason from a fixed list, each failed delivery's app, state and error kind, lint rule ids with counts) and Daloy's own fixed text. Error text, step ids, labels, URLs, hosts, addresses, form values and booking fields never leave that function. `apps/api/src/explain-api.test.ts` seeds a run holding a name, an address, booking text, a host with a token in its query string and a step id, records the fake model's request and asserts none appears and the message has exactly those keys. The reply is plain text, at most 600 characters, refused when it holds a link, shown as text under "Written by the AI model", never stored; the route writes no run, step or delivery row (tested by comparing rows before and after). Only owners can ask, 10 a minute, each ask one AI action under the plan. Remaining risk: the model can still word the facts wrongly; the fixed text stays above it. See [decision 0039](decisions/0039-failure-explanations.md). | Done, N10a |
| Private data reaches the model, or an answer changes a run, through Ask about a request (N10b) | Off unless the installation sets `AI_ASK=on`. The owner picks a reference and one of three fixed questions; nothing typed reaches the model. The answers are fixed text from closed-set fields. The reword sends only `{ question, language, facts, fixed }`: N10a's facts plus the plain state and a timeline of step type, state, outcome and attempts. `apps/api/src/ask-api.test.ts` seeds a run whose payload, step input and output, error and request subject hold an email, a name, a booking time, a workspace secret and a URL with a token in its query string, records the fake model's request and asserts none of them, nor the reference, ids, workflow name or labels, appears, and that the keys are exactly the allowlist. Answers are read-only: `GET` for the fixed answers, the reword writes only the usage count (tested by comparing run, step and delivery rows before and after), and the card has links only. A reference from another workspace is a 404 like an unknown one; approvers and requesters get 403; only owners reword, 10 a minute, one AI action each. Remaining risk: the model can word the facts wrongly, so it stays off until the twenty-request check in [ai-ask-measurement.md](ai-ask-measurement.md). See [decision 0041](decisions/0041-ask-about-a-request.md). | Done, N10b (off by default) |
| The AI model page used to make the server call internal hosts | No user-entered URLs: hosted providers have fixed URLs in code, and the local choice uses the operator's `LLM_BASE_URL`. Reading the provider's model list (`POST /settings/ai/models`, also on save) sends the key to that same fixed URL and nowhere else. The live test and the list are each limited to 10 calls a minute per IP. | Done |
| Trigger data sent to a hosted model | Ollama on the host is the default, so nothing leaves the machine. Photos and PDF text reach a hosted model only for file fields an AI step lists (decision 0052). A hosted provider (`LLM_PROVIDER=openai`) is opt-in through env vars and `.env.example` says what it receives. `LLM_API_KEY` comes from the environment and is only sent for accounts when `SHARED_LLM_KEY=open` (off by default, decision 0035) and the workspace has a plan (decision 0038), so strangers on a public installation cannot spend the operator's quota. LLM errors never include the provider's response body. Remaining risk: with a hosted provider, form messages, names and emails reach that provider, and free tiers may use them for training. See [decision 0015](decisions/0015-openai-compatible-llm.md). | Done |
| Prompt injection through trigger data | Trigger data only reaches the model inside `<data>` tags in the user message; a closing tag in the data is escaped. The system prompt holds only fixed text and the owner's literal text (the schema rejects `{{` there). Replies are validated against a fixed per-task JSON schema, so classify can only return a configured label. Remaining risk: a model can still be steered within that schema, such as a wrong label or unwanted text in a draft. See [decision 0010](decisions/0010-ai-step.md). | Done, phase 7 |
| MCP tool abuse | Bearer token per user, stored as SHA-256 and checked on every request, so revocation takes effect at once. A token only sees its owner's workflows and runs; another user's run gets the same "run not found" as a missing one. Only workflows with a form trigger and a published version become tools, and their arguments pass the same field schema as the hosted form. Runs keep their approval steps. 60 requests a minute per IP and a 256 kb body limit. Remaining risk: a leaked token can do what its scopes allow until it expires or is revoked, see the token scopes row. See [decision 0011](decisions/0011-mcp-sdk-v2.md). | Done, phase 8 |
| A session surviving a password change | Changing the password needs the current one, keeps only the session that asked, deletes the account's other sessions and marks open reset links used. A wrong current password is a 400, and the route allows 10 a minute per user. Remaining risk: API tokens are not revoked, because they belong to the workspace; the owner revokes them on the tokens page. | Done, N11a |
| Reset link theft and replay | 32 random bytes, only the SHA-256 stored, valid 30 minutes, used once through a guarded UPDATE. Using a link or changing the password retires the account's other open links, and success deletes every session. Unknown, used and expired links give the same 400. The link is in the URL fragment, so it is not sent to the server in request lines or Referer. Remaining risk: whoever controls the mailbox controls the account, and sign-up emails are not verified, so a reset goes to whatever address registered. See [decision 0053](decisions/0053-accounts-and-token-scopes.md). | Done, N11a |
| Finding which emails have accounts through password reset | The request always answers 202 `{ ok: true }`, and the lookup and mail run after the response, so neither the body nor the timing differs. | Done, N11a |
| Mail flooding one address through password reset | 5 requests per 15 minutes per IP (the in-memory `RateLimit`) and at most 3 links per account per hour, counted in Postgres under a row lock so it holds across processes. Over the cap the answer is the same and no mail is sent. Remaining risk: the per-IP counters are per process, and an SMTP failure is only logged, so the requester cannot tell. | Done, N11a |
| A leaked API token doing more than it needs to, or lasting forever | A token has scopes (`read`, `run`, `manage`) and an optional expiry of 1 to 365 days. Tools outside the scopes are not registered for that request, so they are absent from `tools/list` and a call is an unknown tool. Expired tokens get 401 like revoked ones. Remaining risk: tokens made before N11a keep full access with no expiry so live tokens keep working; the owner can revoke and replace them. | Done, N11a |
| Oversized payloads | Body size limits on every route, 1 MB HTTP response limit, at most 100 steps per definition, expression output limit, at most 10 email recipients | Done, phases 1 to 4 |
| Two workers running the same step at once | Run lease claimed with a conditional UPDATE, guarded state updates, unique `(run_id, step_id, attempt)`. Each attempt has a random `claim_id`; a worker writes its result only under its own claim, so one that lost its lease mid-send cannot overwrite the worker that took over or an operator's answer (decision 0030) | Done, phase 2, P5 |
| Duplicate orders or emails after a lost answer, a 5xx or a crash | Failures are classified as not_sent, rejected, throttled or unknown. An unknown outcome on a POST, PATCH or email is never resent on its own: the run waits in `needs_review` for It went through, Send again or Stop. `not_sent` is claimed only when no socket opened for request bytes (connect, or the TLS handshake for https); the request's `finish` event is not trusted. Right before an unsafe send the worker writes `dispatched_at` under its claim and holds a row lock until the request is on its way, again before every redirect hop; a worker that takes over an attempt with the mark parks it instead of resending, and a stale worker whose claim was taken sends nothing. A non-idempotent request answered with a redirect is never resent, whatever the follow-up does, and an error status is classified before its body is read. The `Idempotency-Key` is the same on every attempt and treated as a hint only. Each operator action is one guarded UPDATE. Remaining risk: a step wrongly flagged `idempotent: true` is retried after a 5xx; a 429 with a long `Retry-After` dead-letters and needs a person | Done, P5 |
| Stolen database credentials or SQL injection | In compose the API and worker connect as `daloy_app` (SELECT, INSERT, UPDATE, DELETE only); a one-shot `migrate` service holds the owner credentials. CREATE on `public` is revoked from PUBLIC. Remaining risk: the app role can still read and change every row. See [decision 0013](decisions/0013-app-database-role.md). | Done, phase 9 |
| Password guessing on login | argon2id hashes, 10 login attempts a minute per IP, same response time for unknown emails | Done, phase 3 |
| Rate limits bypassed or shared behind a proxy | `TRUST_PROXY` is a hop count, so `req.ip` is the address the nearest trusted proxy saw and a client's own `X-Forwarded-For` entries are ignored. Sign-up is limited per IP per hour. Remaining risk: if port 3000 is reachable without passing the proxy, a client can write its own `X-Forwarded-For` and pick a bucket; compose binds it to 127.0.0.1 for that reason. Counters are per API process. See [decision 0035](decisions/0035-deployment-settings.md). | Done, N3 |
| Session cookie sent over plain HTTP | `SECURE_COOKIES=true` (or `NODE_ENV=production`) marks it Secure; docs/deployment.md sets it. An unreadable value stops the boot. | Done, N3 |
| Default database passwords | Compose refuses to start without `POSTGRES_PASSWORD` and `APP_DB_PASSWORD`; `.env.example` has none filled in. | Done, N3 |
| Backups read off the machine | Dumps are copied through an rclone `crypt` remote, so Google Drive holds only ciphertext. `SECRETS_KEY`, the database passwords and the crypt password are stored apart from the dumps. The Google account is the remaining trust boundary: its loss deletes or exposes ciphertext only. | Documented, N3; not yet run on the target |
| Cross-site request forgery on console routes | SameSite=Lax session cookie, so other sites cannot send it with a POST | Done, phase 3 |
| Session theft from a database leak | Only SHA-256 of session cookies and API tokens is stored | Done, phase 3 |
| Form spam | Honeypot field named `_website`, which no real field can be called, so a real website field is never dropped. 10 submissions a minute per IP, field validation | Done, phase 3 |
| Replayed or duplicated business events | A webhook's `eventKey` (or the caller's `Idempotency-Key`, or MCP `idempotencyKey`) is stored in `run_keys` with a primary key on workflow, test flag and key, inserted in the same transaction as the run, so a replay or a burst of copies starts one run, also under concurrency. Remaining risk: a webhook without a key, or a caller that sends no key, gets a run per call; keys are per workflow, so two workflows fed the same event both run. See [decision 0029](decisions/0029-business-event-keys.md). | Done, eight-workflow P4 |
| Out-of-range or malformed amounts reaching a workflow | One field check (`parsePayload`) for the hosted form, webhooks with `fields`, builder test runs, the console Run button and MCP: required fields, number `min`, `max` and `integer`, plain decimal number text only, emails and text length. A numeric condition on a missing or non-number value takes its `invalid` edge or fails the run, never `false`. Remaining risk: a webhook without `fields`, and manual or scheduled runs, still pass any JSON to the workflow, where only `invalid` branches catch bad numbers. See [decision 0027](decisions/0027-field-limits-invalid-branch.md). | Done, eight-workflow P2 |
| Duplicate or replayed office requests | Each form load carries a random submission key. `unique (workflow_id, submission_key)` in the database means a double-click, a retry or a replay of the same post returns the first reference and creates no second run or email. A key that is missing or not a UUID is rejected. Remaining risk: someone who copies a page's key only gets that same reference back. See [decision 0019](decisions/0019-office-request-records.md). | Done, roadmap phase 1 |
| Guessing request references | References are identifiers only. The public thank-you page shows the reference of the request just sent. The request list and run details need the owner's session and are scoped to the owner's workflows. | Done, roadmap phase 1 |
| Mail sent as the wrong owner, or from another address after a failure | `resolveSender()` is the only place that picks the sender, and every email step, approval email and test email goes through it. It reads the run's workflow owner only. An unconfirmed, failed or disconnected Gmail sender blocks the send before any server is contacted, and nothing falls back to the installation server or another owner. Returning to the installation server is a separate, explicit action. See [decision 0020](decisions/0020-owner-mail-senders.md). A Google sign-in keeps these rules: a refused grant (a password change, a revoke) or a second 401 marks the sender failed, and an installation without its Google client blocks the send (decision 0063, tested). | Done, roadmap phase 2; Gmail sign-in P5 |
| Secrets sent where trigger data points | Secrets reach HTTP steps only; saving another step that names one is refused and the worker resolves it to nothing. An HTTP step that uses a secret must keep its host independent of trigger and step data, checked at save and again at run by comparing the origin with that data blanked. Only the owner may save workflows (operators get 403). Remaining risk: the owner can still send their own secret anywhere they type. See [decision 0025](decisions/0025-destination-aware-secrets.md). | Done |
| Conflicting approval outcomes after a retried email | Every link of one approval step stands for one decision under the run lock; later links keep the first deadline; an early wake-up never takes the timeout branch. See [decision 0009](decisions/0009-approval-links.md). | Done |
| Open relay through the installation's mail server | A new sign-up could mail any address through the shared server from a live test run, a published workflow, an approval email or the test email. `SHARED_MAIL=approved`, the default for any server other than Mailpit or localhost, lets only workspace owners the operator approved send through it. Each owner has a daily recipient limit, counted atomically in `shared_mail_usage` before the send, so it holds across API and worker processes. Refusals contact no server and are not retried. Remaining risk: an operator who sets `SHARED_MAIL=open` on a real relay, or approves an account without checking who owns it (sign-up addresses are not verified). See [decision 0024](decisions/0024-shared-mail-policy.md). | Done |
| Gmail app password theft | Encrypted with AES-256-GCM, the owner's id bound in as associated data, so a ciphertext copied to another row does not decrypt. ## Residual risks from the public intake review (decision 0057)

- The Appointment reminder and Renewal reminders starters still email submitted text (`{{trigger.service}}`, `{{trigger.item}}`) to the address typed on their forms. They are meant for staff entry, but the form URLs are public.
- A custom workflow that books straight from a public form still reserves slots. Only the Lead to booking starter has an approval step.
- Workflows already built from the old starters keep the old wording and the old booking flow until the owner edits them.
- Requester attribution needs the browser's `Origin` header to reach the API and `PUBLIC_URL` to match the address people use. A proxy that drops or rewrites `Origin` makes every tracked request anonymous.

## Public demo boundary

The demo page (`apps/web/demo`, published as `site/demo/` on Cloudflare Pages) accepts a free-text request and sample form values. It renders them as React text, keeps them in browser memory, and never sends them anywhere: there is no model call, no API call and no storage. On daloyapp.pages.dev it is a static site with no console behind it. ## Telegram (decision 0042)

- The bot token is encrypted like the Slack token, bound to the owner and provider, and never returned by the API or written to logs. It is part of the Telegram request URL, so Daloy never prints a request URL or puts one in an error message.
- The Telegram address is fixed (`api.telegram.org`) or set by the installation's env var, never by a user, so a user cannot point Daloy at an internal host.
- The chat id is validated (a number or `@name`), and the chat is pinned to each delivery when it is queued, so editing the connection cannot redirect messages already queued.
- Anyone in the chat can read what is sent. The same rule as Slack: keep private details out of the message text.
- A bot token that leaks lets someone message the bot's chats. Replace it in BotFather (/revoke), then Replace token in Apps.

## Google Calendar (decision 0044)

- The service account key is stored encrypted like Sheets, bound to the owner and provider, and never returned or logged. The scope is `calendar.events`. The account sees only calendars their owner shared with it, so a leaked key can read and change those calendars' events, nothing else.
- The Calendar address is fixed or set by the installation's env var (`GOOGLE_CALENDAR_URL`), never by a user.
- The calendar id is validated, and the calendar is pinned to each delivery when it is queued, so editing the connection cannot redirect a queued event. A changed calendar holds the delivery for review.
- An event is bound to the account and calendar it was last written to. A reschedule or cancel after the owner switched calendars goes to that same calendar or stops in review, so guest details are never copied to a calendar with a different audience without the owner choosing Post again (security review M11).
- Writes for one booking are ordered by the booking row lock, so an older update cannot restore an event after a cancel (M12). Error text stored for a delivery is Daloy's own, never Google's wording (M9).
- Event ids come from the booking id through sha256, so an id gives away nothing and a caller cannot choose another booking's event. A delivery reads the booking by id and workspace.
- Event title and description are text from the workflow's templates and can hold guest details. Anyone with access to the calendar sees them: share the calendar only with the people who may see bookings.
- Connect with Google (decision 0064): the grant has `calendar.app.created` only, so a leaked token can read and change events on the calendar Daloy created and cannot see the owner's other calendars. The access and refresh tokens are one encrypted blob like every OAuth connection, are never returned or logged, and are hidden from history, Activity, CSV and the delivery list by the same hider. `calendar.events` and `calendar.calendarlist.readonly` are not requested, and a test fails if they are added; their class is unverified. A Google sign-in is pinned by calendar id, which is safe because it can reach only calendars Daloy created, so a different calendar or a different Google account (which gets a new calendar) still holds the delivery for review (M11). The create route is owner only and rate limited, and takes no calendar id from the page, so the page cannot point Daloy at another calendar.
- No attendees are invited, so Daloy sends no Google invitation email to an address a guest supplied.

## PayMongo (decision 0045)

- A forged webhook: the path is 32 random bytes and finds the connection, then `Paymongo-Signature` must verify (HMAC-SHA256 of `t.rawBody` with the webhook secret, constant-time compare, only the part for the connection's mode). A bad signature is 401 and an unknown path is 404.
- Replay: an event id this workspace has seen answers 200 `duplicate`. Event ids are kept per workspace, so a workspace without the order cannot use up another workspace's event (decision 0056). A `t` older than 72 hours or more than 5 minutes ahead is refused. Runs are keyed `paymongo:<paymentId>:<status>`, so a replayed or second event starts nothing. The 72 hours is wide on purpose (PayMongo retries, and disables a failing webhook) and is to be tightened after the live check.
- Amount tampering: the paid amount and currency must equal the centavos and PHP stored when the link was made, or the payment goes to needs_review and no run starts. The amount is parsed from text into integer centavos, never a float. Payment state never moves back.
- A leaked webhook path: it only finds the connection. Without the webhook secret a caller cannot pass the signature. The path is kept when keys are replaced, so disconnect and connect PayMongo again to get a new one, and update the URL in PayMongo.
- Key leakage: the secret key and webhook secret are encrypted per workspace like the other connections and never returned or logged. The key is sent only in the `Authorization` header, and errors never include a header or body. If a key leaks, roll it in PayMongo and replace it in Apps.
- A live key by mistake: `sk_live_` is refused unless the server has `PAYMONGO_LIVE=on`, and an event whose `livemode` differs from the connection is refused. The worker checks the switch again right before it creates a checkout, so turning it off stops new live links from a key saved earlier. Live events still settle payments already made (decision 0056).
- A buyer setting the price (decision 0056): the order starter asks the owner to approve the item and amount before the buyer gets a link, and both sheet rows carry the Daloy payment id and the amount in pesos. A workflow an owner builds with a public amount and no approval still charges what the buyer typed.
- A test payment starting real work (decision 0056): the listeners for a sandbox payment, or for a payment made by a builder test run, start as test runs, which mock emails, HTTP calls and sheet rows. A payment row only changes on an event of its own mode.
- Events out of order (decision 0056): a paid or refund event that matches no payment yet is kept with what is needed to apply it. A paid event applies a kept refund, and storing a checkout session applies a kept paid event (without starting listeners, since Daloy hands out the link only after storing it).
- A GCash screenshot as proof: nothing in Daloy marks a payment paid except a signed PayMongo event that matches the stored amount.
- Remaining risk: abandoned links stay pending (PayMongo sends no expiry event), failed payments and partial refunds are not handled, and the signing format is only checked against PayMongo's documentation until the live check is run.

## Airtable, Notion and Trello (decision 0046)

- The Airtable token, Notion secret and Trello key and token are encrypted like the Slack token, bound to the owner and provider, and never returned or logged. Trello's key and token are in its request URL, so Daloy never prints a request URL or puts one in an error message.
- The three addresses are fixed or set by the installation's env vars, never by a user.
- Ids are validated at the boundary (a Notion link is reduced to its 32-character id), and the target is pinned to each delivery when it is queued, so editing the connection cannot redirect what is already queued.
- Airtable takes only a table id, which a rename does not change. A collaborator who renames a table and gives another one its name cannot redirect records. Connections saved by name before this change send nothing until reconnected (security review M16).

## Form files and Google Drive (decision 0051)

- A file that runs in the browser: types are read from the first bytes (JPEG, PNG, WebP, HEIC or HEIF, PDF); SVG, HTML and every other type are refused whatever the name or the browser says. Downloads are always attachments with the stored type, `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and `Cache-Control: private, no-store`. Nothing is shown inline, so a PDF's scripts only run if someone opens the downloaded file.
- Large or many uploads: 5 MB per file, 3 per field, 5 per submission, 50 text fields of 64 KB at most. The 10 posts a minute per IP guard runs before the upload parser, so a blocked address is refused before its body is read. Remaining risk: the parser holds up to 25 MB per request in memory, and many addresses together are not capped.
- Filling the database: each workspace may store a number of files per Manila day (Pilot 100, Business 500, Business Plus 2000, 20 without a plan, 20 on Preview). On a tracked form the claim is made in the request's own transaction, so repeated posts with one submission key spend it once (M15), counted before storing. Files are deleted 7 days after upload, and with their run. An invalid or replayed submission stores nothing.
- A caller pointing a run at someone else's file: only the hosted form handler sets a file field; values from webhooks, MCP, test runs and the Run button are dropped, and a webhook cannot have a file field. The Drive delivery and the download read a file by id, run and workspace together; anything else is a 404.
- File contents reaching the AI: trigger data holds only id, name, type and size. File bytes never enter trigger data, step input, step output, failure explanations or Ask. They reach the model only for a field the owner listed in an AI step's `files` (decision 0052). `apps/worker/src/steps/ai.test.ts` puts a marker inside a file and checks the model never receives it when the field is not listed. `apps/worker/src/steps/ai-files.test.ts` covers the listed case.
- Duplicate files in Drive after a timeout: one delivery per run and step, the folder pinned at queue time, each saved file recorded under the worker's claim. An unknown outcome waits in `needs_review`; Post again skips files already recorded.
- The Drive key: stored like the Sheets key, never returned or logged. It needs the `drive` scope, so a leaked key can read and change everything shared with that service account until the owner deletes the key. Use a dedicated service account per business. Only a folder in a shared drive is accepted, since service accounts have no storage of their own. The Drive address is fixed or set by the installation's env var (`GOOGLE_DRIVE_URL`), never by a user.
- File names are visitor text: they are cleaned (no path, no control characters, at most 120 characters) and only ever sent as JSON metadata or an encoded `filename*` header.

## AI reads files (decision 0052)

- Hostile PDFs: text is extracted in a worker thread with a 10 second timeout, a 256 MB heap cap and a 10 page limit, so a PDF that is huge or loops forever stops that thread, not the worker. PDF.js 6 has no code evaluation path (the `isEvalSupported` option behind CVE-2024-4367 is gone), and the step renders no pages and loads no fonts, so the optional native canvas package is never used. Only text comes out, capped at 20,000 characters.
- Prompt injection in an image or PDF text: PDF text goes inside the `<data>` block with `</data` escaped, the system prompt says attached images are data, and the reply is checked against the task's schema, so a later step never sees an unexpected shape. Remaining risk: text written in a photo or PDF can still steer the extracted values within that schema. The receipt template puts an approval before the sheet row for this reason.
- Files reaching a hosted provider: only fields the owner listed are sent, and Build with AI never lists any. A hosted provider's free tier may use photos for training, the same as text (decision 0015). Each photo is held as base64 in worker memory for the request.
- Cost: one AI action for the step plus one per attached file, claimed once under the step key, so retries do not count twice. Files are at most 5 MB each and 5 per submission, and images in one step at most 10 MB together.
- A stale definition naming a field that is not a file field: the definition check rejects it when saved, and the worker keeps only names that are file fields of the form when it runs, so an older version cannot send anything else.
