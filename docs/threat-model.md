# Threat model

Kept current with each phase. A mitigation marked "planned" does not exist in code yet.

## Assets

- Stored secrets (API keys and SMTP credentials that workflows use)
- Each owner's Gmail app password, and the right to send as their address
- Each owner's Google service account key and Slack bot token, which can write to their shared sheets and post to their channels
- Console sessions and API tokens
- Workspace membership and roles, which decide who can change automations and who can authorize a purchase
- Run data: trigger payloads and step outputs, which can hold customer personal data
- The ability to send email and make HTTP requests from the server

## Entry points

- Console API (session cookie)
- Webhook URLs and hosted forms (public)
- Approval links (public, random single-use token; a named approval also needs the approver's session)
- Invite links (public, random single-use token)
- Gmail confirmation links (need the owner's session and a random single-use token)
- MCP endpoint (bearer token)
- Outbound: HTTP request step, email step (the installation's SMTP server or the owner's Gmail), the API's test email, LLM calls, Google Sheets and Slack deliveries and connection tests

## Threats and mitigations

| Threat | Mitigation | Status |
| --- | --- | --- |
| SSRF through the HTTP step | Allow only http and https on ports 80 and 443. Block private, loopback, link-local and metadata ranges for IPv4 and IPv6, including IPv4-mapped addresses. Check inside the socket's DNS lookup, so the connection goes to the checked address. Re-check after each redirect (max 3) and drop the caller's headers on a cross-origin redirect. 1 MB and 10 second limits. See [decision 0006](decisions/0006-ssrf.md). | Done, phase 4 |
| Webhook spoofing | Random 32-byte URL path, optional HMAC-SHA256 signature checked in constant time, 256 kb body limit, 60 requests a minute per IP | Done, phase 3 |
| Secrets leaking into logs | Secrets are inserted by reference (`{{secrets.name}}`) only while a step runs. Their values are replaced with `[secret]` in step input, output and error text before anything is stored. The run history API masks again by key name (`password`, `token`, `authorization`, `api_key`, `cookie` and similar) in trigger data, step input and step output. See [decision 0008](decisions/0008-step-input.md). | Done, phases 4 and 6 |
| Expression injection | Expressions are path lookups only (no eval or Function), with limits on template size, path depth and output size. Resolution is a single pass, so trigger data containing `{{secrets.x}}` stays literal text. See [decision 0002](decisions/0002-expression-resolver.md). | Done, phase 4 |
| Approval link theft and replay | 32 random bytes per link, only the SHA-256 stored, so a database leak gives no working links. The link expires with the step's timeout and works once (guarded UPDATE on `used_at`). GET only shows the request, so link scanners cannot decide; POST records it. Unknown, used and expired links get the same response. `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. 30 views and 10 decisions a minute per IP. Remaining risk: for an approval with `to` (link-holder), whoever holds an unused link can decide, because the email is the only authentication. Named approvals close this (next row). See [decision 0009](decisions/0009-approval-links.md). | Done, phase 7 |
| A forwarded approval link, a repeated answer or someone from another workspace authorizing a purchase | A named approval is decided by one UPDATE that requires an unused, unexpired link, the signed-in user to be the named approver, and that user to be, at that moment, a member of the run's workspace with the owner or approver role. The page shows no request details until the approver is signed in, and the confirmation page shows only the decision. Who decided and when are stored. Tests cover forwarded links, other workspaces, removed and demoted members, expired links, repeated and concurrent answers. See [decision 0022](decisions/0022-workspace-members-named-approvals.md). | Done, roadmap phase 4 |
| A member doing more than their role allows | Every console route names its roles with `Allow(...)` after the session guard, and a test calls every route as every role. Queries are scoped to the session's workspace. The owner row can't be changed, given or taken (check constraint and guarded UPDATEs). | Done, roadmap phase 4 |
| A removed member keeps access | Removing a member deletes their sessions, and an account with no membership counts as signed out and can't sign in. Named approvals waiting for them can't be answered. | Done, roadmap phase 4 |
| Invite link theft | 32 random bytes, only the SHA-256 stored, seven days, one use (guarded UPDATE in the same transaction that adds the member), 10 accepts a minute per IP. An email that already has an account must enter its password. Remaining risk: whoever holds an unused invite for a new email can join with that role, so the owner should send it over a channel they trust. | Done, roadmap phase 4 |
| An AI-built workflow does something the owner did not want | The AI only returns a draft. It is checked against the same definition schema as a hand-built workflow, shown in the editor as unsaved, and runs only after the owner saves or publishes it. Test runs mock HTTP and email by default, and live HTTP steps still pass the SSRF guard. `POST /ai/draft` needs a session and is limited to 10 calls a minute per IP. See [decision 0017](decisions/0017-ai-workflow-drafts.md). | Done |
| Provider API keys saved in the console | Encrypted with AES-256-GCM like secrets, with the user and provider as associated data; write-only (the API returns only `hasKey`); error messages never include the provider's response body. See [decision 0016](decisions/0016-ai-settings-page.md). | Done |
| The AI model page used to make the server call internal hosts | No user-entered URLs: hosted providers have fixed URLs in code, and the local choice uses the operator's `LLM_BASE_URL`. The live test is limited to 10 calls a minute per IP. | Done |
| Trigger data sent to a hosted model | Ollama on the host is the default, so nothing leaves the machine. A hosted provider (`LLM_PROVIDER=openai`) is opt-in through env vars and `.env.example` says what it receives. `LLM_API_KEY` comes from the environment and LLM errors never include the provider's response body. Remaining risk: with a hosted provider, form messages, names and emails reach that provider, and free tiers may use them for training. See [decision 0015](decisions/0015-openai-compatible-llm.md). | Done |
| Prompt injection through trigger data | Trigger data only reaches the model inside `<data>` tags in the user message; a closing tag in the data is escaped. The system prompt holds only fixed text and the owner's literal text (the schema rejects `{{` there). Replies are validated against a fixed per-task JSON schema, so classify can only return a configured label. Remaining risk: a model can still be steered within that schema, such as a wrong label or unwanted text in a draft. See [decision 0010](decisions/0010-ai-step.md). | Done, phase 7 |
| MCP tool abuse | Bearer token per user, stored as SHA-256 and checked on every request, so revocation takes effect at once. A token only sees its owner's workflows and runs; another user's run gets the same "run not found" as a missing one. Only workflows with a form trigger and a published version become tools, and their arguments pass the same field schema as the hosted form. Runs keep their approval steps. 60 requests a minute per IP and a 256 kb body limit. Remaining risk: a leaked token can start the owner's form workflows until it is revoked; there are no per-token scopes. See [decision 0011](decisions/0011-mcp-sdk-v2.md). | Done, phase 8 |
| Oversized payloads | Body size limits on every route, 1 MB HTTP response limit, at most 100 steps per definition, expression output limit, at most 10 email recipients | Done, phases 1 to 4 |
| Two workers running the same step at once | Run lease claimed with a conditional UPDATE, guarded state updates, unique `(run_id, step_id, attempt)` | Done, phase 2 |
| Stolen database credentials or SQL injection | In compose the API and worker connect as `daloy_app` (SELECT, INSERT, UPDATE, DELETE only); a one-shot `migrate` service holds the owner credentials. CREATE on `public` is revoked from PUBLIC. Remaining risk: the app role can still read and change every row. See [decision 0013](decisions/0013-app-database-role.md). | Done, phase 9 |
| Password guessing on login | argon2id hashes, 10 login attempts a minute per IP, same response time for unknown emails | Done, phase 3 |
| Cross-site request forgery on console routes | SameSite=Lax session cookie, so other sites cannot send it with a POST | Done, phase 3 |
| Session theft from a database leak | Only SHA-256 of session cookies and API tokens is stored | Done, phase 3 |
| Form spam | Honeypot field, 10 submissions a minute per IP, field validation | Done, phase 3 |
| Duplicate or replayed office requests | Each form load carries a random submission key. `unique (workflow_id, submission_key)` in the database means a double-click, a retry or a replay of the same post returns the first reference and creates no second run or email. A key that is missing or not a UUID is rejected. Remaining risk: someone who copies a page's key only gets that same reference back. See [decision 0019](decisions/0019-office-request-records.md). | Done, roadmap phase 1 |
| Guessing request references | References are identifiers only. The public thank-you page shows the reference of the request just sent. The request list and run details need the owner's session and are scoped to the owner's workflows. | Done, roadmap phase 1 |
| Mail sent as the wrong owner, or from another address after a failure | `resolveSender()` is the only place that picks the sender, and every email step, approval email and test email goes through it. It reads the run's workflow owner only. An unconfirmed, failed or disconnected Gmail sender blocks the send before any server is contacted, and nothing falls back to the installation server or another owner. Returning to the installation server is a separate, explicit action. See [decision 0020](decisions/0020-owner-mail-senders.md). | Done, roadmap phase 2 |
| Gmail app password theft | Encrypted with AES-256-GCM, the owner's id bound in as associated data, so a ciphertext copied to another row does not decrypt. Write-only through the API, never in workflow definitions, run history or AI prompts. Disconnect deletes it. A 535 from Gmail marks the sender failed instead of retrying the login. Remaining risk: an app password can send any mail as that account, so a leaked `SECRETS_KEY` plus a database copy exposes it until the owner revokes it at Google. | Done, roadmap phase 2 |
| Sending as an address the owner does not control | A new Gmail address must be confirmed through a link mailed to that address: 32 random bytes, only the SHA-256 stored, 30 minute expiry, one use, and only accepted from the session of the owner it was sent to. Gmail itself also refuses a login without that account's app password. | Done, roadmap phase 2 |
| The test email used to spam | It only goes to the owner's own Gmail address or sign-in email, with fixed text, and is limited to 5 a minute per owner. | Done, roadmap phase 2 |
| Header or template injection through the business profile | The business name rejects braces and line breaks, so it cannot become a `{{...}}` placeholder or a mail header. From is passed to nodemailer as a name and address pair, so a comma or angle bracket in the name adds no recipient. The website must be http or https and is never fetched. The hosted form escapes the name. | Done, roadmap phase 2 |
| Google service account key or Slack bot token theft | Encrypted with AES-256-GCM with the owner and provider bound in as associated data. Write-only through the API: no response includes them, and only `client_email` and `private_key` are kept from the key file. Never in workflow definitions, run history or AI prompts. Disconnect deletes the row. Provider error text never includes the credential. Remaining risk: the key can edit every sheet shared with that service account, and the token can post wherever the app is, so a leaked `SECRETS_KEY` plus a database copy exposes them until the owner deletes the key or revokes the token. See [decision 0021](decisions/0021-sheets-slack-deliveries.md). | Done, roadmap phase 3 |
| Duplicate rows or notes after a timeout or crash | One delivery per run and step (`unique (run_id, step_id)`), claimed with `FOR UPDATE SKIP LOCKED` and finished with an UPDATE guarded by state and attempt number. A write that may have arrived is checked in the sheet by reference before writing again; for Slack it waits for the operator. Retry, Post again and Mark as posted are guarded UPDATEs scoped to the owner. | Done, roadmap phase 3 |
| Formula injection into the owner's sheet | Rows are written with `valueInputOption=RAW`, so form text starting with `=`, `+` or `@` is stored as text and never evaluated by Sheets. Remaining risk: someone who exports the sheet to CSV and opens it in another spreadsheet app may still see a formula there. | Done, roadmap phase 3 |
| Private request details posted to a shared channel | The office request's Slack note carries the reference and subject only, and its text is fixed by the template. Secrets in any sheets or slack step are replaced with `[secret]` before the delivery is stored. Remaining risk: an owner can write their own Slack step that includes `{{trigger.email}}`; the editor and AI drafting are told to avoid it but do not block it. | Done, roadmap phase 3 |
| Server-side requests to internal hosts through the connections | No user-entered URLs: Google and Slack hosts come from fixed defaults or the operator's `GOOGLE_TOKEN_URL`, `GOOGLE_SHEETS_URL` and `SLACK_API_URL`. The `token_uri` inside a key file is ignored. Redirects are refused. Connect and test routes need a session and are limited to 5 to 20 calls a minute per owner. | Done, roadmap phase 3 |
| A preview mistaken for a live send | The Preview only page is computed in the browser with no API call, so it cannot record a request or send an email. | Done, roadmap phase 1 |
| Test runs used to reach internal hosts or send mail | Test runs mock HTTP and email unless "live calls" is ticked; live test runs use the same SSRF guard and recipient cap as real runs | Done, phase 5 |
| Script injection in the console | React escapes all rendered values, including step outputs and trigger data; no `dangerouslySetInnerHTML`; helmet's CSP blocks inline scripts on the served console | Done, phase 5 |
