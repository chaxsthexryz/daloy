# Threat model

Kept current with each phase. A mitigation marked "planned" does not exist in code yet.

## Assets

- Stored secrets (API keys and SMTP credentials that workflows use)
- Each owner's Gmail app password or Google sign-in (`gmail.send` token blob, decision 0063), and the right to send as their address
- IMAP credentials, incoming message text and the saved position of each monitored folder
- Each owner's Google service account key and Slack bot token (pasted, or from Connect Slack), which can write to their shared sheets and post to their channels, and their Telegram bot token, which can message every chat the bot is in. The Google Calendar connection uses the same kind of service account key, which can change every event on the calendars shared with it
- Each owner's Microsoft access and refresh tokens, which can send email as their mailbox, and their Teams workflow link, which lets anyone holding it post to one channel
- OAuth consent flows in progress (the hash of a random state and an encrypted PKCE verifier, ten minutes) and every OAuth connection's token blob (decision 0058)
- The installation's Microsoft Entra client secret (`MICROSOFT_CLIENT_SECRET`)
- Console sessions and API tokens
- Workspace membership and roles, which decide who can change automations and who can authorize a purchase
- Run data: trigger payloads and step outputs, which can hold customer personal data
- Files visitors attach to forms (photos, IDs, receipts), kept 7 days in the database
- Receipt images on payment claims (kept the retention days after the due closes) and the text of customer DMs inside run data
- The ability to send email and make HTTP requests from the server
- The browser service (B2, decision 0108): a Chromium that runs any public page's scripts, and `BROWSER_TOKEN`, which lets a caller on the `browser` network run jobs

## Entry points

- Console API (session cookie)
- Platform admin API (`/admin/*`, session cookie of an account in `PLATFORM_ADMINS`; 404 for everyone else)
- Shopify order webhook (`POST /hooks/shopify/:path`, public, signed by Shopify)
- Telegram message webhook (`POST /hooks/telegram/:path`, public, checked by Telegram's secret token header)
- Webhook URLs and hosted forms, including anonymous embedded forms (public), and file uploads on those forms
- Customer privacy export and delete (`GET /privacy/customer`, `POST /privacy/customer/delete`, owner session)
- File downloads from run details (`GET /runs/:runId/files/:fileId`, owner and operator session)
- Owner mailbox setup and the worker's outbound IMAP connection
- Approval links (public, random single-use token; a named approval also needs the approver's session)
- Invite links (public, random single-use token)
- Gmail confirmation links (need the owner's session and a random single-use token)
- MCP endpoint (bearer token)
- Browser service API (`apps/browser`, bearer `BROWSER_TOKEN`, no published port, on the `browser` compose network with the worker only)
- Password reset links (public, random single-use token)
- Outbound: HTTP request step, email step (the installation's SMTP server, the owner's Gmail over SMTP, or the Gmail API), the API's test email, LLM calls, Google Sheets, Google Drive, Slack, Outlook, Teams and Shopify deliveries and connection tests, and the Shopify token request
- Inbound from OAuth providers: the shared consent callback, `GET /settings/connections/oauth/callback`, and Outlook's older address for it, `GET /settings/connections/outlook/callback` (no session needed to reach either; only Microsoft's administrator consent answer is handled without one)

## Threats and mitigations

| Threat | Mitigation | Status |
| --- | --- | --- |
| A site frames a signed-in console or attributes an inquiry to a visiting employee | Cross-origin framing is enabled only for the public form embed. Its submissions ignore cookies for requester attribution. The standalone form records a signed-in member as the requester only when `Origin` equals the `PUBLIC_URL` origin, so a sibling origin cannot post a tracked request as a member (M14). Standalone and embedded forms share field validation, the honeypot and the ten-post per-IP limit. | Implemented, N9 |
| Someone reads a mailbox password or directs the worker to an internal service | Only the workspace owner can manage a mailbox. Credentials are encrypted for the workspace and workflow, omitted from status responses, and cleared on disconnect. The worker checks all resolved addresses and connects to a checked public IP with TLS certificate verification against the entered host on port 993. Provider error text and authentication data stay out of logs. | Implemented, N9 |
| Replayed messages, a large attachment or a forged sender starts unintended work | The worker bounds each read and stores a run and mailbox checkpoint together. Obsolete polls lose their claim. It skips oversized mail, exposes plain text and leaves attachments in the mailbox. Sender and Reply-To headers are untrusted. A workflow that needs authorization must use a separate approval. One workspace's slow or failing mailboxes cannot delay another office's mail: live mailboxes go before drafts, workspaces take turns, one workspace holds at most one poller, and a failing mailbox backs off to one check an hour (security review M13, decision 0055). | Implemented, N9; fair turns N11c-3 |
| SSRF through the HTTP step | Allow only http and https on ports 80 and 443. Block private, loopback, link-local and metadata ranges for IPv4 and IPv6, including IPv4-mapped addresses. Check inside the socket's DNS lookup, so the connection goes to the checked address. Re-check after each redirect (max 3) and drop the caller's headers on a cross-origin redirect. A 307 or 308 to another origin fails instead of resending the body. 1 MB and 10 second limits. On a public demo `HTTP_ALLOWED_HOSTS` limits HTTP steps, and their redirects, to listed hosts. See [decision 0006](decisions/0006-ssrf.md). | Done, phase 4; allowlist N3 |
| Webhook spoofing | Random 32-byte URL path, optional HMAC-SHA256 signature checked in constant time, 256 kb body limit, 60 requests a minute per IP. A blank or missing signing secret name fails closed with 401, the definition schema requires a valid name, and publish checks the secret exists (M1) | Done, phase 3 |
| Replay of a captured signed webhook call | The signature covers a timestamp and the body, and calls more than 5 minutes from the server clock are refused. An identical replay inside the window returns the first run and starts nothing. A caller still on the old format (no timestamp) stays replayable until its owner ticks "Require the timestamp"; the last such call is recorded and shown in the editor, and the response carries a warning header. | Done, N11b (decision 0054). Remaining: old callers until their owner switches |
| A busy automation getting the owner's Gmail or Outlook suspended, or mailing far more people than intended | A per-workspace daily cap on recipients through Gmail and Outlook (`MAILBOX_DAILY_CAP`, default 400, Manila day), counted before sending with the step key. Over the cap the run waits in review with a plain reason; nothing is sent or dropped. Remaining: the watchdog's alert and the test email are not counted. | Done, N11b (decision 0054) |
| A paused automation still starting runs through a forgotten route | One check, in the transaction that inserts a run, under a share lock on the workflow row. Every insert of a live run calls it (`createRun`, the tracked request insert, a booking reschedule). Webhook, form, MCP, Run button, schedule, email-in and PayMongo are tested; builder test runs are exempt on purpose. A new route that inserts runs must call `assertNotPaused`. | Done, N11b (decision 0054) |
| Cancelling a run racing the worker, or an approval link confirming a cancelled run | Cancel is one guarded UPDATE from pending or waiting, so the worker's wake-up and the cancel have one winner. The waiting attempt closes as not sent and the run's open approval links expire. Cancel is for owners and operators of the workspace; another workspace gets 404. | Done, N11b (decision 0054) |
| Secrets leaking into logs | Secrets are inserted by reference (`{{secrets.name}}`) only while a step runs. The stored step input is a preview resolved with `[secret]` in place of each secret, so no encoding of a secret is stored through it; output and error text have every form of every value (raw, JSON-escaped, URL- and form-encoded) replaced before anything is stored. Every API and MCP read surface that returns stored payloads, request subjects, approval messages, delivery fields, or provider and mailbox errors applies `historyHider` (current secrets, `retired_secrets`, active OAuth tokens, then secret-looking keys), loading the hider before querying history rows so a concurrent purge cannot land between the two reads. See [decision 0008](decisions/0008-step-input.md), [decision 0025](decisions/0025-destination-aware-secrets.md), and [decision 0067](decisions/0067-retired-secrets-purge.md). | Done, phases 4 and 6; all readers N11c-3 and N11 |
| Rotated or deleted secrets kept indefinitely in `retired_secrets` | The worker's daily maintenance sweep runs `purgeRetiredSecrets` (default 90 days, configurable via `RETIRED_SECRETS_MAX_AGE_DAYS`). For each workspace, one transaction guarded by a per-workspace advisory lock skips workspaces with in-flight `running` runs or `sending` deliveries (retrying on a later sweep), scans history tables in bounded keyset batches (`LIMIT 200` by primary key), locks each row being scrubbed with `FOR UPDATE`, re-computes scrubbing of all four forms of expired retired secrets on the locked row, updates only the changed columns across `runs`, `step_runs`, `deliveries`, `requests`, `connections`, `email_sources`, `mail_senders`, `calendar_events`, and `payments`, re-checks for active work, and deletes only those exact `retired_secrets` ids. Undecryptable rows are skipped without deletion, and a mid-transaction error rolls back atomically. See [decision 0067](decisions/0067-retired-secrets-purge.md). | Done, N11 (decision 0067) |
| Expression injection | Expressions are path lookups only (no eval or Function), with limits on template size, path depth and output size. Resolution is a single pass, so trigger data containing `{{secrets.x}}` stays literal text. See [decision 0002](decisions/0002-expression-resolver.md). | Done, phase 4 |
| Approval link theft and replay | 32 random bytes per link, only the SHA-256 stored, so a database leak gives no working links. The link expires with the step's timeout and works once (guarded UPDATE on `used_at`). GET only shows the request, so link scanners cannot decide; POST records it. Unknown, used and expired links get the same response. `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. 30 views and 10 decisions a minute per IP. Remaining risk: for an approval with `to` (link-holder), whoever holds an unused link can decide, because the email is the only authentication. Named approvals close this (next row). See [decision 0009](decisions/0009-approval-links.md). | Done, phase 7 |
| A forwarded approval link, a repeated answer or someone from another workspace authorizing a purchase | A named approval is decided by one UPDATE that requires an unused, unexpired link, the signed-in user to be the named approver, and that user to be, at that moment, a member of the run's workspace with the owner or approver role. The page shows no request details until the approver is signed in, and the confirmation page shows only the decision. Who decided and when are stored. Tests cover forwarded links, other workspaces, removed and demoted members, expired links, repeated and concurrent answers. See [decision 0022](decisions/0022-workspace-members-named-approvals.md). | Done, roadmap phase 4 |
| A form, webhook or MCP caller naming another workspace's resource, an archived one, or a time the business does not offer | `parsePayload` accepts a resource id only from the active resources of the workflow's own workspace, loaded at every entry point (hosted form, webhooks, test runs, the Run button, MCP); a name or a foreign id is a 400 that reveals nothing about other workspaces. The name stored with the id is read from the database, never from the caller. Times are checked on the server whatever the browser sends: real date and time, in the field's IANA zone, not in a DST gap, not ambiguous without an offset, in the future and on the slot grid. Only owners add, rename or archive resources; resource names are shown on the public form by design. See [decision 0031](decisions/0031-zoned-times-and-resources.md). | Done, P6a |
| Double booking a resource, or a retried request moving a booking twice | A Postgres exclusion constraint refuses overlapping active bookings per workspace, test scope and resource, whatever the path. A booking step stores its result with its change, so a retry returns it. Staff and MCP changes carry the version they saw; each version changes once (primary key on the change log), and a repeat of the same change gets the first answer. See [decision 0032](decisions/0032-booking-lifecycle.md). | Done, P6b |
| A public form or an unsigned call cancelling or moving someone's booking | Saving refuses reschedule and cancel steps unless the trigger is manual (the owner's Run button) or a webhook with a signing secret, whose calls are checked in constant time. Staff changes need the owner or operator role and are scoped to the workspace; MCP needs the owner's token. Bookings of other workspaces answer 404. | Done, P6b |
| A reminder or follow-up sent for a booking that was moved or cancelled | Runs are linked to a booking version and stop before any attempt of an older version, including retries, resumed waits and operator recovery. Emails and unsafe HTTP calls check again under a lock held until the send starts. Sheets, Slack, Outlook and Teams deliveries check the run's booking under a lock held until the provider answers, and Retry and Post again refuse them once the booking moved on. Remaining risk: idempotent HTTP calls can still go out if the change lands between the check and that send; a change during an open send waits for it. | Done, P6b and N2b |
| Test bookings blocking or leaking into live ones | `test` is part of the constraint and of every lookup; test references start with `TEST-`; staff lists and MCP show live bookings only. | Done, P6b |
| A logo upload carrying script, or a page or email loading something from another site | The logo is accepted only as PNG, JPEG or WebP by its first bytes, at most 100 KB, from a signed-in owner. SVG and every other type are refused. It is served from the API with a fixed image type, `nosniff` and no cookies needed. Pages and emails reference it on their own origin or as an inline attachment, and the accent colour is checked as `#rrggbb` before it reaches CSS. See [decision 0050](decisions/0050-brand-kit.md). | Done, N18 |
| A member doing more than their role allows | Every console route names its roles with `Allow(...)` after the session guard, and a test calls every route as every role. Queries are scoped to the session's workspace. The owner row can't be changed, given or taken (check constraint and guarded UPDATEs). The matrix covers every session route, signed out included, and a completeness test fails when a route is registered without a row or a place on the short list of routes with their own rules. A two-workspace test calls every id-addressed object from another workspace. | Done, roadmap phase 4 and N11d |
| A removed member keeps access | Removing a member deletes their sessions, and an account with no membership counts as signed out and can't sign in. Named approvals waiting for them can't be answered. | Done, roadmap phase 4 |
| Invite link theft | 32 random bytes, only the SHA-256 stored, seven days, one use (guarded UPDATE in the same transaction that adds the member), 10 accepts a minute per IP. An email that already has an account must enter its password. Remaining risk: whoever holds an unused invite for a new email can join with that role, so the owner should send it over a channel they trust. | Done, roadmap phase 4 |
| An AI-built workflow does something the owner did not want | The AI only returns a draft, checked against the same definition schema as a hand-built workflow. A draft the checker finds nothing to fix is then created and turned on in one step (decision 0048), because the owner asked for a chat that deploys what it builds; the owner lands in the editor with it on and can turn it off there. A draft with lint warnings, or one whose publish is refused (an app it needs is not connected), is not saved until the owner presses Turn it on or Save as draft. Remaining risk: a clean-looking draft that does something the owner did not intend starts running as soon as it exists. Test runs mock HTTP and email by default, and live HTTP steps still pass the SSRF guard. `POST /ai/draft` needs a session and is limited to 10 calls a minute per IP. A draft is also linted for silent approvals, unrouted classify labels, test switches and unguarded number gates, and the editor lists the warnings (advice only, not a security boundary; the messages hold only step ids, field names and labels, so the repair round adds no free text to the prompt). See [decision 0017](decisions/0017-ai-workflow-drafts.md) and [decision 0033](decisions/0033-draft-lint.md). | Done |
| Private data reaches the model through Build with AI (N4f) | The tab sends the conversation as typed, the current draft when there is one and the connected app kinds (a fixed list, never typed text), nothing else: no form submissions, run data, booking details, secrets, business profile or team addresses. People are labels (`owner@people.invalid`, `member1@people.invalid`); the page puts the real address into the draft after it returns and takes it out again before the next message. `apps/api/src/ai-draft.test.ts` records the request the fake model receives in a workspace holding a member, a profile, a secret and a submission and asserts none appears, and `e2e/build-with-ai.spec.ts` asserts the same on the browser's request body. Nothing is saved until Save as draft, so a draft the owner dislikes leaves no record. Remaining risk: what the owner types is sent as written (the page says so), a model may ignore the labels and invent an address (the review lists every address and the owner reads it before saving), and the editor's "Ask the AI" still sends the open draft with its real addresses, as before; moving it to labels is a follow-up. | Done, N4f |
| API token or secret value lingering in the browser (W8, W9) | A new API token is returned once, kept only in page state and removed on reload or when the next token is made; `GET /tokens` and `GET /secrets` never return a value. The secret value field is a `new-password` input and is cleared after every save, successful or not. Delete and revoke use a dialog that names the item. `e2e/workspace-tokens.spec.ts` and `e2e/workspace-secrets.spec.ts` assert a synthetic value is absent from the page HTML and from the API list after saving. Remaining risk: the token stays on screen until reload, and the clipboard keeps it until overwritten. See [decision 0073](decisions/0073-advanced-pages.md). | Done, W8 and W9 |
| Provider API keys saved in the console | Encrypted with AES-256-GCM like secrets, with the user and provider as associated data; write-only (the API returns only `hasKey`); error messages never include the provider's response body. See [decision 0016](decisions/0016-ai-settings-page.md). | Done |
| Private data reaches the model through failure explanations (N10a) | The model gets only `{ facts, fixed }`: closed-set fields built by `failureFacts` (run state, preview flag, step type, outcome, attempts, dead-letter flag, an HTTP status code, a reason from a fixed list, each failed delivery's app, state and error kind, lint rule ids with counts) and Daloy's own fixed text. Error text, step ids, labels, URLs, hosts, addresses, form values and booking fields never leave that function. `apps/api/src/explain-api.test.ts` seeds a run holding a name, an address, booking text, a host with a token in its query string and a step id, records the fake model's request and asserts none appears and the message has exactly those keys. The reply is plain text, at most 600 characters, refused when it holds a link, shown as text under "Written by the AI model", never stored; the route writes no run, step or delivery row (tested by comparing rows before and after). Only owners can ask, 10 a minute, each ask one AI action under the plan. Remaining risk: the model can still word the facts wrongly; the fixed text stays above it. See [decision 0039](decisions/0039-failure-explanations.md). | Done, N10a |
| Private data reaches the model, or an answer changes a run, through Ask about a request (N10b) | Off unless the installation sets `AI_ASK=on`. The owner picks a reference and one of three fixed questions; nothing typed reaches the model. The answers are fixed text from closed-set fields. The reword sends only `{ question, language, facts, fixed }`: N10a's facts plus the plain state and a timeline of step type, state, outcome and attempts. `apps/api/src/ask-api.test.ts` seeds a run whose payload, step input and output, error and request subject hold an email, a name, a booking time, a workspace secret and a URL with a token in its query string, records the fake model's request and asserts none of them, nor the reference, ids, workflow name or labels, appears, and that the keys are exactly the allowlist. Answers are read-only: `GET` for the fixed answers, the reword writes only the usage count (tested by comparing run, step and delivery rows before and after), and the card has links only. A reference from another workspace is a 404 like an unknown one; approvers and requesters get 403; only owners reword, 10 a minute, one AI action each. Remaining risk: the model can word the facts wrongly, so it stays off until the twenty-request check in [ai-ask-measurement.md](ai-ask-measurement.md). See [decision 0041](decisions/0041-ask-about-a-request.md). | Done, N10b (off by default) |
| The AI model page used to make the server call internal hosts | No user-entered URLs: hosted providers have fixed URLs in code, and the local choice uses the operator's `LLM_BASE_URL`. Reading the provider's model list (`POST /settings/ai/models`, also on save) sends the key to that same fixed URL and nowhere else. The live test and the list are each limited to 10 calls a minute per IP. | Done |
| A model host redirecting a prompt or a key to another origin | Both LLM calls (`generate`, `listModels`) use `redirect: "error"`, so a 3xx from the configured host fails the call and sends nothing on. Tested with a local host that redirects to a second server. | Done, N11d |
| Trello key and token in logs | Trello puts both in the query string. Daloy's own errors, delivery failures and console messages never carry the URL or query (`provider-errors.test.ts`). Remaining risk: the operator's reverse proxy and any outbound proxy must not log query strings (docs/deployment.md section 8). | Done in the app, operator check |
| Trigger data sent to a hosted model | Ollama on the host is the default, so nothing leaves the machine. Photos and PDF text reach a hosted model only for file fields an AI step lists (decision 0052). A hosted provider (`LLM_PROVIDER=openai`) is opt-in through env vars and `.env.example` says what it receives. `LLM_API_KEY` comes from the environment and is only sent for accounts when `SHARED_LLM_KEY=open` (off by default, decision 0035) and the workspace has a plan (decision 0038), so strangers on a public installation cannot spend the operator's quota. LLM errors never include the provider's response body. Remaining risk: with a hosted provider, form messages, names and emails reach that provider, and free tiers may use them for training. See [decision 0015](decisions/0015-openai-compatible-llm.md). | Done |
| Prompt injection through trigger data | Trigger data only reaches the model inside `<data>` tags in the user message; a closing tag in the data is escaped. The system prompt holds only fixed text and the owner's literal text (the schema rejects `{{` there). Replies are validated against a fixed per-task JSON schema, so classify can only return a configured label. Remaining risk: a model can still be steered within that schema, such as a wrong label or unwanted text in a draft. See [decision 0010](decisions/0010-ai-step.md). | Done, phase 7 |
| MCP tool abuse | Bearer token per user, stored as SHA-256 and checked on every request, so revocation takes effect at once. A token only sees its owner's workflows and runs; another user's run gets the same "run not found" as a missing one. Only workflows with a form trigger and a published version become tools, and their arguments pass the same field schema as the hosted form. Runs keep their approval steps. 60 requests a minute per IP and a 256 kb body limit. Remaining risk: a leaked token can do what its scopes allow until it expires or is revoked, see the token scopes row. See [decision 0011](decisions/0011-mcp-sdk-v2.md). | Done, phase 8 |
| A session surviving a password change | Changing the password needs the current one, keeps only the session that asked, deletes the account's other sessions and marks open reset links used. A wrong current password is a 400, and the route allows 10 a minute per user. Remaining risk: API tokens are not revoked, because they belong to the workspace; the owner revokes them on the tokens page. | Done, N11a |
| Reset link theft and replay | 32 random bytes, only the SHA-256 stored, valid 30 minutes, used once through a guarded UPDATE. Using a link or changing the password retires the account's other open links, and success deletes every session. Unknown, used and expired links give the same 400. The link is in the URL fragment, so it is not sent to the server in request lines or Referer. Remaining risk: whoever controls the mailbox controls the account, and sign-up emails are not verified, so a reset goes to whatever address registered. See [decision 0053](decisions/0053-accounts-and-token-scopes.md). | Done, N11a |
| Finding which emails have accounts through password reset | The request always answers 202 `{ ok: true }`, and the lookup and mail run after the response, so neither the body nor the timing differs. | Done, N11a |
| Mail flooding one address through password reset | 5 requests per 15 minutes per IP (the in-memory `RateLimit`) and at most 3 links per account per hour, counted in Postgres under a row lock so it holds across processes. Over the cap the answer is the same and no mail is sent. Remaining risk: the per-IP counters are per process, and an SMTP failure is only logged, so the requester cannot tell. | Done, N11a |
| A leaked API token doing more than it needs to, or lasting forever | A token has scopes (`read`, `run`, `manage`) and an optional expiry of 1 to 365 days. Tools outside the scopes are not registered for that request, so they are absent from `tools/list` and a call is an unknown tool. Expired tokens get 401 like revoked ones. Remaining risk: tokens made before N11a keep full access with no expiry so live tokens keep working; the owner can revoke and replace them. | Done, N11a |
| Many large uploads exhausting the API's memory | multer buffers a file in memory, and per-file and per-IP limits do not bound the total. A guard before the parser reserves each multipart post's declared length from a shared 128 MB budget (503 with `Retry-After` when full), refuses a post with no length (411) or above one submission's maximum (413), and checks the form exists and takes files (404, 415) before any body is read. Remaining risk: the budget is per process, and slow clients hold their reservation until they finish. See [decision 0078](decisions/0078-pre-release-checklist.md). | Done, N11d |
| Oversized payloads | Body size limits on every route, 1 MB HTTP response limit, at most 100 steps per definition, expression output limit, at most 10 email recipients | Done, phases 1 to 4 |
| Two workers running the same step at once | Run lease claimed with a conditional UPDATE, guarded state updates, unique `(run_id, step_id, attempt)`. Each attempt has a random `claim_id`; a worker writes its result only under its own claim, so one that lost its lease mid-send cannot overwrite the worker that took over or an operator's answer (decision 0030) | Done, phase 2, P5 |
| Duplicate orders or emails after a lost answer, a 5xx or a crash | Failures are classified as not_sent, rejected, throttled or unknown. An unknown outcome on a POST, PATCH or email is never resent on its own: the run waits in `needs_review` for It went through, Send again or Stop. `not_sent` is claimed only when no socket opened for request bytes (connect, or the TLS handshake for https); the request's `finish` event is not trusted. Right before an unsafe send the worker writes `dispatched_at` under its claim and holds a row lock until the request is on its way, again before every redirect hop; a worker that takes over an attempt with the mark parks it instead of resending, and a stale worker whose claim was taken sends nothing. A non-idempotent request answered with a redirect is never resent, whatever the follow-up does, and an error status is classified before its body is read. The `Idempotency-Key` is the same on every attempt and treated as a hint only. Each operator action is one guarded UPDATE. Remaining risk: a step wrongly flagged `idempotent: true` is retried after a 5xx; a 429 with a long `Retry-After` dead-letters and needs a person | Done, P5 |
| Stolen database credentials or SQL injection | In compose the API and worker connect as `daloy_app` (SELECT, INSERT, UPDATE, DELETE only); a one-shot `migrate` service holds the owner credentials. CREATE on `public` is revoked from PUBLIC. Remaining risk: the app role can still read and change every row. See [decision 0013](decisions/0013-app-database-role.md). | Done, phase 9 |
| Password guessing on login | argon2id hashes, 10 login attempts a minute per IP, same response time for unknown emails | Done, phase 3 |
| Rate limits bypassed or shared behind a proxy | `TRUST_PROXY` is a hop count, so `req.ip` is the address the nearest trusted proxy saw and a client's own `X-Forwarded-For` entries are ignored. Sign-up is limited per IP per hour. Remaining risk: if port 3000 is reachable without passing the proxy, a client can write its own `X-Forwarded-For` and pick a bucket; compose binds it to 127.0.0.1 for that reason. Counters are per API process. See [decision 0035](decisions/0035-deployment-settings.md). | Done, N3 |
| Session cookie sent over plain HTTP | `SECURE_COOKIES=true` (or `NODE_ENV=production`) marks it Secure; docs/deployment.md sets it. An unreadable value stops the boot. | Done, N3 |
| Default database passwords | Compose refuses to start without `POSTGRES_PASSWORD` and `APP_DB_PASSWORD`; `.env.example` has none filled in. | Done, N3 |
| Backups read off the machine | Dumps are copied through an rclone `crypt` remote, so Google Drive holds only ciphertext. `SECRETS_KEY`, the database passwords and the crypt password are stored apart from the dumps. The Google account is the remaining trust boundary: its loss deletes or exposes ciphertext only. | Documented, N3; not yet run on the target |
| Cross-site request forgery on console routes | SameSite=Lax session cookie, so other sites cannot send it with a POST. A sibling origin of the same site still can, and the API reads urlencoded bodies, so `SessionGuard` also refuses a POST, PUT, PATCH or DELETE whose `Origin` is neither the `PUBLIC_URL` origin nor the host the request was sent to ([decision 0078](decisions/0078-pre-release-checklist.md)). ## Residual risks from the public intake review (decision 0057)

- The Appointment reminder and Renewal reminders starters still email submitted text (`{{trigger.service}}`, `{{trigger.item}}`) to the address typed on their forms. They are meant for staff entry, but the form URLs are public.
- A custom workflow that books straight from a public form still reserves slots. Only the Lead to booking starter has an approval step.
- Workflows already built from the old starters keep the old wording and the old booking flow until the owner edits them.
- Requester attribution needs the browser's `Origin` header to reach the API and `PUBLIC_URL` to match the address people use. A proxy that drops or rewrites `Origin` makes every tracked request anonymous.

## Public pages (Doop rows E7 to E11, decisions 0079 and 0080)

- Reflected input on the re-rendered form: the visitor's answers and the error messages are HTML escaped before they go back into the page, and the form is returned only for a 400 or 429, so no other status carries input. `public-form-pages.test.ts` posts `<tables>` and checks it comes back as text.
- CSS injection through the brand colour: the accent and ink are written into the stylesheet only if they match `#rrggbb`, whatever the database holds (`safeColour`, `public-pages.test.ts`).
- Availability probing: `GET /forms/:id/slots` is limited to 60 calls a minute per IP, answers 404 for a resource that does not belong to the form's workspace or an inactive one, rejects a bad date or id with 400, and returns only start times and a taken flag. It reveals when a resource is busy (the booking form shows this on purpose) and nothing about who booked. The date range is not capped, so a scraper can read a year of busy times; this is the same information the form shows a visitor.
- Another workspace's brand on an approval: the brand is read with the approval's own workspace id. An unknown link has no workspace and shows the Daloy page. `approvals-brand.test.ts`.
- Scripts on public pages: the pages have no inline script. The booking form loads `/public/slots.js` from the API origin, so `script-src 'self'` stays. The embed route keeps the framing allowance and the plain form keeps `X-Frame-Options`.
- Taken-time notice for browsers only: it does not stop a double booking, which the booking step's exclusion constraint does.

## First-time onboarding (R1, decisions 0082 to 0084)

- Entry point: `/onboarding` (owner session only, `Allow(MANAGE)`). Operators, approvers and requesters get 403, and no session gets 401 (`onboarding.test.ts`).
- Input: every screen is validated with zod at the boundary (`identityInput`, `typeInput`, `workflowInput`). The name refuses braces and line breaks (they would become template placeholders or mail headers), the website must be http or https, categories are a fixed list of at most three that differ from the primary one, and unknown keys are refused.
- Order and races: a screen saves only after the one before it, and the finish route locks the owner's progress row, so concurrent finishes make one draft. Three simultaneous finishes are tested.
- Isolation: every query filters on the session's workspace id. The draft is created for that workspace only, and the placeholder reviewer address is replaced with the owner's own sign-in address, never a value from the request.
- Side effects: onboarding connects no app, publishes nothing, sends no message and sends no invitation. The draft is an unpublished version, and the API test checks it has no live version and no run.
- Logo: reuses `PUT /settings/brand/logo` (PNG, JPEG or WebP by file signature, at most 100 KB, SVG refused).

## Telegram (decision 0042)

- The bot token is encrypted like the Slack token, bound to the owner and provider, and never returned by the API or written to logs. It is part of the Telegram request URL, so Daloy never prints a request URL or puts one in an error message.
- The Telegram address is fixed (`api.telegram.org`) or set by the installation's env var, never by a user, so a user cannot point Daloy at an internal host.
- The chat id is validated (a number or `@name`), and the chat is pinned to each delivery when it is queued, so editing the connection cannot redirect messages already queued.
- Anyone in the chat can read what is sent. The same rule as Slack: keep private details out of the message text.
- Chat discovery (guided setup): `POST /settings/connections/telegram/chats` takes a pasted token, calls `getMe` and `getUpdates`, and returns the bot name and up to 20 recently seen chats (id, type, title). Titles can be personal: a private chat's title is the person's name. They go only to the signed-in owner who pasted the token, are not stored or logged, and message text and sender details are never read into the answer. The route is owner only and limited to 10 calls a minute. `getUpdates` is called without an offset, so it does not remove updates the bot has not processed. Anyone who holds the token can already read the same updates from Telegram, so the route adds no new reach. Unverified against the live Bot API.
- A bot token that leaks lets someone message the bot's chats. Replace it in BotFather (/revoke), then Replace token in Apps.

## UniSMS Philippine SMS (decisions 0074 and 0100)

- UniSMS is the operator's account only (decision 0100): the Secret Key and Sender ID come from the server env (`UNISMS_SECRET_KEY`, `UNISMS_SENDER_ID`), so a workspace no longer holds a UniSMS secret and there is one customer secret fewer to protect. The routes that saved and tested a workspace key are removed (404). A key stored by an older version is never decrypted into a send; the worker retires it into `retired_secrets` at start, where read-side redaction (`secretValuesToHide`) keeps hiding it until the daily purge scrubs it. The key and its Base64 Basic Auth header are scrubbed from provider error text before anything is stored or returned, and the operator's upstream error text is not shown on a 400.
- The UniSMS API base URL is fixed (`https://unismsapi.com`) or set only by server env (`UNISMS_API_URL`) for local tests, with `redirect: "error"` and a 10-second timeout, preventing SSRF and credential forwarding on redirects.
- Monthly `sms` quotas (`preview: 0`, `pilot: 50`, `business: 300`, `business_plus: 1500`) are enforced atomically in Postgres before sending, keyed per delivery so retries never double-bill. Because every workspace now spends the operator's credits, a preview workspace is refused before the call, and a workflow step cannot change the Sender ID (it is the operator's). A workspace with no plan (`plan: null`) is unlimited, which is the private install case: on a public server where every workspace has a plan, the quota is the only cap on operator spend.
- Recipient numbers are restricted to valid Philippine mobile numbers (`+639XXXXXXXXX`) and messages to 670 rendered characters, blocking international SMS toll fraud and oversized multi-part message abuse.
- Unknown send outcomes (timeouts, dropped connections, 5xx, stale worker takeover) park in `needs_review` instead of retrying automatically, preventing duplicate paid SMS sends. Cancelled or rescheduled bookings stop queued SMS deliveries under the booking share lock before quota is claimed or UniSMS is called.
- `DELETE /settings/connections/unisms` stays only to clear a row an older version left behind. It is owner-only and rate limited. Publishing a workflow with an SMS step needs the server env, so nothing is queued that can never send.

## Google Calendar (decision 0044)

- The service account key is stored encrypted like Sheets, bound to the owner and provider, and never returned or logged. The scope is `calendar.events`. The account sees only calendars their owner shared with it, so a leaked key can read and change those calendars' events, nothing else.
- The Calendar address is fixed or set by the installation's env var (`GOOGLE_CALENDAR_URL`), never by a user.
- The calendar id is validated, and the calendar is pinned to each delivery when it is queued, so editing the connection cannot redirect a queued event. A changed calendar holds the delivery for review.
- An event is bound to the account and calendar it was last written to. A reschedule or cancel after the owner switched calendars goes to that same calendar or stops in review, so guest details are never copied to a calendar with a different audience without the owner choosing Post again (security review M11).
- Writes for one booking are ordered by the booking row lock, so an older update cannot restore an event after a cancel (M12). Error text stored for a delivery is Daloy's own, never Google's wording (M9).
- Event ids come from the booking id through sha256, so an id gives away nothing and a caller cannot choose another booking's event. A delivery reads the booking by id and workspace.
- Event title and description are text from the workflow's templates and can hold guest details. Anyone with access to the calendar sees them: share the calendar only with the people who may see bookings.
- Connect with Google (decision 0064): the grant has `calendar.app.created` only, so a leaked token can read and change events on the calendar Daloy created and cannot see the owner's other calendars. The access and refresh tokens are one encrypted blob like every OAuth connection, are never returned or logged, and are hidden from history, Activity, CSV and the delivery list by the same hider. `calendar.events` and `calendar.calendarlist.readonly` are not requested, and a test fails if they are added; their class is unverified. A Google sign-in is pinned by calendar id, which is safe because it can reach only calendars Daloy created, so a different calendar or a different Google account (which gets a new calendar) still holds the delivery for review (M11). The create route is owner only and rate limited, and takes no calendar id from the page, so the page cannot point Daloy at another calendar.
- No attendees are invited, so Daloy sends no Google invitation email to an address a guest supplied.

## PayMongo (decision 0045)

- A forged webhook: the path is 32 random bytes and finds the connection, then `Paymongo-Signature` must verify (HMAC-SHA256 of `t.rawBody` with the webhook secret, constant-time compare, only the part for the connection's mode). A bad signature is 401 and an unknown path is 404.
- Key saved before the webhook secret (guided setup): the webhook address only exists after the key is saved, so a connection can briefly have no secret. The hook then answers 401 to every event, because an empty secret is never accepted as a key. The card says the secret is missing until it is saved (decision 0059).
- Replay: an event id this workspace has seen answers 200 `duplicate`. Event ids are kept per workspace, so a workspace without the order cannot use up another workspace's event (decision 0056). A `t` older than 72 hours or more than 5 minutes ahead is refused. Runs are keyed `paymongo:<paymentId>:<status>`, so a replayed or second event starts nothing. The 72 hours is wide on purpose (PayMongo retries, and disables a failing webhook) and is to be tightened after the live check.
- Amount tampering: the paid amount and currency must equal the centavos and PHP stored when the link was made, or the payment goes to needs_review and no run starts. The amount is parsed from text into integer centavos, never a float. Payment state never moves back.
- A leaked webhook path: it only finds the connection. Without the webhook secret a caller cannot pass the signature. The path is kept when keys are replaced, so disconnect and connect PayMongo again to get a new one, and update the URL in PayMongo.
- Key leakage: the secret key and webhook secret are encrypted per workspace like the other connections and never returned or logged. The key is sent only in the `Authorization` header, and errors never include a header or body. If a key leaks, roll it in PayMongo and replace it in Apps.
- A live key by mistake: `sk_live_` is refused unless the server has `PAYMONGO_LIVE=on`, and an event whose `livemode` differs from the connection is refused. The worker checks the switch again right before it creates a checkout, so turning it off stops new live links from a key saved earlier. Live events still settle payments already made (decision 0056).
- A buyer setting the price (decision 0056): the order starter asks the owner to approve the item and amount before the buyer gets a link, and both sheet rows carry the Daloy payment id and the amount in pesos. A workflow an owner builds with a public amount and no approval still charges what the buyer typed.
- A test payment starting real work (decision 0056): the listeners for a sandbox payment, or for a payment made by a builder test run, start as test runs, which mock emails, HTTP calls and sheet rows. A payment row only changes on an event of its own mode.
- Events out of order (decision 0056): a paid or refund event that matches no payment yet is kept with what is needed to apply it. A paid event applies a kept refund, and storing a checkout session applies a kept paid event (without starting listeners, since Daloy hands out the link only after storing it).
- A GCash screenshot as proof: nothing in Daloy marks a payment paid except a signed PayMongo event that matches the stored amount.
- Remaining risk: a link made by `paymongo_link` stays pending when abandoned (PayMongo sends no expiry event; a `payment_due` checkout is expired by its deadline step, decision 0089), partial refunds are not handled, and the signing format is only checked against PayMongo's documentation until the live check is run.

## Payment review and the pay page (R3, decisions 0088 to 0091)

Assets: the confirmed state of an order, the seller's payment details (where customers send money), receipt images, the customer's mobile number.

Entry points: `GET` and `POST /pay/<token>`, `GET /pay/<token>/qr`, the PayMongo webhook, and the staff routes under `/payments`.

- A screenshot or an edited receipt: a claim never confirms. Only a reviewer's decision or a verified PayMongo event that matches workspace, checkout, order reference, currency and amount does. Reused references are flagged across the workspace, including references the Messenger receipt check saw.
- Guessing another order's page: the token is 32 random bytes, so the order reference alone opens nothing. Malformed tokens are refused before any query.
- Spam and oversized uploads: 10 posts a minute per IP and the shared multipart byte budget, both checked before multer reads the body, with an unknown link refused first; one file of at most 5 MB, a honeypot, zod on every field, and the daily `upload` quota for images, charged inside the claim transaction after the repeat check, so a repeated reference or an unreadable file costs nothing. A file that is not JPEG, PNG, WebP or HEIC by its bytes is flagged and not stored. One order can have at most 5 references waiting for the seller (review of 22 November, M1 and M2, decision 0102).
- A buyer choosing the price: a `payment_due` amount or total cannot read `{{trigger.*}}` unless the trigger is manual, a schedule, a payment or a signed webhook (review of 22 November, M4, decision 0102). A price taken from a step output is not traced.
- Seeing receipts: images are served only to owners and operators of the claim's workspace, with `nosniff`, a `sandbox` CSP and `no-store`. Approvers, requesters, other workspaces and the customer get 403, 404 or 401. Decisions and the review list have the same rule.
- Redirecting payments: only the owner may change the GCash number, account name or QR image. The QR upload must be a JPEG, PNG or WebP of at most 1 MB by its bytes. The checkout link on the page must be `https://` and comes from PayMongo's answer, never from a customer.
- Two reviewers, or a reviewer and a webhook, at once: the due row is locked first in every path, decisions carry the claim version, and the confirmation reply is a delivery unique per run and step, so one confirmation goes out.
- An unassigned staff member deciding: a due with an assigned reviewer is decided by that reviewer or the owner (403 otherwise).
- Rows of another workspace: every query filters by the workspace from the session or the webhook path, and all queries are parameterised through Drizzle.
- A late or second payment: a payment after the deadline or after a manual confirmation is parked as a checkout claim for a person, never counted as a second confirmation.
- Remaining risk: the rate limit and the byte budget are per API instance; a holder of one pay link can keep 5 references waiting for that order; reminders can reach a customer who paid but is not confirmed yet; the Expire API is checked against the fake only until the live check.

## Telegram message trigger (T9, decision 0117)

- A forged message: the path is 32 random bytes and only finds the connection. `X-Telegram-Bot-Api-Secret-Token` must equal an HMAC of the path keyed with the encrypted bot token, compared in constant time before the body is parsed. An unknown path is 403, a missing or wrong secret 401. The secret is never returned or logged; it is only sent to Telegram in `setWebhook`.
- Replay and retries: runs are keyed `telegram:<bot id>:<update_id>` per workflow, so a replayed or retried update starts nothing new.
- Strangers: with "my chat only" (the default) a message from any other chat starts nothing. With "anyone" a stranger can start runs and spend AI and upload usage, which the plan limits cap.
- Hostile files: one file per message, from Telegram's fixed file server (`TELEGRAM_API_URL`, env only), with no redirects. Sizes are capped at 5 MB at every step and while reading, the `file_path` must match a plain path pattern, and the bytes must sniff as JPEG, PNG, WebP or PDF. The token is in the download URL, so no error includes the URL.
- The bot sent elsewhere: a reply's chat id is allowed only under this trigger and must equal the run's `trigger.chatId`, so text in a message cannot redirect the bot.
- Personal data: sender names and chat ids become run data like a DM, under the privacy export, delete and retention of decision 0094.
- Remaining risk: Telegram shares a few source addresses, so the per-address rate limit is shared by every bot on the installation. Untested against the live Bot API.

## Shopify (I2, decision 0105)

- A forged order: the path is 32 random bytes and only finds the connection. `X-Shopify-Hmac-Sha256` must be the base64 HMAC-SHA256 of the raw body with the app's client secret, compared in constant time before the body is read. A bad or missing signature is 401, an unknown path 403, and a signed call for another store (`X-Shopify-Shop-Domain`) 403.
- Replay: Shopify signs no timestamp, so a captured delivery stays valid. Runs are keyed `shopify:<shop>:order:<order id>` per workflow, so a replay, a retry or a resend with a new webhook id starts nothing. A replay can only repeat an order that already ran.
- Secret and token leakage: the client secret and any older Admin API token are encrypted per workspace and never returned. Tokens from the client credentials grant live only in process memory. Calls send them in the request body (token request) or the `X-Shopify-Access-Token` header, and no error echoes a header or body. The stored values are in the history redaction list.
- A secret sent to the wrong host: `normalizeShopDomain` allows only `*.myshopify.com` and runs before every request, including the token request, so an edited destination cannot redirect the secret. `SHOPIFY_API_URL` is env only, for tests.
- Least privilege: the card asks for `read_orders` and `write_products` only. Customer name, email and phone in the order become run data like a form submission, and fall under the privacy export, delete and retention of decision 0094.
- A stranger writing to the store: a product step cannot read `{{trigger.*}}` from a public form, an unsigned webhook, inbound email or a DM. Descriptions are HTML-escaped and images must be https links.
- Duplicate products: Shopify has no idempotency key for product mutations. A create with a SKU checks for that SKU first and on a retry takes the one it finds as its own; a create without a SKU goes to review after an unknown outcome, never to an automatic retry.
- A changed store: each product delivery is pinned to the shop connected when it was queued; after a reconnect to another store it waits for review.
- Remaining risk: a leaked client secret lets someone forge orders until it is rotated in the Dev Dashboard and replaced in Apps. Signature handling and the token grant are checked against Shopify's documentation only until the [live check](live-shopify-check.md) is run.

## Airtable, Notion and Trello (decision 0046)

- The Airtable token, Notion secret and Trello key and token are encrypted like the Slack token, bound to the owner and provider, and never returned or logged. Trello's key and token are in its request URL, so Daloy never prints a request URL or puts one in an error message.
- The three addresses are fixed or set by the installation's env vars, never by a user.
- Ids are validated at the boundary (a Notion link is reduced to its 32-character id), and the target is pinned to each delivery when it is queued, so editing the connection cannot redirect what is already queued.
- Airtable takes only a table id, which a rename does not change. A collaborator who renames a table and gives another one its name cannot redirect records. Connections saved by name before this change send nothing until reconnected (security review M16).
- Field values come from run data and go only to the owner's own base, database or list. Keep private details out of anything the whole board or workspace can read.
- A leaked token lets someone write to what it was granted. Revoke it at the provider, then Replace token in Apps. Grant the narrowest scope: Airtable data.records read and write on one base, Notion access to one database.

## Form files and Google Drive (decision 0051)

- A file that runs in the browser: types are read from the first bytes (JPEG, PNG, WebP, HEIC or HEIF, PDF); SVG, HTML and every other type are refused whatever the name or the browser says. Downloads are always attachments with the stored type, `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and `Cache-Control: private, no-store`. Nothing is shown inline, so a PDF's scripts only run if someone opens the downloaded file.
- Large or many uploads: 5 MB per file, 3 per field, 5 per submission, 50 text fields of 64 KB at most. The 10 posts a minute per IP guard runs before the upload parser, so a blocked address is refused before its body is read. Remaining risk: the parser holds up to 25 MB per request in memory, and many addresses together are not capped.
- Filling the database: each workspace may store a number of files per Manila day (Pilot 100, Business 500, Business Plus 2000, 20 without a plan, 20 on Preview). On a tracked form the claim is made in the request's own transaction, so repeated posts with one submission key spend it once (M15), counted before storing. Files are deleted 7 days after upload, and with their run. An invalid or replayed submission stores nothing.
- A caller pointing a run at someone else's file: only the hosted form handler sets a file field; values from webhooks, MCP, test runs and the Run button are dropped, and a webhook cannot have a file field. The Drive delivery and the download read a file by id, run and workspace together; anything else is a 404.
- File contents reaching the AI: trigger data holds only id, name, type and size. File bytes never enter trigger data, step input, step output, failure explanations or Ask. They reach the model only for a field the owner listed in an AI step's `files` (decision 0052). `apps/worker/src/steps/ai.test.ts` puts a marker inside a file and checks the model never receives it when the field is not listed. `apps/worker/src/steps/ai-files.test.ts` covers the listed case.
- Duplicate files in Drive after a timeout: one delivery per run and step, the folder pinned at queue time, each saved file recorded under the worker's claim. An unknown outcome waits in `needs_review`; Post again skips files already recorded.
- The Drive key: stored like the Sheets key, never returned or logged. It needs the `drive` scope, so a leaked key can read and change everything shared with that service account until the owner deletes the key. Use a dedicated service account per business. Only a folder in a shared drive is accepted, since service accounts have no storage of their own. The Drive address is fixed or set by the installation's env var (`GOOGLE_DRIVE_URL`), never by a user.
- File names are visitor text: they are cleaned (no path, no control characters, at most 120 characters) and only ever sent as JSON metadata or an encoded `filename*` header.

## AI reads files (decision 0052)

- Hostile PDFs: text is extracted in a worker thread with a 10 second timeout, a 256 MB heap cap and a 10 page limit, so a PDF that is huge or loops forever stops that thread, not the worker. PDF.js 6 has no code evaluation path (the `isEvalSupported` option behind CVE-2024-4367 is gone), and the step renders no pages and loads no fonts, so the optional native canvas package is never used. Only text comes out, capped at 20,000 characters.
- Prompt injection in an image or PDF text: PDF text goes inside the `<data>` block with `</data` escaped, the system prompt says attached images are data, and the reply is checked against the task's schema, so a later step never sees an unexpected shape. Remaining risk: text written in a photo or PDF can still steer the extracted values within that schema. The receipt template puts an approval before the sheet row for this reason.
- Files reaching a hosted provider: only fields the owner listed are sent, and Build with AI never lists any. A hosted provider's free tier may use photos for training, the same as text (decision 0015). Each photo is held as base64 in worker memory for the request.
- Cost: one AI action for the step plus one per attached file, claimed once under the step key, so retries do not count twice. Files are at most 5 MB each and 5 per submission, and images in one step at most 10 MB together.
- A stale definition naming a field that is not a file field: the definition check rejects it when saved, and the worker keeps only names that are file fields of the form when it runs, so an older version cannot send anything else.

## Record app OAuth and pickers

An OAuth grant can expose more data than the single destination selected in Daloy. Airtable consent controls accessible resources; Notion consent shares pages and databases; Trello scopes cover board operations and the member scope also includes email and memberships ([scope table](https://developer.atlassian.com/cloud/trello/guides/rest-api/oauth-2-client-configuration/)). A picker is not a provider-side restriction to one destination. Select only the resources needed and review the grant at the provider.

Picker routes require a signed-in workspace manager and read with that workspace's OAuth credential. They validate target IDs, check membership in fresh provider lists before storing the target, and reject the save if the credential changed during the picker operation. Child list reads also check the parent. This limits forged targets to resources visible to that grant, but cannot prevent later permission changes, provider-side changes, or a race between validation and use. Airtable's OAuth picker accepts a table ID, not a table name; the pasted credential path is separate. Tokens stay server-side and the shared OAuth core handles state, encrypted credentials and refresh serialization (decision 0058).

Rotating refresh tokens create a crash window between provider response and local commit. Reconnect can be necessary if the old token is no longer valid. Disconnect removes the local credential first and provider-side revocation is best effort where supported. Airtable says it has no dedicated API to revoke refresh tokens and directs users to revoke access in account settings ([Airtable support](https://support.airtable.com/articles/6811769763-third-party-integrations-via-oauth-overview)). Trello OAuth 2 revocation behavior remains unverified. Never include tokens, callback URLs containing codes, or personal records in check results. Live consent, refresh, revocation and destination behavior remain unverified until the owner runs the documented check.

## Facebook Messenger and Instagram DMs (N16, decision 0075)

- Spoofed Meta webhooks or challenge probes: `GET /hooks/meta/:path` requires an active `meta_messenger` connection matching the random 32-byte path, `hub.mode === "subscribe"`, and a constant-time match against the workspace's decrypted `verifyToken` (403 otherwise). `POST /hooks/meta/:path` verifies `X-Hub-Signature-256` against raw request bytes with HMAC-SHA256 and `timingSafeEqual` (401 on missing or invalid signature), is rate-limited to 60 requests a minute per IP with a 256 KB body limit, passes echoes to the conversation (decision 0115), ignores delivery/read receipts, and drops events whose `entry.id` does not match the connected `pageId` or `instagramAccountId`.
- SSRF or malicious uploads through Meta image attachment URLs: attachment downloads allow only HTTPS port 443 on `*.fbcdn.net`, `lookaside.fbsbx.com`, and `*.cdninstagram.com` (test override via `ProviderUrls.metaCdn` only), resolve DNS through an IP-pinned lookup blocking private, loopback, link-local, and metadata IPv4/IPv6 ranges, refuse redirects, stop at 5 MB and 10 seconds, and accept only JPEG, PNG, or WebP magic bytes via `fileType` (rejecting HTML, SVG, and non-images). Verified files count against the workspace's daily `upload` quota and only metadata references enter `triggerPayload`.
- Replayed webhooks and reused GCash or bank screenshots: incoming messages are deduplicated per `(workflowId, test: false, "meta:" + mid)` in `run_keys` inside the run transaction. Distinct messages carrying the same normalized receipt reference are flagged in `receipt_references` per workspace with a warning shown on the owner approval, and the starter template logs rows as "Pending verification" and never auto-marks an order paid.
- Meta credential exposure: `pageAccessToken`, `appSecret`, and `verifyToken` are encrypted with AES-256-GCM bound to `${userId}:connection:meta_messenger`, write-only in the API, never echoed in connection responses or provider errors, and loaded by `secretValuesToHide` so `historyHider` redacts all four encoded forms on every read surface. Auth failures (401, 403, or Meta code 190) mark the connection failed fenced by credential IV; 24-hour window errors (code 10, subcode 2018278) fail without altering connection status; timeouts and 5xx writes park in `needs_review`. Remaining risk: live Meta webhook behaviour and App Review permissions (`pages_messaging`, `instagram_manage_messages`) remain unverified until the owner runs [docs/live-meta-check.md](live-meta-check.md).


## Guest conversations (C1, decision 0115)

- Assets: guest message text, saved details (dates, guests, name, phone, email) and the reply history in `conversations` and `conversation_messages`, and the copy of the last 10 messages in each answering run's trigger payload.
- Entry points: the signed Meta webhook and the email-in poller, the only writers of inbound messages; `meta_reply` and `conversation_update` in the worker.
- A forged or replayed message: inbound text is only stored after the Meta signature check or from the owner's own mailbox, and a replayed `mid` or Message-ID adds nothing and starts no run. A guest can only move their own conversation: the key is the workspace, channel and sender id from the signed event.
- A guest who silences the bot: only an echo, which Meta sends for messages the Page itself sent, can set `staff`; a guest message never can. A staff echo is told apart from Daloy's own by the `metadata` mark and by matching recent reply text. Remaining risk: if another app on the Page sends messages, its echoes also pause the bot, which errs on the side of not answering.
- A stale reply after the guest wrote again: older runs stop at their next step and their queued deliveries are not sent, checked under a share lock on the conversation row while the provider is called.
- Keeping data too long: the worker deletes conversations, messages and the linked runs' content after the workspace's retention days (90 by default). R6 export and delete cover conversations and messages, including a Messenger guest with no email, matched by any phone or email in a message.
- Sending outside Meta's window or after a staff takeover: `meta_reply` checks `last_inbound_at` and the staff status before queuing and takes `outside_window` or `paused`; the delivery checks the window again before sending.
- Notice: the first reply says the bot is automated, what is kept, for how long, and that messages go to the AI provider. Remaining gap: no link to the resort's own privacy notice yet.

## Menu buttons (C2, decision 0118)

- A forged tap: quick replies and postbacks go through the same `X-Hub-Signature-256` check as messages, so an unsigned or wrongly signed postback is refused with 401 before anything is read.
- A payload chosen by someone other than the Page: anyone can send the Page an event with any payload. Only the fixed choice ids are kept, and only for a workflow whose published menu offers that choice. Anything else is dropped (a postback whole, a quick reply down to its text), so `{{trigger.choice}}` is always a known word and a payload can never carry a template, a step id or a link.
- A replayed tap: the tap's `mid` keys the run in `run_keys` and the conversation message, so a replay starts nothing. A postback without a `mid` is dropped.
- Email numbers: a reply's number only picks from the workflow's own email menu; a number outside it, or a line with more than a number, sets nothing.

## Platform admin page (A1, decision 0122)

- Assets: every workspace's counts, owner emails, plans and shared mail approvals, and run metadata across tenants.
- Entry points: `GET /admin/overview`, `GET /admin/runs`, `PUT /admin/workspaces/:id/plan`, `PUT /admin/workspaces/:id/shared-mail`, and the `#/admin` page.
- A normal user reaching cross-tenant data: `AdminGuard` sits on the whole controller and looks up the session itself. A missing or expired session, or an email not in `PLATFORM_ADMINS`, gets 404, so the routes look absent. Workspace roles play no part: a workspace owner is refused like anyone else. An empty allowlist turns the page off. `admin.test.ts` sends every registered `/admin` route as an owner, an operator and a signed-out client and expects 404 each time.
- Cross-site changes by an admin's browser: PUT routes need this installation's own Origin, as with `SessionGuard`.
- Leaking customer data or secrets to the admin: the queries live in `packages/db/src/admin.ts` and select named columns only. They never return trigger payloads, step input or output, error text or delivery payloads, and the module imports no secrets code (`packages/db/src/admin.test.ts` checks its imports and source). Reads run in a `SET TRANSACTION READ ONLY` transaction, so Postgres refuses a write on that path.
- The database role: the API keeps connecting as `daloy_app`. No grant changes, because that role could already read every table; tenant isolation is the `workspaceId` filter in app code, and only `AdminController` calls the unfiltered queries.
- Untraced changes: each plan or shared mail change and its audit row are written in one transaction with the old and new values and the admin's email. No route edits or deletes `admin_actions`.
- Abuse of an admin session: reads are limited to 30 a minute and changes to 10 a minute per admin, on top of the global limit.
- Remaining risks: a stolen admin session can read every workspace's counts and change plans; there is no second factor. Rate limit counters live in process memory. Owner emails are visible to admins by design.

## Guarded answers and stay quote (C4, decision 0119)

- Assets: rate accuracy on guest quotes, payment due amounts, guest email and phone data, and the integrity of links sent under the resort's Page.
- Entry points: inbound guest messages routed into an `ai` (`answer`) step, model responses returned to `runAnswer`, `stay_quote` step inputs, and `payment_due` step `amount` and `total` templates.
- Invented or uncited prices and availability claims: `guardReply` parses every peso figure and rate-phrase number in the model reply and replaces the reply whenever any number is absent from the priced entries (`room`, `rate`, `fee`) listed in `entryIds`. Availability claims in English or Tagalog are replaced with a fixed team-check message and `needsHuman: true`.
- Prompt injection and phishing links: guest messages stay inside delimited `<data>` blocks in the user message, never in the system prompt, and `guardReply` strips any URL or bare domain not present in the published knowledge sheet or the step's pay link, as well as `{{...}}` braces and contact placeholders.
- Guest contact data sent to the AI provider: `answerPrompt` runs `redactContacts` over both the current message and conversation history before calling the model, replacing emails and phone numbers with `[email]` and `[phone]`, while `contactsIn` extracts them locally in code.
- Tampered payment amounts (L7): `untrustedSource` in `definitionSchema` walks step references transitively across `payment_due.amount` and `total` and rejects any chain reaching an `ai` step or a `{{trigger.*}}` field from an untrusted trigger (`meta_dm`, `form`, `email`, `telegram_message`, or unsigned `webhook`), so guest text or model output cannot set a payment amount through `stay_quote` or an intermediate step.
- Remaining risks: live model answer quality in English and Taglish is unverified until C9's 50-conversation measurement; `guardReply` rate and availability regexes can false-positive on harmless phrasing, erring on the side of handing off to staff.

## Stays (C5, decision 0120)

- Assets: room inventory ranges in `bookings`, guest contact details exposed via `bookings.conversation_id`, and pre-arrival reminder schedules.
- Entry points: `POST /bookings/stays`, `GET /bookings`, `GET /bookings/:id`, `POST /bookings/:id/reschedule`, MCP booking tools, and the `booking` workflow step in `mode: "stay"`.
- Unauthorized stay creation from guest text: `definitionSchema` restricts stay-mode `create` steps to `manual`, `payment`, or HMAC-signed `webhook` triggers, and `untrustedSource` transitively rejects any input derived from an `ai` step or a guest-facing trigger (`meta_dm`, `email`, `form`, `telegram_message`, unsigned `webhook`). Staff Confirm stay (`POST /bookings/stays`) requires an authenticated `owner` or `operator` session (403 for approvers and requesters, 401 signed out).
- Cross-workspace resource or conversation linkage: both `confirmStay` and `bookFromStep` verify `resources.user_id = workspaceId` (and `active = true`) and `conversations.user_id = workspaceId` inside the transaction, returning 404 or `not_found` for any foreign or missing id without leaking existence.
- Double-booking and race conditions: Postgres `bookings_no_overlap` rejects overlapping ranges across all nights atomically, and `confirmStay` serialises matching `(user_id, idempotency_key)` calls on a per-key advisory lock and partial unique index.
- Guest PII retention after deletion or purge: `booking_changes.result` omits `guest` contact fields and reads them live from the joined `conversations` row; `bookings.conversation_id` uses `ON DELETE SET NULL` and R6 `collect()` includes bookings linked via `bookings.conversation_id`, so customer deletion or conversation retention purge clears the link and change-log results while preserving only the non-personal held range.

## Daily tools (R5, decision 0093)

Assets: the owner's inbox, confirmed payment records, customers' receipt photos.

Entry points: `GET /payments/export.csv`, `GET` and `PUT /settings/digest`, `GET /public/compress.js`, and the worker's digest tick.

- Customer data in an email: the digest carries three counts and links to the console, never a customer name, number, reference or amount. It goes only to the owner's login address, through the installation's server.
- A surprise or repeated email: it is off until the owner turns it on, sent once per Manila day by a conditional UPDATE, and not sent at all on a morning with nothing to do. A failed send is retried only until noon.
- Spreadsheet formula injection: the payments CSV uses the N19 `toCsv`, which puts a quote before a cell that starts with `=`, `+`, `-`, `@`, tab or return. The reference and the transfer reference are customer or workflow text.
- Who downloads payments: owners and operators of the workspace only (403 for approvers and requesters, 401 without a session). The query filters by the session's workspace and leaves out test runs, so another workspace's payments never appear. A range is at most a year.
- Turning the digest on for someone else: only the owner changes it, for their own workspace, and the body is strict (an extra field is a 400).
- The compression script: it is static, public and served from the same origin, so `script-src 'self'` still holds and no inline script is added. It is a convenience, not a control. The server still reads the file type from the bytes, refuses anything over 5 MB and counts the upload against the quota, so an edited or skipped script gets the same checks. It only touches files the visitor already chose in that input.
- Remaining risk: the digest says an order is unpaid even while a reminder is already queued, so the number can overstate the work; the digest needs the installation's SMTP server; a worker that is down all morning sends no digest that day.


## Disable a step (U3, decision 0097)

Assets: the sends a workflow makes (emails, HTTP calls, messages, payment links).

Entry points: the saved definition (`POST /workflows/:id/versions`, the editor, MCP), read by the worker.

- A turned-off step still sending: the worker checks the flag before it creates an attempt, so no executor call, claim or retry happens for that step. A worker from before U3 would ignore the flag and send, so the engine and worker are deployed together.
- A turned-off step changing the route: the definition check refuses `disabled` on any step that branches, so a skip always has one edge to follow and the run cannot take a path the owner did not draw.
- Turning off a safety step: an owner can turn off an approval's follow-up or a notification like they could delete it. Turning off an approval itself is refused because it branches. The run history shows every skipped step with its reason, so the change is visible after the fact.

## Customer privacy (R6, decision 0094)

Assets: customers' receipt images, DM and form text inside run data, the export file the owner downloads, the audit rows.

Entry points: `GET /privacy/customer` and `POST /privacy/customer/delete` (owner session), the notice on public forms and the pay page, and the worker's receipt image sweep.

- Someone other than the owner exporting or erasing customer data: both routes are owner-only (403 for operators, approvers and requesters, 401 without a session).
- Reaching another workspace's customer: every query filters on the session's workspace id, and rows are found through that workspace's runs, dues and events. The same email in two workspaces is two separate customers.
- Erasing the wrong customer by accident: the delete needs the typed word DELETE, exactly one identifier, and a valid email or phone. An email matches only as a whole address, so `maria@x.com` does not touch `annamaria@x.com`.
- Abuse of the endpoints: a per-owner rate limit, and a scan limited to one workspace.
- The audit trail holding the data it is meant to protect: `privacy_requests` stores counts and fixed reasons only, never an email, phone, name or deleted value.
- The export file leaking: it is an attachment with `Cache-Control: no-store`, and it holds receipt images as base64, so the owner should treat it as sensitive.
- Workspace secrets in the export: the file goes to the customer, so it passes through the same history hider as the run page (current and retired secret values, then secret-looking keys). Review of 22 November, M3.
- The identifier in the URL: the export takes the email or phone in the query string, which a proxy may log (review of 22 November, L2). Planned as a POST before the pilot.
- Matching limits: a customer who used another email or number is not found, and a number written in an unusual way may be missed. The owner can repeat the request per identifier. The scan reads every run in the workspace, which is fine for small workspaces.
- Data outside Daloy: copies already sent to Sheets, Slack, Telegram, Airtable, Notion, Trello, Drive, Google Calendar or email are not reached. The export lists the deliveries so the owner can find them.
- Event keys: a `run_keys` row can hold an event key the workflow built from customer data. The delete does not rewrite it.
- Backups keep old data until they roll over.
- Old receipt images: removed by the worker after the retention days (default 90) once the due closes. Open dues keep theirs.
- Remaining risk: Daloy provides tools only. It does not make a business compliant with any law, and the owner's own duties are listed in docs/how-it-works.md.

## Read a public page (phase B1, decision 0107)

- Asset: the private network around the worker (database, cloud metadata, other services), the daily request cap, and the prompts of later AI steps.
- Entry points: the `url` of a `read_page` step, which can come from a template and so from a public form; the page that answers; the robots.txt of that host.
- SSRF: the step uses the same guarded request as the http step, so scheme, port, private, loopback and link-local ranges, DNS answers and every redirect hop are checked as before. A redirect to a private address is refused, and `HTTP_ALLOWED_HOSTS` limits the demo instance. Tests in `read-page.test.ts` cover a private address, a host that resolves to one, a redirect to one and a `file:` address.
- Large pages: the body is cut off at 2 MB while it is read, only `text/*` and `application/xhtml+xml` are accepted, the request has a total timeout, and `maxChars` (at most 20,000) limits what is kept. robots.txt is read up to 500 KB.
- Abuse of the owner's quota or of other sites: each step claims one request against the daily cap, the user agent names the bot and a page address, and robots.txt is honoured before the page is fetched. A server error on robots.txt stops the step instead of reading the page.
- Page text as untrusted input to later AI steps: a page can say anything, including instructions for a model. The AI step puts the resolved input only in the user message, inside `<data>` tags, tells the model it is not instructions, and rewrites a closing `</data` tag inside the text. A test sends a hostile page text through the template and `buildPrompt`. The AI step has no tools, and its output is checked against a schema, so an injected instruction can change a label or a summary but cannot call anything. Other steps that read `{{steps.<id>.output.text}}` (an email, an SMS) put the text in a message the owner designed, so a workflow should not send page text to people without a check.
- Page content in run history: output is stored like any step output. The step reads public pages only and sends no cookies or credentials, so it cannot read a page behind a login.
- Remaining risk: a page can change its text on purpose to trigger alerts. The step cannot tell a real price change from one made to be noticed. A DNS answer that changes between the check and the connection is handled by the guarded lookup, which connects to the address it checked.

## Discord and Google Docs steps (phase I1, decision 0104)

- The Discord webhook URL carries its own token, so it is a secret: anyone holding it can post to the channel. It is stored encrypted (AES-256-GCM, owner and provider bound in), write-only through the API, and never put in definitions, run history, deliveries, step results, logs, errors or AI prompts. The Apps card shows the channel name only. Remaining risk: with `SECRETS_KEY` and a database copy, an attacker can post to the channel until the owner deletes the webhook in Discord.
- The one user-entered URL is checked before it is stored and again before every call: https only, host `discord.com` or `discordapp.com` or a subdomain, no user info or query, the exact webhook path, redirects refused. That stops a pasted address from reaching an internal host (SSRF). Only the operator can add a host, with `DISCORD_WEBHOOK_HOSTS` (empty by default, for tests and local fakes), like the other provider address variables.
- Text from a public form can end up in the channel, so messages are sent with `allowed_mentions.parse` empty and cannot ping `@everyone` or a role. Everyone in the channel can read the text; the Apps card says to keep names and emails out of it. Messages over 2000 characters fail without a request.
- A Discord post that may have gone out (5xx, connection lost) goes to `needs_review`, so a person decides whether to post again. 429 waits for Discord's own wait.
- Make a document uses the existing Google Drive grant, `drive.file` only (no new scope). Daloy can open only the template the owner picked in the Picker, the folder picked in Apps and the copies it made itself. The template id from the browser is read with the grant first, so a forged id gets a 404 and nothing is stored. Only a Google Docs document is accepted.
- A visitor's text used as a placeholder value is inserted as plain text and never read as another placeholder (two-pass replace with a random token). A document made from visitor text lives in the owner's own Drive and is not shared by Daloy.
- Remaining risk: a retry can leave a second copy of the document when Drive's file list lags; it stays in the owner's folder. A document holds whatever values the workflow puts in it, so a template meant for customers should not receive more than the customer needs.

## Browser step and browser service (phase B2, decision 0108)

- SSRF through the browser. A page, its redirects, iframes, scripts (`fetch`, WebSockets) and service workers could aim the browser at Postgres, the API, the host or cloud metadata. Every connection Chromium makes goes through the job's forward proxy, with no bypass list (Playwright then forces even loopback through it). The proxy resolves the host once, refuses it when any answer is in `BLOCKED_RANGES` (the same list as the HTTP step, now in `@daloy/engine`) or the port is not 80 or 443, and connects to the exact address it checked, so DNS rebinding cannot swap the address after the check. The browser is launched with a deny-all proxy, so a context without its own proxy reaches nothing. Service workers are blocked, and `context.route` aborts anything that is not http or https as a second check. The service is on its own Docker network, so Postgres, Mailpit and the API are not reachable by name, and a check on 23 November 2026 showed a container on the default network was not reachable by IP either. Tests: `apps/browser/src/proxy.test.ts` (literal, DNS, mixed answers, IPv4-mapped IPv6, ports, deny-all) and `service.test.ts` (a redirect, an iframe, a `fetch` and a WebSocket aimed at 127.0.0.1 never reach the internal server). Private addresses are allowed only through an option the tests pass.
- Page scripts. Any public page's JavaScript runs in Chromium. Each job gets a fresh context, closed afterwards, so nothing carries over between jobs or workspaces. Downloads are off, file choosers never get a file, passkeys always fail, QUIC is off and WebRTC is limited to proxied UDP. The container drops all capabilities, has `no-new-privileges`, a read-only root with tmpfs for `/tmp` and home, `init` and a process limit. Chromium's own sandbox is off (Playwright's default in containers), so a Chromium exploit lands in this container, which holds `BROWSER_TOKEN` and nothing else: no database address, no secrets key, no provider tokens. Remaining risk: from there it can reach any public address and make other browser jobs fail.
- Typing secrets. The step resolves without secrets. `fill` refuses password, one-time code and card fields, read from the element right before typing, and any value that is a card number. Remaining risk: a page can change a field's type between the check and the typing; the value is the owner's own template value.
- Resource exhaustion. A heavy or hostile page could take memory, CPU or time. A job has 60 seconds in all (`BROWSER_JOB_SECONDS`) and 10 seconds per action, with 20 actions and 5 screenshots at most. `BROWSER_CONCURRENCY` (2) jobs run at once and one more answers 503. The container has `mem_limit: 2560m`, `pids_limit: 1024` and `shm_size: 1g`, so a runaway page stops at the container and the rest of the stack keeps running. Request bodies are capped at 256 KB and a snapshot at 40,000 characters. Each step counts one web request against the daily cap.
- What comes back. The worker treats the service as untrusted: it checks the answer's shape and stores only PNG screenshots under 5 MB. A page's text reaches later steps as data. B3 will mark page text as untrusted before any of it reaches a model.
- Unknown outcomes. A time-out or a lost answer after a click or a fill may already have done something on the site, so it goes to review instead of a retry.

## DM receipt photo claims and email reply threading (phase C6, decision 0121)

- Assets: payment confirmation integrity (`payment_dues.status`), Receipts to review queue capacity, upload quotas, and outbound SMTP/Gmail MIME headers.
- Entry points: Meta DM webhook (`POST /hooks/meta/:path`, signed with `X-Hub-Signature-256`) and inbound IMAP email headers (`Message-ID`, `In-Reply-To`, `References`).
- Fake or replayed receipt photos marking a due paid: a DM receipt photo never changes `payment_dues.status` from `pending`. It only creates an open `payment_claims` row for human review through the same `evaluateTransferClaim` pipeline as the pay page (flagging `duplicate_reference` across `payment_claims` and `receipt_references`, `amount_mismatch`, and `unreadable_upload`). Webhook replays are deduplicated by `unique (user_id, source_mid)` under the due's row lock, charging at most one upload and creating at most one claim. Claims are refused on test, confirmed, cancelled, or refunded dues and capped by `OPEN_CLAIMS_PER_DUE` (5).
- Malicious image URLs or oversized uploads in a DM: every DM image passes the existing SSRF-safe Meta CDN downloader (`isAllowedMetaCdnUrl`, IP-pinned DNS lookup, no redirects, 5 MB cap, JPEG/PNG/WebP magic-byte check) before reaching `submitDmReceiptClaim`, and only the first verified image per message creates a claim.
- SMTP or MIME header injection via inbound email headers: untrusted `Message-ID`, `In-Reply-To`, and `References` headers are rejected on any CR, LF, NUL, whitespace, or non-RFC-5322 syntax (`sanitizeMessageId`, `sanitizeReferences`) both on IMAP ingest and again inside `buildThreadHeaders` right before nodemailer constructs the SMTP or Gmail API RFC 822 message. The `References` chain is capped at 20 message-ids (preserving the thread root). Internal `imap:` dedup keys fail `sanitizeMessageId` and never reach outbound headers.
- Thread header leakage to staff alerts or other recipients: the `email` step attaches `In-Reply-To` and `References` only when the run belongs to an `email` conversation and the resolved recipient list is a single address matching `conversations.external_id` (case-insensitive). Staff alerts and multi-recipient emails receive no guest thread headers and are not written to `conversation_messages`.
- Remaining risk: a guest who sends a receipt screenshot with no text caption creates a claim with no extracted reference number; the reviewer still inspects the image and verifies the real GCash or bank history before confirming.

## Conversations inbox, staff alerts and R6 privacy (phase C7, decision 0125)

- Assets: conversation messages and extracted guest fields, `users.staff_alert_psid`, Messenger Page Access Tokens, Telegram bot tokens, staff alert email/DM channels, and customer R6 exports/deletions.
- Entry points: authenticated endpoints on `ConversationsController` (`GET /conversations`, `GET /conversations/:id`, `POST /conversations/:id/take-over`, `POST /conversations/:id/hand-back`, `PUT /conversations/:id/fields`, `POST /conversations/:id/alert`, `POST /conversations/:id/deposit-request`, `PUT /conversations/settings`, `POST /conversations/:id/export`, `POST /conversations/:id/delete`) and `POST /privacy/customer/export`.
- Cross-tenant access or privilege escalation: every conversation query filters by `eq(conversations.userId, user.workspaceId)`. Viewing, replying, editing fields, alerting, and deposit requests require `OPERATE` (owner or operator; approvers and requesters receive 403); retention, alert settings, and R6 export/delete require `MANAGE` (owner only) plus explicit `"DELETE"` confirmation. `POST /conversations/:id/export`, `delete`, and `alert` apply `RateLimit(20)`.
- Guest PII or injection leaking into staff notifications: `sendStaffAlert` sends only sanitized single-line `firstName` (max 40 chars), stay dates/guest count, clamped single-line reason (max 120 chars), and the `#/conversations` link, stripping CR/LF/tab characters so header injection in installation alert emails is impossible and raw guest messages never leave the inbox.
- Silent Meta alert drops after 24 hours: `staffAlertStatus` checks `windowOpen(staffLastInbound)` on `staffAlertPsid`; when the staff member's 24-hour Messenger window is closed or unconfigured, `sendStaffAlert` falls back to Telegram and then installation email.
- Empty PATCH/PUT settings error: `saveConversationSettings` short-circuits cleanly to `conversationSettings` when no fields are changed, avoiding an invalid empty SQL `UPDATE`.

## Resort templates, Concierge plan and C9 security review (phases C8 and C9, decisions 0126 and 0127)

- Assets: `users.plan` (`concierge` quota ceiling), price and stay-booking integrity across pre-built templates (`resort-concierge-dm`, `resort-concierge-email`, `resort-deposit-and-stay`), and `guardReply` deterministic checks.
